# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start Next.js dev server with TurboPack on http://localhost:3000
- `npm run build` — production build. **Requires a reachable `DATABASE_URL`** (in `.env.local` locally; the Neon integration provides it on Vercel): prerendered pages read the portfolio through `src/lib/projectsStore.ts` at build time — the Navbar/Footer project panel alone puts every route on that path.
- `npm run start` — serve the production build
- `npm run lint` — runs the ESLint CLI directly (`eslint .`) against `eslint-config-next`'s **native flat configs** (`core-web-vitals` + `typescript`) in `eslint.config.mjs`. `next lint` was removed in Next 16, so don't reintroduce it.
- `npm run optimize-images` — `node scripts/optimize-images.mjs`, shrinks any over-budget asset in `public/images` in place (quality-safe; wrapped by the `/optimize-images` skill). `scripts/` also holds one-off image tooling not wired to npm: `migrate-images-to-avif.mjs` (ImageKit → self-hosted AVIF, with `--max-dim` downscale), `reduce-images.mjs`, and `generate-dotted-map.mjs` (world-map dot data).
- `npm run image-variants` — `node scripts/generate-image-variants.mjs`: pre-generates the responsive `-384/-640/-960/-1280` rungs next to every laddered image in `public/images` **and** regenerates the blur-up LQIP map `src/lib/imageBlur.generated.json`. Idempotent (skips up-to-date variants; `--force` rebuilds, `--dry-run` previews, optional subfolder arg). **Run it whenever images are added and commit the generated files with them.** The rung ladder + "what gets variants" rule live in `src/lib/imageVariants.ts` and are mirrored by the script and `deviceSizes` in `next.config.ts` — keep all three in sync.
- `npm run indexnow` — `node scripts/indexnow-submit.mjs`: pings IndexNow (Bing → Copilot/ChatGPT-search grounding) with changed URLs. **Run it after any content change deploys** — `npm run indexnow -- /blogs/<slug>` for a post, `npm run indexnow -- --sitemap services` after services-copy changes (`--dry-run` previews). Saman forgets this, so Claude should run it proactively (or remind explicitly) whenever a content change ships. Project edits in /admin ping automatically (`src/lib/indexnow.ts`, `after()` in `_actions/projects.ts`), and so do careers edits — `_actions/careers.ts` pings `/contact/careers` only when a non-draft listing's public fingerprint changed, and `/frequently-asked-questions` too when the open set changed (a draft edit, a reorder, or an icon swap pings nothing). **Client edits do NOT** — `_actions/clients.ts` only invalidates caches (its `after()` calls are blob cleanup, not pings), so when a client rename changes visible copy on `/`, `/about`, or project cards, ping those URLs manually. A logo swap or marquee reorder changes pixels rather than indexable text and is deliberately left unpinged. **Never ping unchanged URLs** — false freshness is a Bing spam signal, which is why this is a manual command and must never become a deploy hook. The key file `public/<32-hex>.txt` is public by protocol and must stay byte-identical with `INDEXNOW_KEY` in `src/lib/indexnow.ts`.
- `npm run psi` — `node --dns-result-order=ipv4first --env-file=.env.local scripts/psi.mjs` (`.env.local` supplies `PSI_API_KEY`; **keep `--dns-result-order=ipv4first`** — without it the googleapis call stalls on IPv6 from some networks, which is the "PSI is flaky" symptom): PageSpeed Insights v5 against the **live production site** — Lighthouse category scores, lab metrics (FCP/SI/LCP/TBT/CLS), and CrUX p75 field data, mobile + desktop in one run. Defaults to the homepage; `npm run psi -- /about /services` tests other paths, `--strategy mobile|desktop` narrows. Local changes don't move these numbers until deployed.
- `npm run db:generate` / `npm run db:migrate` — drizzle-kit against the Neon Postgres database (schema `src/db/schema.ts`, config `drizzle.config.ts`, migrations committed under `drizzle/`). Workflow for any schema change: edit schema → `db:generate` → `db:migrate` → commit `drizzle/` with the change. **Never use `drizzle-kit push`** — the schema will keep evolving (/admin, blogs) and needs migration history. `drizzle.config.ts` loads `.env.local` via dotenv (drizzle-kit doesn't read Next env files); `DATABASE_URL` comes from the Neon integration on Vercel.
- `npm run db:studio` — opens **Drizzle Studio** (`drizzle-kit studio`), a local read/write GUI over the Neon Postgres tables, at `local.drizzle.studio`. This is the way to browse/inspect the database in development (there is no in-app database viewer — a custom `/admin/database` route was removed in favor of this). Needs `DATABASE_URL` in `.env.local`.

- `node --import tsx scripts/check-search-terms.mts` — the search-tokenizer self-check (no DB, no env). Pins the strictness bug that motivated `src/lib/searchTerms.ts` and is easy to reintroduce: `"arshia real th"` could not find **"Arshia Real Estate TH"**, because the whole query was wrapped in one `%…%` and a contiguous substring cannot skip the word in the middle. It also pins the token cap (each token becomes its own OR over four correlated EXISTS on the task board), that `%`/`_` survive tokenizing as literals for `likePattern` to escape, that an empty query yields NO tokens and therefore WIDENS to everything rather than collapsing to a pattern matching nothing, and three refusals in `suggestQuery` that each exist to stop a confident wrong guess: a short token is never rewritten (at three characters half the vocabulary is one edit away), a token already present is never rewritten (it matched nothing only because a neighbour failed), and real words that simply never co-occur get no suggestion at all. The load-bearing one is that candidates are scored by **how many records match the whole corrected query**, not by edit distance — against the real board, distance-plus-longest-prefix confidently corrected `"ubc dilan th"` to a client called **Divan** instead of the task about **Dylan**, since both are one edit away and "divan" shares the longer prefix. ## Architecture

Next.js 16 / React 19 site using the **App Router** with TypeScript (Turbopack is the default bundler for both `dev` and `build`), split into two route groups: **`(marketing)`** — the public site — and **`(admin)`** — the team dashboard. Route groups don't affect URLs, but file paths carry the group segment. All routes are server components by default; interactive pieces opt in with `'use client'`. Services content is code-defined — `src/constants/*`, **no CMS** — while the portfolio (case studies + clients) and the blog (posts, authors, categories) both live in Neon Postgres. Both are managed from `/admin`: the portfolio from `/admin/projects` + `/admin/clients`, and the blog from **`/admin/blogs`** — the editor, its draft preview and its saved-version history (see "Services, projects & careers content model" and "Blog content model").

Mutations are server actions only. The public site has two: the `submitContact` server action (`src/app/(marketing)/contact/actions.ts`) validates with Zod (`src/lib/contactSchema.ts`), writes to **Neon Postgres via Drizzle** (`src/db/schema.ts` + `src/db/index.ts`, `server-only`-guarded), uploads career-application resumes to **Vercel Blob**, and emails notifications via **Resend**; and the blog's "was this article helpful?" vote (`src/app/(marketing)/blogs/[blog]/actions.ts`) upserts into `article_feedback` (tallies at `/admin/feedback`). The `(admin)` dashboard — Better Auth email+password + passkeys, public sign-up disabled, optimistic session-cookie gate in `src/proxy.ts` with real DB-validated sessions in `(protected)/layout.tsx` — manages the team's task board, per-client monthly reports, the leaderboard, tickets, the contact/careers inboxes, portfolio projects/clients, the blog (posts, authors, categories, media), payroll, company costs, users & per-area access, the activity log, and feedback tallies through server actions under `(protected)/_actions/`; private files (résumés, avatars, ticket screenshots) stream through authenticated route handlers. All email goes through `src/lib/mail.ts` (`sendMail` + the `NOTIFY_FROM`/`AUTH_EMAIL_FROM` constants — the one Resend door). **`text` is mandatory and `html` is an optional SECOND rendering of the same message**: ten of the eleven senders are still plain text, and the weekly digest is the one exception, because it is the only email that is read rather than acted on. A sender passing both must derive them from ONE fold (`src/lib/digestEmail.ts` returns `{ subject, text, html }` from a single pass) rather than writing each by hand; never add an `html` without its `text`, which is the multipart fallback several call sites treat as the record. `/api` routes: the Better Auth handler at `/api/auth/[...all]`, plus **six** `CRON_SECRET`-gated cron endpoints (`weekly-digest`, `recurring-tasks`, `due-reminders`, `payroll-nudge`, `monitoring`, `blog-publish`) invoked by the `crons` in `vercel.json`, the repo's only Vercel config file (exact schedules in the Route map below — they are staggered on purpose, not all at one hour), every one of them running inside `runCron` (`src/lib/cronRun.ts`), which owns the secret check and stamps the run's outcome for `/admin/monitoring`. Server secrets (`DATABASE_URL`, `RESEND_API_KEY`, `BLOB_READ_WRITE_TOKEN`, `PUBLIC_BLOB_READ_WRITE_TOKEN`, `BETTER_AUTH_SECRET`, `GOOGLE_PLACES_API_KEY`, `CRON_SECRET`, and the optional `VERCEL_API_TOKEN` behind the monitoring page's two Vercel reads — the recent request log and the request counts) are never `NEXT_PUBLIC_*`.

### Contact form (unified project + careers)

`/contact` renders `ContactHub` (tabs: "Inquiries" / "Join the team") behind the SSR-kept `dynamic()` wrapper `ContactHubLazy` — ContactHub is the only client importer of zod, so that weight stays in the contact async chunk. The server page derives slim props: `serviceGroups` (29-service picker projection from `CATEGORIES`) and `roles` (the `open` listings from `getOpenRoles()` in `src/lib/careersStore.ts` + `GENERAL_APPLICATION` from `src/lib/careerFields.ts`), plus `initialTab`/`initialRole` from `await searchParams` (`?tab=careers&role=<slug>` deep links pushed by the careers page's Apply cards — crawl-silent `NavButton`s, not `<a>`s; see "Conventions to respect" — this makes `/contact` request-time rendered, same trade as `/blogs`). Idempotency: the client generates one `client_id` per fill session (invalidated on any edit, so an *edited* resubmission is a new submission while an unchanged retry dedups); `contact_submissions.client_id` is unique and the insert is `onConflictDoNothing`, so outbox replays/retries can't double-write or double-email. Roles: `submitContact` resolves the slug through `getRoleTitleMap()` (every listing, any status, + General application) and stamps the title onto `contact_submissions.role_title` — a snapshot, because listings get deleted from /admin/careers and an application must outlive the posting it answered. An unknown slug is **stored raw, never rejected** (the same degrade policy as services and referral sources): a validation rejection makes the offline outbox permanently drop the queued record, so a role delisted between queue time and flush time would silently lose a candidate. Spam: honeypot (`pcs_extra` — the name/label deliberately avoid browser-autofill vocabulary like "organization", which would get autofilled for real visitors) + minimum-fill-time; flagged submissions are **stored with `status: 'spam'`** (no email) rather than dropped, so false positives are recoverable. Resume uploads: PDF ≤4MB (Vercel's hard body cap is 4.5MB — `experimental.serverActions.bodySizeLimit` in `next.config.ts`), magic-byte sniffed on both client and server, stored **private** in Blob (`resume_path` column); the notification email carries the PDF as an attachment, and /admin will stream it later via `get(pathname, { access: 'private' })`. There is no code-level rate limit — if abuse appears, add a Vercel WAF rate-limit rule on POSTs to `/contact` (zero code) before reaching for a Redis-backed limiter.

### Services, projects & careers content model

Services are **code-defined content** (not MDX); projects split between code-defined category chrome and **database-backed case studies**; careers (the job openings on `/contact/careers`) are **fully database-backed**. Services and projects share the same five category slugs: `production`, `websites`, `digital-marketing`, `social`, `branding`.

- **Services** — `src/constants/services.ts` is the single (very large) source of truth. `CATEGORIES` holds the five category-landing records; the per-category service-detail records live in `PRODUCTION_SERVICES` / `WEBSITE_SERVICES` / `MARKETING_SERVICES` (the `digital-marketing` category) / `SOCIAL_SERVICES` / `BRANDING_SERVICES`. `getServiceDetail(category, service)` resolves a detail page; `allServiceDetailParams()` feeds the `[service]` route's `generateStaticParams()`. Every record carries its own `seo` block (`title`/`description`/`canonicalPath`) consumed by `generateMetadata`. Section media comes from a registry at `src/components/Services/visuals/` via `getServiceVisual(category, slug)` → `ServiceVisualCard` (bespoke code/SVG art — distinct from the photographic category cover slots).
- **Projects** — split across two sources. `src/constants/projects.ts` is **chrome only**: `PROJECT_CATEGORIES` holds each category's hero/comingSoon/proof/FAQ/CTA/SEO copy, and its key order is the site-wide category ORDER. The case-study cards, clients, and detail media live in Postgres (`clients` / `projects` / `project_media`, managed via /admin) and are read through the cached accessors in `src/lib/projectsStore.ts` (`getCategoryProjects`, `getServiceProjects`, `getLatestAcrossCategories`, `getSummariesByCategory`, `getCategoryTallies`, `getProjectSummary`, …) — all `async`, `unstable_cache`-wrapped, and tag-invalidated (`updateTag` in the /admin actions), so content edits go live **without a redeploy**. Don't reintroduce project card data as module-scope constants — module scope evaluates before any async read can happen.
- **Careers** — `job_categories` + `job_openings` in Postgres (migration 0026), managed from `/admin/careers` (the `careers` area, in `DEFAULT_AREAS`), read through `src/lib/careersStore.ts` (`getCareersSnapshot`, `getOpenRoles`, `getRoleTitleMap`, `allListedRemote`, `latestCareersDate` — `unstable_cache` under `CAREERS_TAG`, `updateTag` in `_actions/careers.ts`). Three states: `open` (the "Available" card, a contact-form option, a JobPosting node), `filled` (kept on the page as "Position filled" — listings are never hidden when a seat closes), `draft` (admin-only). Delete is a hard delete; applications keep the `role_title` snapshot. **Two slugs are immutable after creation** — a listing's (it is the `?role=` deep-link payload and the value stored on applications) and a category's (the filter value) — the actions refuse a change rather than silently keeping the old one. **An `open` listing must carry a pay range and a posted date**, enforced by `careersSchema.ts` on both doors (the dialog and the roster's quick flip): BC's Pay Transparency Act requires expected pay on any publicly advertised posting a BC resident could fill, and Google's JobPosting requires `datePosted`; `validThrough` past its day drops the JSON-LD node (a stale-open posting is a policy violation) while the card stays. Advertised pay is a **public display range in whole CAD dollars** (`integer pay_min/pay_max`), not ledger money — `careerFields.formatPay` is its one formatter and it never touches `payrollAmounts.ts`. **The open roles are spelled into prose in exactly one place**: the composers in `src/lib/careerFields.ts` (`composeHiringIntro` → the hero paragraph, `composeHiringMeta` → the ≤160-character meta/OG description, `composeHiringFaq` / `composeRemoteFaq` → the two FAQ answers) — never hand-write a sentence that names or counts the open roles, it will be stale by the next hire. Categories carry an icon key from the fixed `JOB_CATEGORY_ICON_KEYS` vocabulary (`src/lib/jobCategoryIcons.ts` maps it to a lucide glyph); an unknown key renders the briefcase.

### Payroll

Monthly team pay, and the most privacy-sensitive surface in the app. Three compensation shapes coexist and **none is special-cased**: a payment stores an *anchor* currency+amount (what the agreement fixes) and a *paid* currency+amount (what landed), so everything collapses to `paid = anchor × rate` with `rate = 1` when they match — CAD-anchored paid in toman, toman-anchored paid in toman, and CAD paid in CAD are one row shape.

- **Money is integer minor units, never `numeric`/float** (the `estimatedMinutes` rule). CAD is `integer` cents; toman (`IRT`, the unit every invoice uses — rial appears nowhere) is `bigint({ mode: 'number' })`, because a member-year of toman overflows `int4` and `mode: 'bigint'` isn't JSON-serializable into an RSC prop. The rate is `bigint` `rate_micro` = toman-per-CAD × 1e6. **`src/lib/payrollAmounts.ts` is the single conversion door** — nothing else parses, formats, converts, prorates, or computes growth.
- **The rate belongs to a payment, not a month.** The exchange quotes each wire separately (June 2026 spanned 123,300.00–123,376.06 toman/CAD across four lines), so `payroll_runs.rate_micro` is the month's canonical figure — it pre-fills lines and drives the trend — and `payroll_payments.rate_micro` overrides it per wire. Two rounding granularities, both measured off the invoices: delivery rounds to 5,000 toman, proration to 10,000.
- **Computed amounts are suggestions.** `anchor × rate` pre-fills the cell; the admin overrides it to match the invoice exactly. The system records what happened, it doesn't dictate it.
- **The wire fee is company cost, outside anybody's salary** — never in a salary calculation, never shown to a member. The Donya invoice PDF is deliberately **never stored**: one page lists everyone's pay, so it can have no member-facing surface. Only its reference number is kept.
- **Standing salary is effective-dated** (`payroll_terms`, no `effective_to` — the next row supersedes, so gaps and overlaps are impossible). A month resolves to the newest term effective on or before its **last** day, then prorates by join/end dates: that is the only reading that reproduces Mahdi NP's July (35,000,000 × 13/31 → 14,680,000).
- **Status and amounts move through separate doors** (the tasks convention). No edit action accepts a status; no status action accepts an amount. Every transition is re-checked server-side by `checkTransition()` in `src/lib/payrollStatus.ts`, whatever the UI offered.
- **Two audiences, two projections — the split IS the privacy mechanism.** `src/db/payrollQueries.ts` exposes `admin*` (every column, every member) and `own*` (one member, scoped by a session-derived id matched in SQL, projected so `cost_cad_cents`, `fee_cad_cents`, `wire_ref`, `admin_note`, and member `notes` are never selected). A column that was never selected can't leak through a spread or an RSC payload. **Never widen an `own*` projection to reuse it for an admin screen, and never reach for an `admin*` query on a member path** — that includes the member row and the term history, not just payments: `ownGetMember` / `ownListTerms` exist so the admin's private notes about a person and the name of whoever set their salary are never *fetched* onto their own page, rather than merely left unread at the render site. Members also never see a `draft` line, and a toman-anchored member is never shown the rate (it played no part in their figure and would hand them the company's cost basis).
- **Access is three named gates** in `src/lib/adminAccess.ts`: `requirePayrollAdmin()` (the owner-granted `'payroll'` sensitive area — the named gate paid off: moving off "every superadmin" was one edit, not a sweep), `requireOwnPayroll()`, and `requirePayrollAccess(memberId)` for the shared payslip. The payroll-admin rule itself lives once, in `isPayrollAdmin(profile)` — `requirePayrollAccess` serves both audiences so it must *ask* rather than enforce, and re-deriving the answer inline there would quietly survive any future change to who counts as a payroll admin.
- **A line can't be sent until its cost is knowable.** `costInCadCents` returns null without a rate and every write path coerces that to `0` — so "cost unknown" would land in the one summable column as "cost nothing". `sendPayrollRun` therefore refuses any draft that still needs a rate, and a line needs one unless it is CAD-anchored *and* CAD-paid: the rate states the delivered amount when the currencies differ, and the company's CAD cost whenever the anchor isn't already CAD. A toman-anchored member (IRT→IRT) trips only the second half — miss it and `cost_cad_cents` freezes at 0 forever, since `repriceDrafts` only touches drafts. `getAccessProfile()` resolves `payrollMemberId`/`payrollSelf` via a `leftJoin` on its existing PK read (free on neon-http) — so **migration 0020 must be applied before this code deploys**, or every admin render breaks. Payroll is a grantable but **sensitive** area (`SENSITIVE_AREAS` in `src/lib/adminAreas.ts`): only the owner can flip its chip, it is never in the explicit `DEFAULT_AREAS`, and it contributes **no sidebar badge** (the layout computes tallies for everyone and masks after, which for payroll would mean counting other people's rows on a member's render).
- Whether a member sees their own pay is `payroll_members.self_view_enabled`, toggled from the roster — that's the switch to reach for, not an area grant. A member record's `user_id` is nullable + `ON DELETE SET NULL` with a `display_name` snapshot (the `tasks.assigneeId` precedent): pay history has to outlive an offboarded account.
- Emails (send notice, flag alert, nudge) carry **no figures**, by design. Audit rows go to `payroll_events` behind `after()`, like `logTaskEvents`.
- **`/admin/my-pay` is written for the member, not for payroll.** It is `wide` like every other dashboard route: hero (amount + status + confirm/flag) beside a 12-month column chart, three tiles (year, all time, salary now), then the growth split beside the salary step chart, the year-filtered month list, and *last* the working behind the figure. The mechanics are demoted, never removed — the standing ruling is that a member sees their whole own line, so the rate and the agreed figure stay on the page, just below the money. Labels are deliberately plain ("your agreed salary", "rate used this month"); "anchor" never appears on a member surface. Each month row links to that month's payslip, which re-derives the audience from the session, so the member id in the URL grants nothing.
- **The charts are hand-rolled and stay that way.** `PayrollCharts.tsx` (`PayColumns`, `SalarySteps`) are server components whose readouts are CSS `group-hover`, so they add nothing to the client bundle; `payrollData.ts` feeds them pre-formatted strings plus 0–100 percentages. There is no chart library in this repo and **none is wanted** — see the note atop `PayrollSections.tsx`. Column heights and the dashed average share one positioning context so they cannot drift off a common axis, and the salary step dots are positioned HTML over the SVG because `preserveAspectRatio="none"` would stretch `<circle>`s into ellipses. `/admin/payroll/[memberId]` renders the same two charts from the same builders, so an admin and a member discuss one picture. The printed payslip keeps `PayrollSections.tsx` — nothing in `PayrollCharts.tsx` is print-safe.

### Company costs

What the studio spends on itself apart from salaries, at `/admin/costs` behind the owner-granted `costs` area (migration 0030) — **labelled "Bills" in the rail and on the page** since `/admin/spend` took the general noun. Subscriptions are the first category; ads spend, hardware and one-off services drop in with no migration. Its roster moved into the merged commitments roster (see "Money" above); `/admin/costs/plans` redirects there.

- **Two tables, because the real invoices prove they differ.** `cost_plans` is the standing commitment (what a thing is *meant* to cost); `cost_entries` is what actually left the bank. The Claude bill forced the split: the plan says CA$299.60/mo, but **June 2026 was charged CA$295.81** after a mid-cycle upgrade that also moved the billing date from the 27th to the 23rd. Storing only a monthly rate would have reported June wrong for ever. Same relationship as `payroll_terms` to `payroll_payments`.
- **CAD cents only — deliberately NOT payroll's anchor/paid currency pair.** Every vendor bills this studio in CAD (the card statement is the source), so `amount_cad_cents` is the one summable column and there is no rate that can be unknown. A vendor quoting another currency records that quote in `billed_note` as free text, **never parsed and never summed**. **Costs own no money door**: `src/lib/payrollAmounts.ts` still parses, formats and caps every figure, called with `'CAD'`.
- **An entry has no status, on purpose.** An entry means money left. Anything unconfirmed would have to be excluded from the one summable column, which is exactly the trap payroll's `?? 0` coercion documents. Forecasting reads the PLANS instead: `monthlyRunRateCents` normalises a yearly or quarterly figure so mixed cadences add into one run-rate. That is a **forecast** — an annual charge still lands whole in the month it was billed, and a plan with no expected amount contributes nothing rather than a guess.
- **`name` / `vendor` / `category` are snapshots on the entry, and the reason is RENAMES, not deletion.** "Claude Pro" became "Claude Max" mid-2026 and June's charge must keep reading as what it was. Deleting a plan is refused while any charge references it (`cancelled` is the retirement path, the task-category rule); the `restrict` FK is the race backstop, not the everyday guard.
- **No unique on `(plan_id, month)`.** A general ledger has to hold two ad-spend rows in one month, and a vendor can genuinely bill twice. The dialog warns about a duplicate instead of the database refusing it.
- **The "expected but not recorded" list is the whole ergonomic**, and `/admin/spend` merges it with payroll's `missing` into one "Not filed yet". It mirrors payroll's `missing`/`seedCandidates`: for the selected month it lists active plans whose cadence lands there with no charge filed, each with a Record button that pre-fills the plan's figure. **The pre-fill is a suggestion, exactly as payroll's computed amounts are** — June pre-fills at 299.60 and gets typed over with 295.81. A quarterly or yearly plan is refused without a start date, because that is the anchor `planLandsInMonth` beats from; with none it would silently never appear.
- **Costs and payroll are separate grants, and the cross-readout respects that.** The costs month screen shows a salaries line only for a viewer who also holds `payroll`, and the payroll month screen shows a subscriptions line only for one who holds `costs` — and in both cases the read is **gated, not masked afterwards** (the overview page's rule: an ungated read is a wasted neon-http round trip *and* a figure fetched for someone not entitled to it). This is what lets cost visibility be handed to someone without exposing a single salary.
- **No CAD figure ever reaches `activity_log`, in the payload OR the summary.** The payload half is enforced — `REDACTED_KEY_RE` already refuses `amount`/`cents`/`invoice`/`note` — but **`summary` is not scrubbed**, so a cost summary names the vendor and never the amount. `/admin/logs` is a wider audience than the costs area, exactly as it is wider than payroll.
- `CostSections.tsx` takes **no `tone` prop**, which is what structurally prevents the company's cost base rendering onto a print sheet (the `InternalKpiPanel` rule). Bars are plain divs — there is no chart library in this repo and none is wanted.
- **Not in the ⌘K palette this round.** Unlike payroll — whose exclusion is permanent, because a search path would be a third projection routing around the own-vs-admin split — costs have exactly one audience, so adding it later routes around nothing.
- No cache tags: costs have no public reader, so mutations call `revalidatePath('/admin', 'layout')` only, and a client success path must never follow with `router.refresh()`.

### Money (spend, payroll, bills)

`/admin/spend` is the one view of the company's money, and it exists because payroll and costs were shipped as two islands when the intent was always to see them together. It is a **composition layer above both, not a third domain** — no tables, no migration, no new grant, and no writes of its own.

- **Payroll and costs are already the same machine twice**, which is what makes the composition cheap: `payroll_terms` : `cost_plans` is the standing commitment, `payroll_payments` : `cost_entries` is what actually left, and **both settle in CAD cents already** (`cost_cad_cents` and `amount_cad_cents` were each built as "the one summable column"). There is no conversion at the seam — only addition of cents already in a column. Do NOT merge the tables: payroll's statuses, proration and own-vs-admin projection split are real distinctions costs deliberately lacks, and collapsing them would destroy the privacy mechanism.
- **Two nouns, never summed together.** A **commitment** is a recurring obligation as monthly CAD (a member's current term, a plan's run-rate) — a FORECAST. An **outflow** is money that left in a month (a payment line, a charge) — a FACT. Every screen is a projection of those two lists, and mixing them is the one mistake here that nothing on screen would reveal.
- **`spendData.ts` composes; it never queries.** It reads only through the existing `admin*` doors in `payrollQueries.ts` and the readers in `costQueries.ts`, and issues **no SQL of its own against the payroll tables** — a third projection opened here would route around the own-vs-admin split exactly the way a search path would, which is also why payroll stays out of ⌘K. The one reader payroll genuinely lacked (`latestRunRate`) was added *to payrollQueries.ts*, not here.
- **The overview needs BOTH grants; the roster adapts.** `requireSpendOverview()` gates `/admin/spend` on `payroll` **and** `costs`, and that is a correctness rule before a privacy one: it is the only screen claiming to show the whole, so a viewer holding one half would read a partial total under a complete label — a misleading figure is worse than a missing one. `requireCommitments()` opens the roster for **either** grant, reads only the half held (absent from the payload, not masked in CSS), and `commitmentsTitle` renames the page to match ("Recurring costs" / "Payroll members" / "Commitments"). The two grants stay separate precisely so cost visibility can be handed out without exposing a salary. **`spend` is therefore NOT an area and must not become one** — a Spend grant held without `payroll` is exactly the partial-total failure the gate exists to prevent. `/admin/users` states the derivation instead: a dashed, non-interactive "Spend" chip after the sensitive hairline that lights only when Payroll and Bills are both ticked, reading the optimistic local state so it flips in the same frame the chip does. It never enters the saved payload.
- **A figure that cannot be known is OMITTED and COUNTED, never zeroed.** `foldRunRate` is the one place that decision lives, and `cadOrDash` the one place the em dash is chosen. A toman-anchored salary with no rate anywhere, and a usage-billed plan with no expected amount, are both excluded from the run-rate with the gap declared on screen ("6 priced, 1 without a figure"). `costInCadCents` already returns null rather than zero, so the behaviour is inherited rather than reimplemented. Pinned by `scripts/check-spend.mts`.
- **A forecast must never read as a fact.** A toman-anchored salary is expressed in CAD at the newest recorded `payroll_runs.rate_micro`, and the page always says which month's rate it used. `latestRunRate()` returning null is a stated absence, not a zero.
- **The merged roster merges the LIST and nothing else.** `CommitmentsRoster.tsx` mounts `MemberDialog` / `TermDialog` / `PlanDialog` unchanged, so every write keeps its own action, validation and audit row; the component knows how to lay out two kinds of row and must never learn how to save either. The sort — biggest monthly CAD first, unknowns last — is the whole reason the two lists merged: a person and a subscription only compare once they share a column.
- **The draft asymmetry is stated on screen, deliberately.** Payroll excludes drafts from spend (`countsAsSpend`) while a cost entry has no status at all, so without the "N payroll drafts not counted yet" reading the People figure would not reconcile with `/admin/payroll` and would read as a bug.
- **Wire fees get their own outflow bucket**, never folded into the people figure — a fee is company cost outside anybody's salary, and adding it in would produce a salary total no payslip agrees with.
- **"Where it went" names the money, and the lines must RECONCILE with the bucket above them.** The People list comes from `adminListMonthPayments` filtered by `countsAsSpend` — the People tile is built from `adminMonthRollups`, which already excludes draft and void, so an unfiltered list would not add up to the figure directly above it. It is sorted biggest-first in JS because that reader returns ROSTER order (right for the payroll table, wrong for a ranking, and wrong for a cap that must fold the smallest rows). The Bills list is per ENTRY, never grouped per plan: there is deliberately no unique on `(plan_id, month)`, so grouping would merge two real charges into one row matching nothing on `/admin/costs`. The wire fee is never folded under a person's name. Neither list may appear on `/admin/spend/commitments`, which a bills-only viewer can open.
- **A capped list states its remainder, with the amount.** `SPEND_LINE_CAP` exists so a growing roster cannot run the section off the page, and `foldLineCap` exists so the cut can never pass for the whole: the remainder line carries the hidden rows' total, which means the visible rows plus that line still equal the bucket. Never cap without saying so — the house no-silent-truncation rule, and on a money screen it is an arithmetic error rather than a display one.
- **The variance compares the RECURRING halves only.** `spendVariance(peopleCents + toolsCents, foldRunRate(raws).cents)` — wire fees are not a commitment and one-offs are not recurring, so folding either in reports a month as over-budget for money the run-rate never claimed to cover. It renders as a sentence rather than a tile, because a tile invites reading a forecast-vs-fact difference as another total.
- **The trend trims its oldest empty months, never an interior one.** Cost tracking began part-way through the studio's life, so a fixed twelve spent half the section drawing dashes. `trimTrailingEmpty` drops only the trailing run and honours a floor of three, and the section's aside names the month it reaches back to. A zero month INSIDE the range is a real fact about that month and stays.
- **Every bar in the dashboard is INK, and Spend was the exception.** The admin theme carries no chroma (`--primary` is a zero-chroma oklch), and `/admin/costs`, `/admin/reports` and the leaderboard all draw the same thing: an `bg-foreground/[0.08]` track under a `bg-foreground` fill, quietened with opacity where something is secondary (`fill` / `baseFill` in `ReportSections.tsx`). Spend's four buckets are one ink ramp ordered darkest-to-lightest, and the leaderboard's gold moved OFF the bars onto the crown, the numeral and the champion wash — gold identifies who won, ink measures how much. Don't reintroduce a hue for a quantity; the opacity ramp survives dark mode and a colour-blind reader without a second palette.
- `SpendSections.tsx` takes **no `tone` prop**, which structurally prevents the company's whole cost base rendering onto a print sheet (the `InternalKpiPanel` / `CostSections` rule). Bars are plain divs — there is no chart library in this repo and none is wanted.
- **The Overview's Money card is the same total, folded through the same function.** `/admin` renders it only for a viewer holding BOTH grants — `requireSpendOverview()`'s rule applied to a module, and the Overview gates by omission rather than redirect. It composes two EXISTING admin doors the page already batches (`adminMonthRollups` + `costMonthRollups`, two round trips) and opens no query of its own, so it is not a third projection around the own-vs-admin split. The addition itself is **`foldOutflow` in `spendFields.ts`**, which `buildSpendMonthView` also folds through — the two screens are therefore structurally incapable of quoting different figures for one month. The card reads the cost ledger UNSPLIT (`oneoffCents: null`), which `billsSplit` declares so no caller can draw a "Recurring costs" bar over a figure that also holds one-offs; it labels that bucket **"Bills"**, the rail's own word. It states the draft asymmetry, gives the wire fee its own segment, draws the dashed honest gap at zero, and takes **no `tone` prop**.
- **The bucket ink ramp lives in `spendFields.ts`** (`OUTFLOW_BUCKET_FILLS`), not beside the bars: two surfaces draw this split now, and a private copy on each is how two screens end up disagreeing about which shade means "salaries".
- **Not in the ⌘K palette, and not to be added.** The section is a view over payroll; a search path into it is a search path into payroll.
- No new audit surface: the section writes nothing to `activity_log`, because it performs no writes. No cache tags — mutations still go through the payroll and costs actions, which revalidate as they always did.

### Tasks

The team's shared work log — it replaced the Telegram daily-digest thread — and the source every report and the leaderboard reads from. Built across migrations 0010–0019 (`tasks`, `task_categories`, `task_events`, `task_templates`, `task_views`, plus `clients.retainer_minutes`).

- **One URL, three views, and `?view=` is a MODE rather than a boolean.** `/admin/tasks` is the board; `?view=calendar` is a month grid; `?view=digest` is a read-only last-7-days roll-up. The page component is a thin shell that branches on the param (the `/admin/inquiries` model) — don't promote any of them to its own route. `TaskViewMode` in `taskFilters.ts` replaced a `digest: boolean` threaded through eight call sites, which was never really about the digest: it stood in for three unrelated decisions (what month a bare URL means, whether a backward date field may serialize, whether `page` may), and a third view had no way to answer them independently. `resolveTaskViewMode` is the one place an unknown `?view=` falls back, and the list is the one mode that writes no `view=` at all.
- **The calendar is a third RENDERING of the same filtered query, not a third domain**: no migration, no new grant, no action of its own, no second definition of anything. Its date field is the existing `dfield` facet, so `date` (due-or-start) draws a planning calendar and `completed` turns the same grid into a record of what shipped. Read-only: a chip is a server-rendered `<Link prefetch={false}>` to `?task=`, and `CalendarDialogHost` — the page's ONE client leaf — turns the arrival into the existing `TaskDialog`, cloning `TaskBoard`'s consume-and-strip (open once per arriving id, guarded by a ref that resets, then `router.replace` so a revalidation cannot reopen a dialog somebody just closed). `prefetch={false}` is load-bearing, not tidy: Next prefetches every in-viewport Link, so a month grid would fire ~150 RSC requests on arrival. **Chips are POINTS, never spans** — 8 of 693 rows on the real board have a due date later than their start, the longest by 7 days, so bars would be a layout engine for 1% of rows and are inexpressible for `completed`, which has one endpoint.
- **On the calendar, `?month=` picks WHICH MONTH THE GRID DRAWS, and that window REPLACES the list's month scope rather than joining it** (`calendarDateWindow`, applied through the existing `applyTaskDateWindow`; `tasksWhere` itself is unchanged). The scope could not be used: it is one OR'd clause — completed inside the month, OR still open — so it admits an open task due in October that August's grid has no cell for. The digest set the precedent when its picked month replaced the rolling week. The consequence is wanted rather than tolerated: **a past month on the calendar shows work that was due in it and never shipped, which the list deliberately hides.** `taskTabsFor`/`coerceTaskView` are month-scope artifacts and do NOT apply there; `calendarTabsFor(field)` is the equivalent, dropping the four working tabs when the field is `completed` because an open task has no completion instant to place it on a day, with `coerceTaskViewIn` as the shared fallback line so the two rules cannot drift. `?month=all` is coerced to the current month and the band passes `allowAll={false}` — a grid draws ONE month. `countTasksByStatus` grew one option for the same reason: its completion-window strip is right when that window is a facet over a scope and wrong when the window IS the grid.
- **A day cell states a true count and shows a ranked sample.** Several days on the real board carry 30 to 49 tasks (one carries 124 by created date) and a 300px cell fits about five chips, so a grid that showed only chips would be quietly wrong about most of the month. The header carries the day's real count and hours, `rankCellTasks` puts overdue then due-today then priority first, and "+N more" links to the list filtered to that one day — **unscoped on purpose**, because carrying the month across would re-apply the list's completed-in-month clause and an open July task would vanish from the very page its own cell sent the reader to. `foldCellChips` guarantees visible + remainder equals the header (the house no-silent-truncation rule), and shows a single over-cap row rather than spending a whole line to announce it.
- **The calendar has TWO renderings and the switch is CSS alone**, the board's own rule: `CalendarGrid` is `hidden md:block`, `CalendarAgenda` is `md:hidden`, both server-rendered from the SAME folded cells so they cannot disagree about what a day holds. No `useMediaQuery` — it initialises `false` and flips in an effect, which SSRs a seven-column grid onto a 360px phone and then snaps. The agenda skips empty days (a week has to keep its shape; a list does not) and uses the same per-day cap. `src/lib/taskCalendar.ts` is the guard-free pure leaf holding every fold, and `monthGridKeys`/`weekdayOfDayKey` live in `calendar.ts` as pure key math with **no zone parameter, ever** (Monday-first, derived from the digest's Mon–Sun week). The shared `loading.tsx` gets no `searchParams`, so it cannot tell the three views apart on the server: `TasksSkeletonSwitch` (its one client leaf) reads `?view=` and picks between `TasksListSkeleton` / `TasksCalendarSkeleton` / `TasksDigestSkeleton`, which are handed to it as server-rendered props so `AdminSkeletons.tsx` stays a Server Component. Its `views` prop is keyed by `TaskViewMode`, so a fourth `?view=` is a type error at the call site rather than a silently missing skeleton.
- **Tags are an optional second label, scoped per category** (migration 0027: `task_tags` + `task_tag_categories` + `task_tag_links`). They replaced a dimension the studio had been writing into task TITLES ("… TH", "… Reels", "Vela 21st Street Vt", "Belcanto OP 1 (Eslahie)"). Five rules hold it together. **A tag belongs to exactly one TYPE, and types are rows** (`task_tag_types`, migrations 0028/0029 — they replaced the `task_tag_group` enum on 2026-08-24, reversing that enum's own "adding a fourth should cost a migration" argument: the people naming the work are the ones who know what axis is missing). A type carries a name, a one-line hint, and a `tone`; it drives BOTH the picker's sections and the chip colour, so colour still belongs to the axis and never to a tag — the board can't drift into confetti. `tone` is a KEY into the fixed 8-colour palette in `taskTagFields.ts`, never a stored colour value (the Tailwind scanner can't see a computed class name, and a hex has no dark-mode answer); unknown keys resolve to `slate` rather than throwing, and the palette deliberately excludes `rose` (overdue) and `amber` (due today / over estimate). The chip is **borderless by design** — a soft tint with same-hue text — because a rim reads as a box-in-a-box wherever a chip sits inside a picker row or a toggle. Types follow the tags' own retirement contract: slug immutable, `deleteTaskTagType` refuses with a count while any tag references it (the `restrict` FK on `task_tags.type_id` is the race backstop), and neither archive nor delete may take the LAST live type. **Archiving a type retires every tag under it**, which is why `TaskTagOption` carries `typeArchived` — `splitTagsForCategory` reads it, and `setCategoryTagOffers` must include those tags in `frozen` alongside the archived ones, or saving any category would try to drop scope rows for tags the pane never rendered. **Scope gates the picker, never the stored value**: `taskTagCategories` says which categories OFFER a tag (zero rows = global, which is how the workflow tags reach everywhere), but `setTaskTags` accepts an out-of-scope tag rather than rejecting it — a task's category can change after tagging, and enforcement would silently drop a member's labels; out-of-scope tags surface in the picker's trailing "Other" section. **Slugs are immutable and archive is the retirement path**, exactly as for categories: filter URLs and saved views carry the slug, `deleteTaskTag` refuses with a count while any task carries it, and the `restrict` FK on `task_tag_links.tag_id` is the race backstop. **Tags move through their own door** — `setTaskTags` / `setTasksTagsBulk` (add/remove, NEVER replace: one "set tags" across a mixed selection would wipe what each row already carried), plus optional `tagIds` on create/update; `patchTask` and `bulkPatchTasks` are structurally unable to touch them, the same rule status follows. Vocabulary CRUD and assignment are both `requireArea('tasks')` — the people doing the tagging are the ones who know what label is missing, and the vocabulary is guarded by its domain rules (delete refuses with a count, archive is the retirement path, slugs are immutable) rather than by a role. **The manage dialog is CATEGORY-first**: a category is a pane, its tags are a checklist, and the pane saves ONCE through `setCategoryTagOffers` — which writes a delta over one `category_id` and therefore must never reach for `writeTagScope` (that replaces a whole tag's scope and would wipe every other category's rows). Two toggles are refused there and on the server, both because empty scope means *everywhere* so "offered nowhere" is inexpressible: a global tag can't be ticked into one category, and a tag can't be dropped from its LAST category. Two tag-major panes survive: "All tags" (rename/retype/rescope/archive/delete) and "Tag types" (the axes themselves). Its Save lives in `GlassDialog`'s **footer slot**, which is why the category draft is held by `TagManageDialog` rather than by `CategoryPane` — the old sticky gradient bar floated a pale band across the pane and is gone. **Reads never N+1**: `tagsForTasks` in `taskQueries.ts` fetches a whole page's tags in ONE query and `withTags` folds them in JS. The filter facet is `?tag=a,b` (+ `?tagmode=all`, + the exclusive `tag=none` untagged sentinel) and rides **EXISTS subqueries, never a join**, so `count(*) over ()` and the join-free tab-badge COUNT keep working. **The Tags column is width-capped and that cap is structural, not styling**: `TASK_TAG_STRIP_MAX` on `TaskTagStrip` is what stops a heavily tagged task widening the board, because the table is auto-layout and a cell's min-content contribution is clamped by its content's own max-width — six visible chips used to add ~400px no other column could give back. Two chips show, the rest fold into a `+N` whose hover panel MUST be portalled (`TaskTagOverflow.tsx`, its own client leaf so `TaskTagChip.tsx` stays server-safe for the internal report) — the table lives inside `overflow-x-auto`, which clips anything positioned within it.
- **Tags are internal, and that is structural rather than a convention.** `TaskListRow` carries no tags; `TaskListRowWithTags` does, and `listClientMonthTasks` — the reader behind the client month report, its print sheet and the `/share` link — returns the base type, so tags *cannot* reach a client surface. Likewise `TagMixStrip` (the "What shipped" readout on the digest and `/admin/reports/internal`) takes no `tone` prop, so like `InternalKpiPanel` it has no print variant to render into. The `tags` CSV column lives in `tasksColumns` only, never `SHARED_COLUMNS`, which the report export also consumes. Whether a client-facing deliverable mix is wanted is its own decision, deferred on purpose (2026-08-24) — it needs its own copy pass, and workflow tags like "Revision" would have to be excluded.
- **Every duration in the database is an integer number of minutes, and `src/lib/taskFields.ts` is the only module that may do the x60 math.** `parseHoursToMinutes` / `formatMinutes` / `composeMinutes` / `splitMinutes` live there and the rule extends to CSV exports. Display is always `2h 50m`, never `2.83 h`; the CSVs additionally carry decimal-hours columns so spreadsheets can sum them. `WORKDAY_MINUTES = 480` — a month's delivery divided by 24 would quietly understate itself on a client-facing PDF.
- **Status and edits move through separate doors** (the same rule payroll cites). `setTaskStatus` is the one status door and `setTasksStatusBulk` the one bulk status door; `patchTask` and `bulkPatchTasks` are **structurally unable** to touch `status`/`completedAt` because their schemas have no such keys. Keep it that way — it is what stops the `completedAt` contract being bypassed from an inline cell edit. The **completion day** rides the same door: `TaskCellPatch` has no key for it, and the Done tab's date cell (`CompletedCellPopover`) calls `setTaskStatus`, not `patchTask` — it is an amendment of the status, not a column edit.
- **A status is either OPEN or SHIPPED, and `SHIPPED_STATUSES` in `taskFields.ts` is the one door for that.** `done` used to mean two things at once — the member finished the work, and it counts for the client — so migration 0042 split them into `done` → `delivered` → `posted` (the ladder's order is load-bearing: `nextStage` walks it and `TaskStatusBadge` paints it as an ink ramp). **All three count as delivered work, identically**; the tabs sit between Done and All, and `OPEN_STATUSES` is the complement, so the two partition the vocabulary and nothing can belong to neither (pinned by `scripts/check-task-stages.mts`). Every report reader filters `inArray(status, SHIPPED_STATUSES)`, never `eq(status, 'done')` — that includes the two raw-SQL correlated subqueries in `taskQueries.ts`, which build their `IN` list from the constant rather than typing it. Deadline pressure is the complement: the Overdue facet is `notInArray(status, SHIPPED_STATUSES)`, while the sidebar badge, `listOpenDueByAssignee` and `listClientOpenSnapshot` enumerate the OPEN set and are unaffected.
- **The `completedAt` contract is a reporting contract.** `completionStampMode` (a pure leaf in `taskFields.ts`) owns it in one place: →done **stamps** (`now`, or the day the member picked when the change carries `completedOn`), →delivered / →posted **preserve** — ``sql`coalesce(${tasks.completedAt}, ${now})` ``, a coalesce and not a read-then-write because neon-http has no transactions — and any open status **clears**. Preserving is the whole reason a task can advance without moving between monthly reports; the coalesce's fallback still stamps a task logged straight to Posted, which never passed through done. An explicit `completedOn` overrides on all three, which is what lets work be logged after the fact — so the day field is offered exactly when a save would stamp one (`offerCompletedDay`), never on a task that already shipped, where a stale value would overwrite a date the server was told to keep. **There is still no month lock and that is still a deliberate call**, but a reopen-and-recomplete no longer has to lose the original day: re-issuing `{status:'done', completedOn}` on an already-done row IS the amendment, which is why `setTaskStatus` has no `status <> target` guard and `setTasksStatusBulk` does. Leaving the shipped set nulls `completedAt` but keeps `actualMinutes` — inert (reports only read shipped rows) and the best prefill for the next completion. `needs_approval` means the work is finished and awaiting client sign-off: `actualMinutes` is confirmed but `completedAt` is still null, so **a task enters a report only once it reaches `done`, and stays in it through `delivered` and `posted`.** Hours on completion coalesce `provided ?? actual ?? estimate`. `setTasksStatusBulk` adds `status <> target` to its WHERE so a mixed-selection "mark done" can never restamp an already-done task into a new month — and it takes **no date**, because one completion day asserted across a mixed selection is the same silent overwrite the bulk tag door refuses.
- **A backdated completion is a calendar DAY stored in an INSTANT column, and it anchors at MIDDAY in the actor's zone** (`dayNoonIn`), never at day start: day start puts a Tehran member's Aug 1 at `2026-07-31T20:30Z`, which every Vancouver reader — and every month window the reports and the leaderboard are built on — reads as July. Midday leaves ~12h of slack each way, which covers the studio's 11.5h Vancouver↔Tehran winter spread with **30 minutes to spare** (Iran has had no DST since 2022); a teammate further east than about +4 would break it, and the fix then is a `date` column, not a bigger offset. Picking **today keeps `now`**, so same-day completions retain their real instant and the Done tab's `completed_at DESC` order still reads newest-first within a day — which also lets every caller send the field unconditionally. **Future days are refused in the action, not the schema** (a schema may not name a zone), and there is **no lower bound** on purpose: work is routinely logged days after it happened. The cost is real and accepted — an amendment moves a task between monthly reports, and `/share/reports/[token]` recomputes live, so an already-delivered PDF's numbers change. Every picker therefore shows a non-blocking "Counts toward August 2026" note (`otherMonthNote`) rather than refusing. Four surfaces offer it: the complete-task confirm, the Done tab's date cell, the task dialog when the status is done, and the quick-add band's Done chip — whose day is **prefilled from the START date only when there is no due date**, because a due date is a commitment and filing a late delivery under it would quietly mark it on time.
- **Recurrence is idempotent through the database, never through a read-then-write check** (neon-http has no transactions). `recurring-tasks` mints one task per active template whose schedule lands on today's `STUDIO_TZ` date, keyed `(template_id, template_run_key)` under a partial unique index with `onConflictDoNothing`. That index's `where: isNotNull(tasks.templateId)` predicate is **mandatory and must stay byte-identical to the index** — without it Postgres raises 42P10 and the whole mint throws instead of skipping the duplicate. A monthly template's `repeat_day` is capped **1–28** so no month silently skips February.
- **Whole-team visibility is the design.** Anyone holding the `tasks` grant may edit any task; there are no ownership checks and `taskQueries.ts` never scopes by viewer — this is a trusted seven-person studio. The single exception is comment deletion (own comments only, unless superadmin), and that check **rides the WHERE clause** rather than a read-then-check, so it can't race.
- **Category vocabulary is archived, never deleted**, and **slugs are immutable after creation** — filter URLs and report history carry them. `deleteTaskCategory` refuses while any task *or* template still references it (it counts both and says which); the `restrict` FK is the race backstop.
- **No cache tags.** Tasks have no public reader, so mutations only call `invalidateTasks()` (`revalidatePath('/admin', 'layout')`). The one exception is `quickCreateClient`, which also fires `updateTag(CLIENTS_TAG)` because it writes a `clients` row. The fresh tree rides back on the action's own POST response, so **a client success path must never follow up with `router.refresh()`** — that is roughly ten extra Neon round trips for a render you already have.
- **Deletion policy assumes people leave.** Every FK-to-user is `SET NULL` beside a NOT NULL name snapshot (`assignee_name`, `created_by_name`, `actor_name`, `task_title`) so offboarding an account never breaks last month's report; `tasks.client_id` is `restrict` (billable history must be untangled on purpose); and `task_events.task_id` is **`SET NULL`, not cascade** — a hard delete is the one irreversible act here, so its history has to outlive it, which is why `kind='deleted'` rows are born orphaned.
- **The column headings sort and filter, and both halves are doors onto controls that already existed.** Members read the eleven labels above the table as buttons and clicked them, so each one now opens its column's orders plus that column's own filter. The filter half mounts the **same component the Filters bar mounts** (`FilterSelect` / `TagFilter` in `Admin/tasks/FacetMenus.tsx`, `ClientCombobox`, `TaskDateFilter`), handed a `trigger` and a `leading` block, so the bar and the header cannot answer differently; `useTaskNavigate` is the one function that writes a board URL, Clear included (it passes `replaceAll`, being the one change expressed by what it drops). Two rules decide what a column offers, both in `src/lib/taskColumns.ts` and both pinned: **a column offers a sort only when a task has exactly one value in it** — Tags and Member are many-per-task, so ordering by "the first one alphabetically" would file a shoot two people went on under whichever name sorts first, and keeping every sort one-per-row is also what keeps a correlated subquery out of the ORDER BY — and **a token belongs to exactly one column**, with `newest`/`oldest` the deliberate exception (they read `created_at`, or `completed_at` on a shipped tab, and neither is a column on screen). Sorting rides the **existing `sort` param, widened to 16 named tokens, never a `sort`+`dir` pair**: `TaskListParams` gains no field, the canonical param order never moves, and every string already in `task_views.query` still serializes byte-identically. `due` and `priority` are reused as the canonical spelling of "soonest" and "high first" rather than respelled, so one order can never become two saved views. `taskOrder` lives in the guard-free `src/db/taskPredicates.ts` for `tasksWhere`'s reason, and **every branch ends on `desc(tasks.id)`** or OFFSET paging shows a row on two pages or on none. Note `nulls last` is redundant on the ASC arms (Postgres's default) and load-bearing on the DESC one, where the default is NULLS FIRST. **The bar carries TWO escapes, not one, and they stay separate**: "Clear filters" (shown while anything narrows) and "Clear sort" (shown while the order is not the default). Narrowing to one client and ordering by deadline are different choices, so clearing one must not throw away the other, and one adaptive label cannot say which it will do. Both sit at the END of the row, carry the `var(--destructive)` fill ConfirmDialog gives Delete (Saman's call, made twice: this is the one control in an otherwise ink-only dashboard that spends colour on something that is neither a deadline nor a deletion), and live outside the chip group: that group is the "Filters" fold on a phone, and burying the way out inside the thing you are undoing is what made Clear unfindable (`q` counts for `hasActiveTaskFilters` but deliberately NOT for `countActiveTaskFilters`, so a search-narrowed board showed an uncounted pill, an unopened fold, and no way back). "Mine" is still the first FILTER; neither escape is one. `SortClearRow` is the same control inside the Sort chip and inside the sorting column's own heading, so one action never gets two names.
- `src/lib/taskFilters.ts` is a zero-dependency URL contract: canonical param order, defaults dropped from the URL, and one date facet (`dfield` over date/due/start/completed/created x `drange` presets or a literal `YYYY-MM`) driving menu, trigger label, and window resolver from a single predicate. `group` is a display preference, never a filter, and survives "Clear filters". This module never picks a timezone of its own.
- **The date facet's working-tab default is the composite `date` field — `COALESCE(due_date, start_date)` — not `due`.** Quick-add's default task shape is start-only (start=today, no due), so a due-only default made the board's most common task invisible to every date preset: "Today" hid a task whose Dates column visibly read today (the 2026-08-21 fix). The composite is **point semantics, not range-overlap** (an ongoing "Aug 10 →" task does not appear under "Today" — Saman rejected the flood), and **Overdue stays strictly due-based everywhere** (a start-only task is ongoing, never overdue; the preset is refused on the Start field, where it would have meant "started before today"). The chip prefixes any non-default field ("Start · Today") so it never hides which column it windows. `tasksWhere` lives in the guard-free `src/db/taskPredicates.ts` (schema.ts precedent, never client-imported) precisely so `scripts/check-task-filters.mts --db` can prove the real WHERE against seeded fixtures.
- **Search is TOKENIZED — an AND of ORs — and reaches every field the row DISPLAYS, with every off-table source riding an EXISTS.** `src/lib/searchTerms.ts` is the one tokenizer (a zero-dependency client-safe leaf, pinned by `scripts/check-search-terms.mts`) and `searchAllTokens` in `taskPredicates.ts` the one predicate builder, re-exported through `adminQueries.ts` so all **eight** SQL search surfaces compose the same shape; `matchesAllTokens` is its browser twin for the four rosters that filter in the page. Each token gets its own OR over the surface's fields and the tokens are ANDed, so a token may match a DIFFERENT field from its neighbour. That is the whole fix: wrapping the whole query in one `%…%` meant `"arshia real th"` could not find "Arshia Real Estate TH" — a contiguous substring cannot skip the word in between — and a member's name plus a title word could never match at all. Neither is a typo. `q` spans title, notes, `assignee_name` (the on-table snapshot — free), the client's name, the category's name and any tag's name, plus the `'Perseus'` literal the Client column renders for a null client (there is no row to match it against, so the label is a literal in the predicate). The three joined sources are **correlated EXISTS subqueries, never joins** — the tag facet's reason exactly: `countTasksByStatus` selects from `tasks` alone and `listTasks` rides `count(*) over ()`, so a join would multiply rows and break both. Deliberately excluded: `created_by_name` and `deliverable_url` — a URL hit is invisible in the list and reads as a false positive. Because `tasksWhere` is the one door, the CSV export and the tab badges inherit the same reach for free.
- **"Did you mean" is a SECOND tier, and it only ever runs on a miss.** `src/db/searchVocabulary.ts` fetches a surface's words only once the exact search has already returned nothing, so a working search pays no extra round trip; the correction is then re-run through the **same exact predicate**, which is what makes the results explainable rather than a similarity neighbourhood. It is a vocabulary pass in JS and not `pg_trgm` (verified available on this Neon instance, deliberately not installed) for two reasons: what the reader is owed is a corrected TERM they can see and click, which a row-scoring threshold cannot produce; and at 245 tasks / 96 clients a seq scan is free, so an extension would buy nothing but an ops surface. **Each vocabulary entry is one ROW's text, never a flat word list** — `suggestQuery` scores a candidate by how many rows match the WHOLE corrected query, which is the only thing that can separate two words at the same edit distance, and it also guarantees a suggestion returns rows. The palette's vocabulary spans **only the entities the viewer may see**, because a correction assembled from rows they cannot open would both bounce them and leak that a client or teammate exists. `?nocorrect=1` is the one-shot escape hatch the "Search instead for…" link carries and is deliberately NOT part of any filters URL contract — it is not a filter, so it never enters a saved view.
- Server-formatted strings are the only date values that reach the client — `toRowData` stamps `dueState` server-side so the board never does date math in the browser.
- **A task is worked by ONE OR MORE members, and `task_assignees` is where that lives** (migrations 0034–0036). `tasks.assignee_id` / `assignee_name` are gone: a shoot two people go on was trackable only as one name, so the second person was invisible on the board, the leaderboard, the digest, the client report and the due reminder. The counting contract is the exact **mirror of the revision rule below — there counts split and minutes never do; here counts don't split and minutes do**: a 3h shoot is 3h studio-wide however many people went, apportioned evenly across its members for every per-member fold, while each member is credited the whole delivery and the STUDIO still counts the task once. **`splitMinutesAcross` in `taskFields.ts` is the one door for that division** and it is largest-remainder, not `minutes / n` — every duration here is an integer, so 185 across two is `[93, 92]`; rounding each part independently gives 186 and the per-member bars stop summing to the tile above them, which on a client sheet is an arithmetic error rather than a display one. **A studio figure must never be a sum of member tallies** — `assembleBoard` counts slices, because summing the tallies would inflate the headline the moment anyone added a second name; the gap is stated on screen as "N of them shared", the revisions precedent. **A task always keeps at least one member** (`taskAssigneeIdsSchema.min(1)`, plus a correlated-count guard riding the bulk DELETE's own WHERE so it cannot race), so no fold grows an "Unassigned" bucket. **`tasksWhere` stays tasks-columns-only**: `?assignee=` is still ONE scalar id meaning "is on this task" and rides a correlated EXISTS, never a join — `listTasks` uses `count(*) over ()` and `countTasksByStatus` selects from `tasks` alone, so a join would corrupt both; the q-search reach over member names moved to an EXISTS for the same reason, losing its free on-table ilike. The URL contract is therefore **unchanged**, which is what keeps saved `task_views`, the overview deep links and the cron/email links valid. Reads never N+1: `assigneesForTasks` fans a page in by id (the `tagsForTasks` shape) and `assigneesForDoneWindow` fans the leaderboard in **by the window instead**, because 4000 uuids in an `in (...)` is a six-figure-byte statement. **Assignees move through their own door** — `setTaskAssignees` / `setTasksAssigneesBulk` (add/remove, never replace, the tag rule) plus `assigneeIds` on create/update; `patchTask` and `bulkPatchTasks` have no such key. Deletion policy is the old column's, unchanged: `user_id` is `set null` beside a NOT NULL `member_name` snapshot, which is why the join table carries a surrogate PK and a **partial** unique index (a nullable column cannot be part of a PK, and two offboarded members on one task are two legitimate rows) — any `onConflict` against it must repeat that `where` predicate verbatim or Postgres raises 42P10. Category champions gained a **tie guard** at the same time: `CATEGORY_MIN_MEMBERS` silently stopped gating once people routinely paired, so a dead heat now crowns nobody, compared on deliverables only because a minute difference between two members of a shared job is usually just an apportionment remainder. Pinned by `scripts/check-task-assignees.mts`.
- **A revision is a LINKED row, and `parent_task_id IS NULL` is the definition of a deliverable everywhere** (migration 0031). The studio had been recording revision rounds as standalone tasks with the round written into the title (`… (Eslahie)`, `… V2`), which inflated every count: 17 of 201 August rows were revisions, so a client who received one video read "3 tasks delivered". A revision stays its own row on purpose — its own hours, its own completion day, its own member — because **a September fix on an August delivery must bill to September**, which is what rules out folding the time into the original. What the link changes is COUNTING: **counts split, minutes never do.** A revision's hours are real work and stay in every total, per-category and per-member figure; only the counts hold them apart, stated on screen as "N revisions" beside the number rather than hidden. The single fold predicate is `isDeliverable` in `reportData.ts` and `slice.parentId === null` in `leaderboardData.ts`/`foldMonthTotals`. Turnaround, on-time and estimate-drift read deliverables only. **Rounds NEST, and the flattening is gone (2026-08-27).** `resolveRevisionParent` used to re-point a revision-of-a-revision at the root, so a third round read "Revision of" the FIRST version — which is not what it revises, and told a member correcting round two that they had corrected round one. Removing it is safe for the arithmetic and that is the part worth understanding, because it is the part that looks risky: every fold is a **binary** `parentId === null` test, so a v3 whose parent is v2 is still not-null and still not a deliverable, **at any depth**. What nesting does cost is four things that all had to move with it, none of which is a count: the round tally became a **recursive CTE** (`revisionMetaFor`) so a deliverable reads its whole chain rather than one hop; the board row and the phone card render **both** the "Revision of …" line and their own tally, where an exclusive ternary used to drop a middle round's; the digest's fold walks up to the chain root instead of hopping once (a single hop was order-dependent and could render a grandchild at the wrong level or lose it); and `updateTask`'s cycle guard grew from `reparent === id` to a real walk (`revisionLinkProblem`), because A→B→A only became expressible once flattening came off — and every row in a loop silently stops being a deliverable. `REVISION_DEPTH_MAX` (8, in the leaf `taskFields.ts` because a `'use server'` module may export only async functions) bounds both walks. **Deleting detaches only the DIRECT rounds** — the FK is `set null`, so a grandchild keeps pointing at its own parent — which is why the confirm quotes `directRevisionCount` and not the chain total, and says so rather than letting it be discovered later.
- **Logging a revision closes the round it replaces, and applies the Revision tag.** Both are conveniences with one hard rule each. The **auto-complete** is a default-ON checkbox in the revision form (and on the quick-add band), never silent, because marking done files that task into a client report and the leaderboard — so it names the month and the hours it will file at. It is **never offered for a parent already done**: `setTaskStatus` has no `status <> target` guard (re-issuing →done is how a completion day is amended), so firing it there would restamp `completed_at` to now and move a delivered task into the current month, the exact trap `setTasksStatusBulk` documents. The **auto-tag** (`withRevisionTag`) declines silently in all three failure modes — tag absent, tag archived, task already at `TASK_TAG_MAX_PER_TASK` — because a task must never fail to save over a label. **The link moves through its own door**: `createTask`/`updateTask` only — `patchTask` and `bulkPatchTasks` have no such key, the same rule status and tags follow. Reads never N+1: `revisionMetaFor` in `taskQueries.ts` fetches a whole page's parent titles and revision tallies in two queries and folds them in JS (`tagsForTasks`' shape), and `TaskBoardRow` sits a step above `TaskListRowWithTags` so `listClientMonthTasks` — the client report, print sheet and `/share` reader — structurally cannot carry them.
- **The "Revision" TAG and the revision LINK are different things, and the tag is not the mechanism — even now that the link applies the tag.** A label carries no pointer to the parent, and a client-facing count must never depend on user-editable vocabulary that can be renamed, archived or deleted. `parent_task_id IS NULL` remains the only definition of a deliverable anywhere; the tag is a label that FOLLOWS the link so the board filter finds a round nobody remembered to label, and removing it breaks nothing.
- **The duplicate guard is where the noise actually stops.** `findSimilarTasks` (gate-first, returns `[]` on every miss and never blocks a submit) offers "looks like you already logged this" in the add band as the title is typed, scoped to the picked client and the last 120 days, matched in JS by `titlesLookSame` — no trigram extension. Members were never going to reach a menu on a row they would first have to find; 22 titles on the live board are duplicated within one client. The normaliser strips the markers the studio writes into titles and lives in the client-safe leaf `taskFields.ts` so `check-task-revisions.mts` can pin it. Matching is **equality after normalising, never a prefix** — `Photos MT Ashley` is a prefix of `Photos MT Ashley Int` and they are two different shoots, and a suggestion that cries wolf is one members learn to dismiss unread.
- **The board has TWO renderings and the switch is CSS alone.** Below `md` (768px) each task is an independent card (`TaskCard` / `TaskCardList`); at `md` and up it is the eleven-column table. Both trees are server-rendered — the card list is `md:hidden`, the table's scroller `hidden md:block` — so the first paint is correct at every width with no JavaScript. **Don't reach for `useMediaQuery` here**: it initialises `false` and flips in an effect, which SSRs the desktop table onto a phone and then snaps. It is also **not a URL param** — `?view`'s only value is `digest`, and the page's other phone adaptations (the folded filter chips, the collapsed add band, the bulk bar's "More") added none either: a layout is not something a link should carry. The card list is a **SIBLING** of the `overflow-x-auto` scroller, never a child, so its horizontal gesture never fights the pan that wrapper owns. The cost is ~50 hidden nodes on each side; the card is read-only, so the desktop half is cheap, and the escape hatch — unmounting the *table* after hydration, invisible because it is already `display:none` — is deliberately not taken pre-emptively.
- **The card is read-only, and that is the point.** The table's whole ergonomic is editing in place; reproducing eleven in-cell popovers on a 360px screen would be worse than the sideways scroll it replaces. A tap opens `TaskDialog`, which is already the full editor (there is no detail route — the dialog IS the editor). Every action a card offers already existed: the ⋯ menu is `TaskRowMenu` unchanged, delete is `openDelete` → the existing `ConfirmDialog` with its revision-orphan warning, and done is `requestStatus(row, 'done')` → `CompleteTaskDialog`. **A card must never grow its own mutation path.** Fills are TINTED with no per-card `backdrop-blur` (the `ClientsGrid` rule — ~50 stacked backdrop-filters is pure paint cost inside an already-frosted `GlassPanel`), and `TASK_TAG_STRIP_MAX` / `TASK_ASSIGNEE_STRIP_MAX` are unwound with `max-w-none`: those are clamps on an auto-layout TABLE's min-content contribution, not design choices.
- **Swipe left deletes, swipe right ADVANCES one stage (`nextStage`), and a `posted` row does neither way but left.** Both land in the confirm the desktop already uses, so no gesture commits anything on its own — and the swipe's own door is `advanceRow`, not `requestStatus`, precisely so it always interposes that confirm even where the row menu moves straight through: a flick is cheap to make by accident and an advance files work into a client's month. The refusal at the end of the ladder is the load-bearing half — see `scripts/check-swipe-actions.mts` above. The reveal names the stage it would move to (`advanceLabel`), never a fixed "Done". Every swipe has a non-gesture twin on the same card (the ⋯ menu carries Delete, the status control carries the stages), so the gesture is a shortcut and never the only path. Selection is a checkbox **and** a long-press; once anything is picked a plain tap toggles instead of opening, and the swipe stands down because the bulk bar owns the actions from there. **The phone hazard is Safari's back gesture**: there is no Lenis below `(min-width:1024px) and (pointer:fine)`, so `touch-pan-y` on the card plus `overscroll-x-contain` on the scrollers are the only defence — a right-swipe started within a few px of the left screen edge may still be claimed by iOS, and that is a known accepted limit, not a bug to re-diagnose.
- **`TasksListSkeleton` carries both shapes too.** `loading.tsx` renders it at every width, so a table-only skeleton puts the wrong shape on every phone and snaps into cards on swap — the exact jump `AdminSkeletons.tsx` exists to prevent. Any change to the card's shape changes the skeleton with it. **Every box the skeleton draws is IMPORTED from `Admin/tasks/menu.ts`** (`panelRow`, `panelDivider`/`panelRowPad`, `tabStrip`/`tabItem`, `tableHeadCell`, `tableHeadTrigger`, `tallyRow`, `taskCardBody`), never copied: five hand-copied class strings are how it drifted to a 26px head row against the table's 44, a missing page-tally line, and tabs 3px short. A row whose height comes from a real component's `text-*` classes uses `SkeletonText`, whose `inline-block`-inside-a-`span` shape puts the bar in the line box the sentence would have had — a bare `h-2.5` div measures itself and comes out short. When a panel row is added, add the token first and use it on both sides.
- **The board is scoped to ONE MONTH, and the rule is: a finished task belongs to the month it finished, unfinished work is always "now".** So a past month is a closed record of what shipped in it, while the current month carries what shipped this month PLUS everything still open, whatever month it started in — which is the strongest form of the old invariant (work in flight can never hide behind a month) rather than a weakening of it. It is one OR'd, tasks-columns-only clause in `tasksWhere` (`completed_at` inside the window, OR `completed_at IS NULL` when the scope is the reader's current month), so `count(*) over ()` and the join-free tab-badge COUNT both keep working, and **there is no column and no migration behind it**. The month is **`?month=`, its own param**, matching Reports/Leaderboard/Payroll/Costs. It used to ride the general date facet (`drange=YYYY-MM`) and be offered on the shipped tabs only, which is exactly what made it read as a duplicate of the Filters date menu: it was one. `drange` therefore no longer accepts a literal month on ANY field (so `dfield=created` loses its month window — `from`/`to` still covers it), the twelve month rows are gone from `TaskDateFilter`, and both legacy spellings (`?drange=YYYY-MM` and the older `?month=`) are PARSED onto the scope and never re-serialized. `exportTasksCsv` must keep tolerating a legacy month token in its raw `drange` gate, which runs before parsing — a stricter gate there 400s every month export URL ever bookmarked. **`month` is deliberately absent from `taskListQs`** and rides `taskScopeQs` instead: `task_views.query` stores the former and compares it by equality, so a month inside it would pin every saved view to the month it was saved in. It is not a filter either — excluded from `hasActiveTaskFilters`/`countActiveTaskFilters`, and it survives "Clear filters". Defaults differ by view on purpose: the list opens on the CURRENT month, the digest opens UNSCOPED, because a rolling seven days straddles a month boundary and clipping it to the calendar month would empty that page every 1st; crossing List↔Digest carries a month only when one was actually picked. `TaskMonthBand` is its own full-width row at the top of the panel, above the tabs, on both views — **and the skeleton must carry it at every width or the panel jumps on swap**. On a past month `taskTabsFor` drops the four working tabs (they could only ever be empty) and `coerceTaskView` re-points a bookmarked `?status=open` to `done` SERVER-SIDE, before the tabs or the query see it; the quick-add band is replaced by a one-line note in a box of the same height (`loading.tsx` gets no `searchParams`, so the one skeleton has to be right for both states), and the bulk bar drops the three reopening moves, which would evacuate a row out of the month somebody is reading. The wrap-up strip is folded from the rows already in hand (zero extra queries, `TagMixStrip`'s discipline) and takes **no `tone` prop**, so like `InternalKpiPanel` it cannot render onto a print sheet.
- **"How long has this been waiting for sign-off" is read from `task_events`, never from a column.** The newest `kind='status'` event whose `payload->>'to'` is `needs_approval`, via `waitingSinceFor` — migrations 0018/0019 added and dropped `tasks.status_changed_at` and it stays gone. `updated_at` is the fallback for rows predating the feature, and the label hedges to "about N days" when it is used, because any later edit resets it and it can only ever under-report. Amber past a week, **never rose**: rose is the overdue tint and has to keep meaning a missed deadline — a client who hasn't replied has missed nothing.
- Migrations 0018 and 0019 are an added-then-dropped `tasks.status_changed_at`. **The column is gone**; the time-in-status badge it fed was removed. Don't reintroduce either.

### The weekly digest email

The Monday letter the studio sends itself, and **the only HTML email in the app**. `src/app/api/cron/weekly-digest/route.ts` owns the window and the recipients; `src/lib/digestEmail.ts` owns everything it says.

- **It is a briefing, not a ledger.** It used to print every finished task, which for Aug 24 to Aug 30 was 158 lines over five screens. That is the board pasted into an inbox, and the dashboard renders the same rows better than an email can (faces, links, nested revisions, tags). It now leads with rollups by **client** and by **category** (neither of which was in the email at all, and the client one is the most useful line in a client-services digest: it says who the week actually went to), then gives each member their longest four jobs. The same week now renders in 62 text lines.
- **Every cap states its remainder, with the hours.** `+ 22 more · 39h 30m`. Visible rows plus that line still equal the total beside the member's name, so the cut can never pass for the whole. The house no-silent-truncation rule; on a page of hours it is an arithmetic error rather than a display one.
- **Three routes to one total, and they must agree.** Members reach the studio total with minutes SPLIT (`splitMinutesAcross`, largest remainder); clients and categories reach it with whole minutes counted ONCE, because a client is owed the entire shoot however many people attended. Pinned by `scripts/check-digest-email.mts` and re-checked against live rows by the preview script.
- **The fold says `deliverables`, the copy says "shipped".** Since the done → delivered → posted ladder, `delivered` names one STATUS, so a field called `delivered` meaning "rows with no parent" and a headline reading "253h shipped" over a set spanning all three stages would both misread. `listRecentDone` filters `SHIPPED_STATUSES`, so the email covers every shipped stage and must not call that "delivered".
- **One fold, two renderings.** `composeDigestEmail` folds once and renders the HTML and its plain-text twin from that result, so they are structurally incapable of quoting different figures. `text` always ships; a client refusing HTML loses nothing.
- **Escaping is a security-shaped correctness fix, not a nicety.** Titles and client names are member-typed free text going into an HTML document, and the real board already carries `Cartel Lash & Supply Co` and `fix: put the "Get 10% off" tab back on mobile`.
- **The letterhead is `public/perseus-wordmark-email.png`**, generated by `scripts/generate-dashboard-icons.mjs` from the wide AVIF wordmark using the same luminance-to-alpha recolour the dashboard icons use. It has to exist because **Gmail renders neither AVIF nor SVG**, and the square coin icons go illegible below about 120px. White on `#141414` with **no alpha** (Outlook mishandles PNG alpha over a coloured background) and 64-colour palette encoded (11.7 KB rather than 36.4 KB). It sits at the public ROOT, not under `/images/`, which is served `immutable` and would need a new filename per content change — and its URL is built by hand, because `resolveImageUrl()` silently swaps anything outside `/images/` for the AVIF placeholder.
- **Email-client rules that fail silently in a browser**, all pinned by the check script: tables and inline styles only (Gmail strips `<style>`), bar widths in PIXELS (Outlook's Word engine mishandles percentage widths on nested table cells), a bulletproof button rather than a bare anchor (Outlook will not size one), `color-scheme: light` so Apple Mail and Outlook.com stop auto-inverting (Gmail inverts regardless, which the near-black band survives), and a hidden preheader carrying the headline, which is what Gmail shows in the list. **No member avatars**: they stream through the authenticated `/admin/avatars/[userId]` route, so no mail client could ever fetch one.
- **The CTA points at `?view=digest`**, the in-app rendering of this same email, so the reader lands on the shape they were just looking at rather than a board tab whose own window disagrees with the week above it.
- **The subject wording is deliberately unchanged.** Gmail threads by subject, so rephrasing it would split the digest away from every previous week.
- The push twin is untouched and stays counts-only (`{ kind: 'digest', tasks, members }`) — it lands on a lock screen. **Nothing the HTML layer adds may reach it.**
- **The inbox avatar is not fixable here.** The grey circle beside the sender name in Gmail's list comes from BIMI (DMARC at enforcement plus a paid verified mark certificate) or a Google Workspace profile photo on `forms@perseustudio.com`. DNS and Workspace work, not repo work.

### Reports & leaderboard

Per-client monthly reporting (`/admin/reports`, `requireArea('reports')`) plus the studio's own standing (`/admin/leaderboard`). Both read the task log through one definition of delivered work: **a status in `SHIPPED_STATUSES` (`done`, `delivered`, `posted`) with `completedAt` inside the reader's month window, valued at `actualMinutes ?? estimatedMinutes`.** The stage a task has reached never changes what it is worth; it only says how far along it is, and the client-facing table carries it as a chip beside a summary line (`stageSummary`, zero stages omitted, the deliverables-caption rule).** The dashboard, the print sheet, the share link, the digest and both crons all use it.

- **The client-facing / internal split is structural, not a convention to remember.** `InternalKpiPanel` and `ReportReadiness` take **no `tone` prop**, so having no print variant they *cannot* render onto the print page or the share link. Keep it that way rather than adding a `tone` and a condition. Likewise the vs-last-month deltas (`tiles.tasksDelta` / `hoursDelta`) are dashboard-only, while `hoursWorkdays`, `turnaroundLabel` and the highlights note do travel — they interpret, they don't compare. `MemberBars` gets `showShare` on the dashboard and the internal page but **not** on print or share: a per-member percentage split is a staffing detail the client didn't ask for. The report CSV omits `notes` because it travels with the PDF; the internal task CSV keeps them.
- `buildClientMonthReport` and friends (`src/components/Admin/reports/reportData.ts`) are shared **verbatim** between dashboard and print, so the PDF shows the exact strings the dashboard showed. Turnaround is a **median, not a mean**. `foldReadiness` deliberately does *not* check for missing hours — a check that can never fire is worse than no check, because its silence reads as a pass.
- **A share token is the whole credential** (`randomBytes(24)`, base64url). It is therefore **never logged** — `mintReportShare` writes an `activity_log` row carrying only `{ month, clientId }` — and `listActiveSharesForMonth` **deliberately does not select the token**, because the roster only needs "have I sent this yet?" and a live URL beside 88 client names is shoulder-surfing bait. Malformed, unknown and revoked tokens all 404 **identically**, so tokens can't be probed apart. The page is `force-dynamic` so revocation bites on the next request, sets its own `noindex` (**required** — the root layout declares no robots default), and is bypassed entirely by `public/sw.js`; `robots.txt` stays untouched on purpose, since a crawler has to be able to fetch the page to see the noindex.
- **The share page recomputes live; it is not a snapshot** — consistent with there being no month lock. Its one frozen value is the timezone: `report_shares.timezone` stamps the minting admin's zone so the client reads the same numbers the sender saw (a null, from pre-column links, falls back to `STUDIO_TZ`).
- **`/admin/reports/internal` is a static segment on purpose.** Next's route precedence shadows `[slug]`, so no client can claim the URL, and client creation additionally reserves the slug.
- **Export params are strict by house rule: an absent filter silently defaults like the list page, a present-but-malformed one is a 400** — a typo must never quietly widen a file someone will believe. An unknown client or category slug returns a header-only CSV, because absent data isn't an error. Both exports set `Cache-Control: private, no-store` and write their activity row **only on success** (logging first left permanent "Exported…" entries for files that never existed). **Export links are plain `<a>`, never `next/link`** — prefetch would fire the export.
- Print is two renderings of one component: theme-aware on screen, literal neutrals under `print:`, with `PRINT_SHEET_CSS` (`src/lib/printSheet.ts`) pinning the ground. See "Print surfaces" — `bg-white`/`text-black` are flip tokens and will betray you here.
- **The leaderboard ranks on DELIVERABLES**, with revision rounds shown as their own figure beside hours and never folded into the rank — otherwise whoever's work needed three rounds outranks whoever got it right first time. Revision hours still count in the hours column, so nothing anyone did is hidden.
- **The leaderboard ranks on task count alone.** Hours and on-time rate ride along as context and are **not blended into a score**, so there is no formula for anyone to distrust; hours only break an exact tie. Member identity is `assigneeId ?? name:<assigneeName>`, shared with MemberBars, the digest and both crons. Ranges are `month` (default), `d30` and `all` — rolling ranges exist because a board one month into tracking is nearly empty.
- **Champions, past champions and Most Improved are structurally absent in rolling mode**, because all three compare one calendar month to another; faking them would be worse than omitting them, and the month switcher hides itself to match. Every badge carries a hint with the row's own numbers so it stays checkable, and category champions need at least 3 tasks across at least 2 members — a single-member category title reads as manufactured praise. When a row cap bites, the **oldest** bucket is dropped and `dropTruncatedMonths` refuses to publish a partial month as a real one (it would crown the wrong champion); the page says so on screen rather than silently truncating.

### Tickets

Internal issues the team files against itself, which is why they sit under "Work" in the rail rather than "Inbox" (Inbox is strictly what arrives from outside).

- **The field is `severity` (`low | medium | high`), not priority, and tickets have no comment thread.** Don't document or build either from memory.
- **`area` is plain text, not an enum** — `TICKET_AREAS` is derived at runtime from `ADMIN_ROUTES`, so adding an admin route needs no migration, and `ticketAreaLabel()` falls back to the raw slug so a retired route's old tickets still render. `ticketAreaGroupsFor(access)` narrows the picker to areas the reporter can actually reach and **groups them the way the rail groups them**, with a trailing "More" section that SWEEPS every route no rail group claimed — that sweep is what keeps a future section-less route pickable. The page resolves the audience through `navAccess(profile)`, never a hand-built object: it was the one call site that spelled the three `NavAccess` fields out, so a field added later would have been dropped exactly here. The picker **wraps and must never go back to a scroll rail**: at twenty one areas the old `no-scrollbar` horizontal rail showed the first eleven and hid the rest, and the owner read a picker with no "Monitoring" in it as an access problem (2026-08-31). Pinned by `scripts/check-ticket-areas.mts`.
- **Two roles, two doors.** Holding the `tickets` area lets you file a ticket and read **your own** (all statuses mixed, no tabs). **Superadmin is triage** — it sees everything behind open/pending/closed tabs and is the only role that can change status. A foreign id returns `notFound()` rather than a 403, so ticket ids aren't enumerable. `searchTickets` never selects `screenshotPath`, and its `reporterId` must be non-null for a non-superadmin or the ⌘K palette becomes an ILIKE oracle over everyone's reports.
- **Screenshot intake is sniffed, not trusted.** Order in `createTicket`: validate, sniff the magic bytes, gate the decoded dimensions (a 4096² ceiling against decompression bombs), `put()` to the **private** store with `addRandomSuffix`, then insert — and if the insert throws, the orphaned blob is deleted. Only then does `after()` mail the superadmins with the image attached and set `emailSent`. A failed email leaves `email_sent = false` and **never loses the ticket**. The sniffers in `src/lib/ticketFields.ts` are reused wholesale by `avatarFields.ts` and `portfolioFields.ts` — fix them there, once.
- The screenshot stream is `private, no-cache` plus a SHA-256 ETag over the stored pathname — **deliberately not `immutable`**, so every view re-authorizes, while a 304 (answered *before* the blob fetch) still skips the up-to-4MB transfer.
- The activity row for a ticket **omits `description`** on purpose: free text may carry a pasted token.

### Logging & activity

Two separate products, deliberately not one system — different durability, retention, and audience.

- **Audit trail → Postgres.** `activity_log` (migration 0021) records who did what across every /admin surface, read at **`/admin/logs`** (the `'logs'` grant — a `SENSITIVE_AREA` like payroll: owner-flipped only, never in the explicit `DEFAULT_AREAS`, and safe to grant beyond superadmins precisely because no figure or secret can reach a row). `src/lib/activityLog.ts` is the single writer: synchronous, `void`-returning, body inside `after()`, failures only log — neon-http has no transactions, so an audit write can never be tied to the mutation it describes. **Call it only in the ok-branch**, after the real write succeeded. `write()` catches `after()`'s own throw and falls back to a fire-and-forget insert, because the Better Auth hooks call this during sign-in and a failed breadcrumb must never become a failed login.
- **Redaction is enforced, not remembered.** `ActivityPayload` (in `schema.ts`) allows scalars only, so `{...row}` is a *type error* rather than a privacy incident; `REDACTED_KEY_RE` in `src/lib/activityFields.ts` (a pure leaf, so it is testable) then refuses the values at runtime. **No payroll figure ever reaches `activity_log`** — `/admin/logs` is a wider audience than `requirePayrollAdmin()`, and payroll's whole privacy design is the own-vs-admin projection split a log line would otherwise route around. Submissions are referenced by kind + short id, never an applicant's name or email. Retention is **365 days**, swept from the daily `recurring-tasks` cron.
- **`task_events` and `payroll_events` stay as they are.** They carry domain columns (`task_title`, `month`, `member_name`) that are what make their own feeds readable. Those two domains write only their **structural and destructive** acts to `activity_log` as coarse, payload-free companion rows — routine task edits would otherwise bury every other domain in the global feed.
- **Diagnostics → stdout, via `src/instrumentation.ts` — and, since 2026-08-27, COUNTED.** `onRequestError` catches every server throw (`routeType: 'action' | 'route' | 'render' | 'proxy'`), which closes a real gap: an error thrown after the RSC stream begins is logged with a **200** status, so scanning for 5xx never found it. It filters client-aborted streams (`The destination stream closed early`, next.js#96704) — otherwise the most frequent "error" the app produces. Beside the stdout line it now calls `recordError` (see "Monitoring"), through `after()` first and an awaited, timeout-bounded write as the fallback: **Next awaits this hook only for route handlers** — for a render or action error the promise is handed to React's `onError` and dropped — so request-source counts are best-effort by construction. The hook is still **vendor-neutral**: an error tracker is one capture call inside that one function.
- **`src/lib/log.ts` is a ~90-line zero-dependency JSON logger** — Vercel's own documented recommendation for Functions. Not pino/winston: their worker-thread transports repeatedly break Next builds (next.js#86099, unresolved for Turbopack-on-Vercel). Two rules baked in: **stateless** (Fluid Compute reuses instances across concurrent requests, so module-level state leaks between them) and **never `console.warn`** — Vercel maps it to `warning` on a streaming function but **`error`** on a non-streaming one, so alerting on level misfires both ways. Use `log()` / `logError()`; the only surviving `console.*` calls are dev-only guarded ones and the client error boundary. Every line now also carries `deployment` (`VERCEL_DEPLOYMENT_ID`), `commit` (7 chars) and `region` when Vercel sets them — omitted, not blank, on a local `next start` — and `errorMessage`/`causeMessage` are capped at `MESSAGE_MAX` like stacks. **The event convention is deliberately small**: `LOG_EVENTS` in `logFields.ts` is a tuple (a typo is a type error) of the ~18 lines an operator searches for — `server.error.unhandled`, `action.error.caught`, `notify.email.failed`, `cron.run.failed`, `monitoring.write.failed` and so on — carried as `context.event` beside the free-text message. The ~110 `'[domain] fnName failed'` action messages were NOT renamed: their message already is their identity, and `reportError` (below) stamps them `action.error.caught` for free.
- **Caught action failures go through `reportError`, not `logError`.** Every outer `catch` in `_actions/*.ts` (plus the contact action, the presence route and the blog vote) calls `reportError(message, error, context?)` from `src/lib/monitoringRecord.ts`: the same signature, the same stdout line, plus a monitoring signal keyed by the message literal. That swap is what makes the error trend reflect what members actually hit — before it, ~110 caught failures produced a "something went wrong" toast and a 1-day stdout line and nothing else. `logError` stays for the seams that record explicitly (`notify.ts`, `push.ts`, `activityLog.ts`, `indexnow.ts`, `googleReviews.ts` — each pairs it with `recordDependencyFailure(component, error)`) and for anything that must never touch the database.
- **No third-party error tracker — decided 2026-08-19, don't re-propose one.** On Turbopack the browser SDKs cannot be tree-shaken (Sentry's `bundleSizeOptimizations`/`webpack.treeshake` are webpack-only), so the floor is 50–80 KB gz — most of what the 2026-07 chunk work removed. The account is on **Vercel Pro**, so runtime logs retain 1 day, which is the backstop. If it is ever revisited, a **server-only** install measures zero client JS and changes only `src/instrumentation.ts`.
- **Also not doing:** `@vercel/otel` (conflicts with tracker-side OTel setup, and a trace of one span is a log line with more machinery), Vercel Log Drains ($0.50/GB on *uncompressed* JSON), AsyncLocalStorage correlation IDs (no public Next 16 API; threading an id through `fetch` headers busts the fetch cache — `x-vercel-id` is recorded on the audit row instead), and **any raw diagnostic log in Neon**. That last clause was revised on 2026-08-27, narrowly: the four `monitoring_*` tables hold **bounded, privacy-safe aggregate signals and incident state** — counters (including per-day response counts), controlled dimensions, fingerprints — and never a message, a stack, a bound parameter or a request. Stack traces still live only on stdout. See "Monitoring".

### Monitoring

`/admin/monitoring` answers **"is the system healthy?"** — the third observability concept beside Activity (**who changed what**, `/admin/logs`) and Vercel's runtime logs (**why did this request fail** — the stack trace, kept for a day). Built 2026-08-27 across migrations 0038 (`monitoring_error_buckets`, `monitoring_checks`, `monitoring_incidents`) and 0039 (`monitoring_daily`, the SLO denominator), a new owner-granted `monitoring` sensitive area, and a fifth cron. No third-party observability dependency; the 2026-08-19 "no tracker" decision stands. **Run `scripts/check-monitoring.mts` (and `--db`) after touching any of it.**

- **Three modules, one direction.** `src/lib/monitoringFields.ts` is the pure leaf (vocabulary, thresholds, the cron registry, schedule math, bucket/series folds, fingerprinting, the row builders, the incident decision, the status derivation, the alert composers — everything `scripts/check-monitoring.mts` pins, and it takes `now` everywhere). `src/lib/monitoringRecord.ts` is the one **write door** for a signal (`recordError` / `reportError` / `recordDependencyFailure`). `src/lib/monitoringEvaluate.ts` is the **evaluator** the cron and "Check now" both run. Under them, `src/db/monitoringStatements.ts` holds every write statement as a function of a passed-in drizzle instance (guard-free, the `taskPredicates.ts` precedent, so the `--db` check runs the real SQL through its own Pool), and `src/db/monitoringQueries.ts` the `server-only` reads. `monitoringRecord` never calls `logError`'s callers back and `logError` never calls `monitoringRecord`, which is why a database outage produces one `monitoring.write.failed` line per failed request and no loop.
- **Counters, dimensions, fingerprints — never diagnostics.** `buildErrorBucketRow` is the only way into `monitoring_error_buckets` and reads three things off an error: its class name (`safeErrorName`, a closed regex, preferring the constructor because DrizzleQueryError's `.name` is `'Error'`), a **code from a closed grammar** (a 5-char SQLSTATE, a Node `E…` code or an HTTP status, walked down `.cause` like the action files' `pgCode`) and Next's opaque `digest`. The message, stack, params, request path with its query, headers and body have **no path into the row**, and `recordError` takes no free-form context so a caller's `{ recipient: email }` — which `notify.ts` passes to `logError` on purpose — can never reach a column. Scopes are bounded by source: a request row's scope is Next's route **pattern** (`/admin/reports/[slug]`, never `request.path`), an action row's scope is the `'[domain] fn failed'` message **literal** (our constant, whose cardinality is bounded by the code), a dependency row's a component from `MONITORING_COMPONENTS`, a cron row's a registered job name; anything else is `unknown`. **The fingerprint is FNV-1a over (source, scope, routeType, errorName, code)** — the message is not an input, so two throws differing only in a message are one group, and hashing a message would not have made storing it acceptable anyway.
- **Five-minute UTC buckets, one row per (bucket, environment, fingerprint), atomic upsert.** A burst of a thousand identical throws is one row with `count = 1000`. `first_deployment` is set on insert and never updated, so a group's earliest bucket says which build it first appeared in ("New in this build" on the page = that build is the one serving the page); the `last_*` columns (deployment, request id, digest) follow the newest occurrence and are the jump-off into Vercel's runtime logs. The page re-buckets server-side into a fixed column count per range (12 × 5 min, 24 × 1 h, 28 × 6 h, 30 × 1 d) and never receives a raw row dump; the top groups come from one DISTINCT ON + window-function query.
- **`monitoring_checks` is STATE, not history — one upserted row per probed dependency or cron job.** The dependency probes (`select 1` on the neon-http client AND on the WebSocket `Pool` behind Better Auth — two transports that fail independently; `list({ limit: 1 })` on each Blob store; Resend's read-only `domains.list()`, where a `restricted_api_key` reply proves the API is up and reads as ok; push from configuration plus device count) are each bounded by `PROBE_TIMEOUT_MS`, and **a timeout is `unknown`, never `ok`**. No dummy email and no dummy push is ever sent: those two are read from configuration plus the failures recorded when they were actually used (`observed` in `DEPENDENCY_CHECKS`). The failure streak and the `last_ok_at`/`last_failed_at` stamps are folded **in the upsert's SET clause**, so a duplicate cron invocation cannot double-count. For a cron the row is written by `runCron` — outcome, duration, summary — and `cronHealth` judges lateness against **that job's own schedule** (`parseCronSchedule` accepts exactly the four shapes `vercel.json` uses and THROWS on anything else, so an unsupported schedule fails the check rather than misreporting): a job is `missed` when the first slot after its last run has passed plus `CRON_GRACE_MS` (30 min), `pending` while it has never run and its first slot since the monitor first saw it has not passed, `failed` when its last run threw; two consecutive misses or failures are critical. `CRON_JOBS` in the leaf is the registry and the check script refuses to pass while it and `vercel.json` disagree in either direction.
- **Incidents: open → resolved, one row per condition, the alert bookkeeping on the row.** `buildSignals` turns a pass's readings into the conditions true right now (`error_burst` keyed by fingerprint — ≥ 5 in 15 min warning, ≥ 25 critical, plus a global critical at ≥ 20 across everything; `dependency` keyed by component — a probe failing **two** consecutive passes is critical for the two database transports and warning otherwise, two timeouts a warning, `unconfigured` in production a warning, ≥ 3 recorded send failures in an hour a warning, all folded to one signal per component at the higher severity; `cron` keyed by job). `decideIncidents` reconciles them against the open rows: open, touch (bump `last_seen_at`, escalate to critical once), cool (a burst waits `RESOLVE_GRACE_MS` of quiet; probes and crons resolve on the first clean reading), resolve, or **reopen** the same row when the key resolved less than `REOPEN_WINDOW_MS` (60 min) ago — the flap guard, and reopening never re-alerts. **Idempotent by the database, because Vercel documents duplicate cron invocations**: `monitoring_incidents_open_uidx` (UNIQUE `(kind, key)` WHERE `status = 'open'`) collapses concurrent opens onto one row, every `onConflictDoUpdate` against it carries `targetWhere: eq(status, 'open')` verbatim (the 42P10 rule), `openIncident` returns `inserted` via the `xmax = 0` idiom, and `claimAlert` / `claimRecovery` are conditional `UPDATE … RETURNING` so exactly one caller sends. At most one open alert (plus one escalation to critical) and one recovery notice per row, and at most `ALERT_CAP_PER_RUN` (3) notices per pass; a claim beyond the cap is simply left for the next pass. **If any read in a pass fails, the decision is skipped outright** — deciding on partial data would resolve real incidents.
- **Alerts go through `notifyGroup` to `monitoringRecipients()`** — the owner plus every `'monitoring'` grant, the `payrollAdminRecipients` shape — so the people told are exactly the people the deep link lets in. The email (`composeIncidentEmail`) carries the severity, the title (error class + route pattern / component / job), the count and window, when it started, the deployment / request / error ids to search Vercel by, and the page link — never a message or a stack. The push is the `monitoring` / `monitoring-resolved` notice kinds: a severity from a closed enum and a **count** of what is open, nothing else, pinned by `check-push.mts`. The evaluator's own send failures are recorded under the `monitoring-alert` component, **which no rule reads** — an email outage is reported once by real sends failing and never re-fed by the report of it.
- **The headline is derived, never "the query worked, so green."** `deriveOverallStatus`: any failed page read ⇒ `unknown`; no check ever ⇒ `unknown`; newest dependency reading older than `EVALUATOR_STALE_MS` (35 min, more than two evaluator periods) ⇒ `unknown` with "the monitoring job may not be running" — the one condition the evaluator cannot report about itself; any open critical ⇒ `incident`; any open warning or any check not `ok` (`failed`, `unknown`, `unconfigured`) ⇒ `degraded`; else `healthy`. The page reads through `Promise.allSettled` so one failed query degrades one named panel and the headline, never the whole page. The Overview's "System" card folds the **same** reads through the **same** function, gated by omission on the `monitoring` grant, so the card and the page cannot disagree.
- **Cadence is 15 minutes** (`*/15 * * * *`, Saman 2026-08-27) — chosen so a scale-to-zero Neon database can still sleep between passes overnight; a probe on both transports wakes it 96 times a day as it is. Alerts therefore land within ~15–30 minutes of a failure. Retention runs on the scheduled pass only, batched by `ctid` (`RETENTION_BATCH` × `RETENTION_BATCHES_PER_RUN`): buckets `BUCKET_RETENTION_DAYS` (30), **resolved** incidents `INCIDENT_RETENTION_DAYS` (90), checks never (they are upserted). `activity_log` keeps its own 365 days.
- **Vercel-owned signals stay on Vercel — except the one with an honest denominator.** Latency, function duration and the full request log have no in-app denominator, so the "On Vercel" card links to Observability, Runtime logs, the Cron Jobs settings and the current deployment rather than drawing a figure. Request SUCCESS is the exception, since 2026-08-27: Vercel's **documented** `POST /v2/observability/query` (the `vercel metrics` command; in the OpenAPI spec) answers `vercel.request.count` over a real window, so the scheduled pass folds yesterday's and today's production responses by UTC day into `monitoring_daily` under the `requests` component — `ok` = every response that was not a 5xx (a 4xx is a client outcome, not an outage), `failed` = 5xx — through `raiseDailyCounts`, a `greatest(stored, answered)` per column rather than a bump: a day's count from Vercel only ever grows, so a duplicate cron invocation lands the same numbers twice instead of doubling them and a defective short answer can never lower a real day. An answer with **no rows at all** is refused outright (`foldRequestCounts` → null) — this site serves thousands of responses a day, so an empty window is a defective reply, and writing it as fact would be the `?? 0` trap. It runs on the **scheduled pass only, never behind "Check now"**: the status scan costs Vercel 10–15 s (measured), and `limit` is 200 groups because the default of ten silently dropped rare statuses — an answer that fills the cap is refused rather than folded short (`foldRequestCounts` → null). A failed fold is a failed step (`stepsFailed`, the cron's warning) and a recorded failure under the `vercel` component, which **no rule reads** — the monitor losing its counts is not the site being down — but which the Requests row names ("the count failed N times in the last hour"), so a stale figure never goes unexplained. The docs say the metric needs Observability Plus; it answered on this team with three days of retention, so if it ever starts replying 402 the row simply stops updating and says when it was last counted. Body shape, filter literal and group cap are pinned by `scripts/check-monitoring.mts`.
- **"Recent on Vercel" is a WINDOW, not a stream — because the documented stream never answers.** `GET /v1/projects/{id}/deployments/{id}/runtime-logs` is a live stream with no window and no limit, and against this project it **held the connection for 90 s without sending a byte** (2026-08-27, every variation tried; `vercel logs --follow`, the very same URL, sat on "waiting for new logs" with ~25 requests a minute flowing — so it is not auth and not our client). What the CLI uses WITHOUT `--follow` is a windowed query — `GET https://vercel.com/api/logs/request-logs?projectId&ownerId&deploymentId&startDate&endDate&page` (found with `vercel logs --debug`; undocumented, but it is what `vercel logs` and Vercel's own MCP server ship against, so a change there breaks their tools before ours) — answering `{ rows, hasMoreRows }`, each row a request with its function log lines nested under `logs[]`. So `recentRuntimeLogs` (`_actions/monitoring.ts`, through `src/lib/vercelApi.ts`, the one door that spends the token) asks for the last `RECENT_LOGS_MINUTES` (5) of the build serving the page, at most `RECENT_LOGS_MAX_PAGES` pages, capped at `RECENT_LOGS_MAX_ROWS`, all inside `RECENT_LOGS_TIMEOUT_MS` (10 s) — behind `VERCEL_API_TOKEN` (an access token **scoped to the team — "All Projects"** at vercel.com/account/tokens; one narrowed to a single project is refused by both Vercel reads, 403 here and a 404 "Observability Data not found" on the counts, and the `vcp_` prefix is shared by both kinds so it tells you nothing — verified both ways 2026-08-27 — **server-only, Production env**; `VERCEL_PROJECT_ID`/`VERCEL_DEPLOYMENT_ID` are Vercel's own system vars, so locally the panel says "only on Vercel"; the team id is a constant in the leaf beside the slugs). Manual only — never on render. Every row passes `parseRequestLogRow`: the request keeps method, path-without-query, status, source and request id — and `redactRequestPath` collapses a **credential-bearing path** to its pattern before the row exists (`/share/reports/<token>` is the whole credential of a client report and is never logged or listed; Better Auth's `/api/auth/reset-password/<token>` is live for an hour; as a backstop any segment shaped like a token — 16+ url-safe characters with a digit and an uppercase letter or underscore, which no slug here has — is collapsed too); beneath it **only our own logger's JSON lines** survive, reduced to the closed field set (`message` matching our literal grammar, `event`, `errorName`, `fingerprint`, `routePath`, `job`, `digest`), and every other line is counted as withheld and never returned. Nothing from the window is stored. `summarizeRecentLogs` counts what came back by status class over the window — never a rate — and says when the window held more than the cap. A connection that never answers inside the bound is reported as `silent` ("did not answer"), one that answered but did not finish as `timeout` — or, when a page had already been parsed, as that page marked truncated — and the token hint is shown only for a 401/403; none of them ever reads as a quiet site.
- **Service levels — only over a denominator the app owns.** `monitoring_daily` (migration 0039; one row per component per UTC day, `ok`/`failed`/`unknown`, bumped by the evaluator for every probe and by `runCron` for every run — and raised whole for `requests` — swept with the incidents) feeds `sloReport` in the leaf: **dependency availability** = ok probes / all probes (a timeout counts against it; `unconfigured` counts as nothing), and **cron reliability** = successful runs / runs the schedule called for since the monitor first saw the job (`slotsBetween`) — so a run that never fired counts against it exactly like one that threw. Targets live in `SLO_TARGETS` (99.9 for both database transports, 99.5 files, 99 email and every cron), the failure budget is stated as used/allowed, and a row is **"Not enough data"** below `SLO_MIN_SAMPLES` (96 probes) or `SLO_MIN_EXPECTED_RUNS` (3) rather than a figure rounded up from nothing. **Request success is the third row** (`requests`, 99.9, listed first): ok / (ok + failed) over the same 30 days from the daily rows the fold above writes, "Not enough data" below `SLO_MIN_REQUESTS` (1,000 responses), and past `REQUESTS_STALE_MS` (2 h without a fold) the row says when it was last counted rather than reading as current. Its earlier absence rested on "no windowed request API exists", which was wrong — the documented observability query has one.
- **Every bar and chip follows the house palette**: ink columns with the PayColumns group-hover readout and an sr-only table, `ok` as the quiet wash (a list that is mostly fine is not a column of black pills), amber for degraded/warning, rose for incident/critical, a dashed outline for unknown — and never colour alone. `MonitoringSections.tsx` takes **no `tone` prop**, so like `CostSections` it cannot render onto a print sheet. Native `<details>` carries the ids so the first screen is the summary and nothing needs JavaScript; the only client leaves are `CheckNowButton` (a server action that revalidates `/admin/monitoring`, no `router.refresh()`), `RecentLogs` (one click, one read, nothing stored) and `CopyChip`.
- **How to debug an incident.** Open `/admin/monitoring` → the incident names an error class and a route pattern (or a component / job) → expand "Ids for Vercel logs" → copy the request id (or the error id the person saw on screen, or the deployment) → search Vercel's runtime logs (link on the page) for the `unhandled server error` line, which carries the stack and the same `fingerprint`. For a cron, the checks row's summary says what the last run did and `cron.run.failed` on stdout has the throw. **No new environment variables**: the probes read the ones the dependencies already need, both Vercel reads share `VERCEL_API_TOKEN`, and the dashboard coordinates (team slug, project slug, team id) are constants in the leaf.
- **Monitoring writes nothing to `activity_log`** — not an incident, not a check, not "Check now". An incident is operational state, not an audit event, and the brief that built this was explicit that automatic exceptions never enter the human timeline. Incident history is the page's own (90 days).

### Admin sessions

**24-hour idle window, 30-day ceiling** (Saman, 2026-08-22), both in `src/lib/sessionPolicy.ts` and pinned by `scripts/check-session-policy.mts`. Better Auth's `expiresIn` is the idle window and `updateAge` (5 min, equal to the cookie cache's `maxAge` because a cache hit never reaches the DB) is how often an active session is re-stamped; the ceiling is a `databaseHooks.session.update.before` clamp in `src/lib/auth.ts` that narrows the refreshed `expiresAt` to `createdAt + 30d`, so the auth layer itself — every endpoint, not just our wrapper — refuses to slide a session past a month from sign-in.

- **"Activity" means the dashboard is visibly open, and that is structural, not a heuristic.** Only server actions and route handlers can refresh a session: Next 16 throws on `cookies().set()` outside the `'action'` phase and the `nextCookies` plugin skips refresh on RSC navigations, so a render can never re-issue the cookie. The 90-second `POST /admin/presence` heartbeat — which already pauses while the tab is hidden and fires on focus — is therefore the app's designated refresher. Work every day and you are never prompted; close the laptop for a day and the browser has dropped the cookie before you return. Don't add input-event idle tracking (rejected: a visible dashboard on an unlocked screen counts as present; the OS lock screen is the control for walking away) and don't add a per-device "keep me signed in" (nobody asked).
- **The normal expiry is the proxy bounce, not a DB rejection.** The cookie's `Max-Age` equals the idle window, so an idle session is gone from the browser before the row is checked. The row-dead-but-cookie-present path (the ceiling landing mid-session, an admin revoking it) is caught by the layout's DB read, and by the heartbeat: `PresenceHeartbeat` follows the route's redirect and sends the open tab to `/admin/login` within 90 seconds instead of letting the next click fail with a generic toast. **That makes the heartbeat a security control, not just a presence dot** — it is the only thing that catches a revoked session while nobody is navigating, so it must be incapable of stopping: its in-flight guard is a DEADLINE (`canPingNow`), never a boolean cleared in `.finally()`, because an iOS Home Screen app frozen at the process level can sever an in-flight fetch without ever settling the promise. It also listens for `pageshow`, which is the event a standalone iOS window actually fires on resume — `visibilitychange` and `focus` are not reliable there, and the interval was paused for the whole suspension. Pinned by `scripts/check-presence-heartbeat.mts`.
- **Re-sign-in lands where you were.** `src/proxy.ts` appends `?next=<path+query>` to its bounce (with Next's `_rsc` prefetch param stripped); `/admin/login` re-validates it through `safeAdminReturnPath` — the same guard, never trusted raw — and shows "Sign in to continue to Tasks." The copy never claims *why* you were signed out: the proxy cannot tell an expired session from a first visit, and a wrong claim is worse than none. The RSC-side redirects (`requireAdmin`, `getAccessProfile`) stay bare `/admin/login` on purpose — they can't see the URL without plumbing a header through the proxy, and they only fire on the rare row-dead path.
- **A lapse is not an auth event.** `session.delete.after` returns without logging when the removed row had already expired (Better Auth deletes an expired row through that same hook when its cookie is presented late), so `/admin/logs` never reads "signed out or revoked" for someone who simply went home. The daily `recurring-tasks` cron prunes the remaining dead rows **directly** (`deleteExpiredSessions`, bypassing the adapter's hooks) and reports the count as `staleLoginsSwept` — not `sessionsSwept`, because the redaction denylist refuses any key containing "session" and a count is not worth an exception.
- **The clamp hook has three rules it must keep**: act only when the patch carries `expiresAt` (the `/update-session` endpoint runs the same hook with none); **never return `false`** (that aborts the update and `getSession` then deletes the cookie and throws UNAUTHORIZED); and stay wrapped, because on the server-side `auth.api.getSession` path it runs inline and a throw there is a 500 on every admin render. `ctx.context.session` is the row being refreshed — verified against `better-auth@1.6.23` (`session.mjs:179` → `:224`) and cited in the hook's comment; re-verify on a Better Auth upgrade.
- **All three password doors evict sessions, and that is one invariant rather than three settings.** Changing your password from /admin/profile passes `revokeOtherSessions: true` (every session dies, and Better Auth immediately mints a replacement for the device doing the changing, so it stays signed in); an owner resetting someone from /admin/users calls `deleteUserSessions` outright; and a self-service "Forgot password?" reset is `emailAndPassword.revokeSessionsOnPasswordReset: true` in `src/lib/auth.ts`, which only deletes — there is no session on that path worth preserving, and ResetPasswordForm sends the person to /admin/login regardless. **The reset door was the one that did not**, until 2026-08-27; it is also the likeliest of the three to mean "someone else may be in here", so leaving the intruder signed in was exactly backwards. Eviction is bounded, not instant: an evicted device works until its signed cookie cache lapses (≤5 min), because Better Auth computes the cache's expected version from the CACHED payload (`session.mjs:87-96`) and therefore cannot notice a server-side revocation — only disabling the cache would close it, which is not worth it for a seven-person studio. **That window used to be more than browse-only: a device inside it could still REGISTER A PASSKEY — a permanent credential that survives every future password change — because the passkey plugin's register endpoints take `freshSessionMiddleware`, which reads THROUGH the cache, where `/change-password` and `/revoke-*-session` take `sensitiveSessionMiddleware`, whose entire purpose is refusing a revoked-but-cached session (`session.mjs:303-307`). Closed 2026-08-27** by a `hooks.before` guard in `src/lib/auth.ts`: on `/passkey/generate-register-options` and `/passkey/verify-registration` it re-reads the row with `internalAdapter.findSession` (a direct read with no cookie cache in it) and throws UNAUTHORIZED when the session is gone or expired — the `getLiveAdminSession` pattern applied at the endpoint seam. **Both paths are guarded on purpose**: refusing only verify still lets a caller burn the challenge, and refusing only the options step is skipped by anyone already holding one. The rest of the window stays browse-only and is still bounded by the cache, and an EXISTING passkey still outlives a password change by design (`resetUserPassword` in `_actions/users.ts`) — which is why the `profile` guide still tells anyone resetting on suspicion to review their passkey list, and why /admin/profile now names the count beside the password form. Auditing: `emailAndPassword.onPasswordReset` writes the CAUSE row (it fires with the user resolved, one line before the deletion), and each evicted row then writes its own `session.delete.after` line — so one reset reads as an act followed by its N consequences rather than a burst of unexplained sign-outs. Those `session.delete.after` / `onPasswordReset` try/catches are load-bearing: hooks flush in an unguarded loop AFTER the handler returns (`transaction.mjs:44-46`), so a throw there discards an already-built 200. (Auth runs on the transaction-capable `src/db/pool.ts`, not the neon-http client — the "no transactions" rule governs `src/db/index.ts` only.)
- **Unrelated but adjacent, don't confuse the two:** `freshAge` (24h from *sign-in*, untouched) gates adding a passkey and `unlinkAccount`, not removing a passkey. A member whose session is a day old cannot register a passkey until they sign in again — pre-existing, and the ceiling doesn't change it.

### Blog content model

Posts, authors and categories live in Neon (`blog_posts`, `blog_authors`, `blog_categories`, `blog_post_revisions`, `blog_post_related`, `blog_entities`/`blog_post_entities`, migration 0044) and are read through `src/lib/blogStore.ts` (`server-only`, `unstable_cache`, TTL 86400 because `Navbar` reads the blog panel on every marketing route). **The public predicate is `status = 'published'`, time-independent**, and every rendered field comes from the revision `published_revision_id` names, never from the working row (`src/db/blogPredicates.ts`, guard-free so the check script runs the real SQL). **One comparator**: `published_at DESC, legacy_id DESC NULLS LAST, created_at DESC, id DESC` (`legacy_id` is the old registry id; 27 of 38 posts share a publish day). **The URL identity is the WORKING row's `blog_posts.slug`**, not the published revision's — so a slug edit would move a live post's URL the moment it is saved, which is why `slugLocked` freezes it at the first publish and will stay that way until redirects ship. The body is a CLOSED Tiptap vocabulary (`src/lib/blogBody.ts`: schema, the zod layer that runs on the RAW JSON first because `nodeFromJSON` drops unknown attrs and `.check()` never validates values, then the canonical `toJSON()` is what is stored), rendered by `@tiptap/static-renderer` through `src/components/Blogs/post/articleMapping.ts` onto the existing `YouTube`/`Image`/`Instagram`/`HowTo`/`ProsCons`/`SmartLink` components (mapping functions ARE element types, so HowTo/ProsCons get real `<Step>`/`<Pros>` elements built from `node.content`; tables split their header rows into `<thead>`; cells and list items unwrap a lone paragraph; the `link` mark is ranked first so `**[x](y)**` renders `<strong><a>`). `ArticlePage.tsx` renders the whole post page from a `PublishedPost` view model and imports every dependency by direct path.

**Cache tags**: every entry carries `BLOGS_TAG` (`blogs`), and `blog:<slug>` additionally rides the per-slug detail entry. There is deliberately no per-category or per-author tag — neither would be attached to a cache entry, and a tag nothing carries is an invalidation that never runs. So every write door must ALWAYS expire `BLOGS_TAG`, whatever else it tags — which is what `refreshPublicBlog` in `blogInvalidate.ts` does, once, for all three doors. Two readers deliberately bypass the store: the "was this article helpful?" vote checks the slug through the UNCACHED `publishedSlugExists` (`src/db/blogQueries.ts`), because a cached gate would keep accepting votes on a post pulled minutes ago; and `/admin/feedback` reads titles through `fetchFeedbackPosts()`, which returns **published posts plus any slug that carries votes** — so a post unpublished since it was voted on keeps its row, suffixed with its status (`(draft)`) and no longer linked, instead of dropping out of the tally with its votes, while a draft nobody has voted on is not listed at all. That second arm is an access boundary rather than tidiness: `feedback` is in `DEFAULT_AREAS` and `blogs` deliberately is not, so the unfiltered read it replaced handed anybody holding the default grant a table of every draft, scheduled, archived and binned title while `/admin/blogs` and the preview both bounced them.

**Dates**: the public blog is a viewerless surface. Instants are stored at noon Vancouver (`dayNoonIn(STUDIO_TZ, key)`), and EVERY date the site emits (`<time dateTime>`, OG, JSON-LD, sitemap `lastmod`) is the STUDIO_TZ day key (`publishedDay`, `modifiedDay`). The two display labels are formatted differently on purpose: the published date goes through `DATE_LABEL` in `blogStore.ts` (`zonedFormat(STUDIO_TZ, { month: 'short', day: 'numeric', year: 'numeric' }, 'en-US')`) because it formats an INSTANT, while the "Updated" label in `ArticlePage.tsx` formats the `modifiedDay` KEY with `toLocaleDateString('en-CA', { …, timeZone: 'UTC' })` — the house rule for a `YYYY-MM-DD` with no instant behind it (`Admin/tasks/format.ts`'s reason). The "Updated" byline renders only when `modifiedDay !== publishedDay`. **JSON-LD** for every blog surface goes through `serializeJsonLd` in `src/lib/blogJsonLd.ts` (escapes `<`); every `@id` anchors on the SELF url, only `<link rel=canonical>` and `og:url` follow `canonical_override`, and the sitemap lists `sitemapEligible` posts only. `PERSEUS_PUBLISHER_REF` lives in `src/constants/index.ts`. `src/constants/blogIndexFaqs.ts` (hub FAQs) is the one code-defined piece left, because it is hub copy rather than post content.

**The write side** lives at `/admin/blogs` (see the Route map). Seven rules hold it together and every one of them is silent when it breaks — `node --import tsx scripts/check-blogs.mts` is what pins them.

- **A working copy and a published revision, and the public never reads the working row.** `blog_posts` is what the editor writes; `blog_post_revisions` is the immutable history, and `published_revision_id` / `pending_revision_id` are the only two pointers a reader or the scheduler follows. So an explicit Save on a live post **invalidates no public cache and announces nothing** — the working copy diverges from the published revision on purpose, and the Update door is what closes the gap. Autosave invalidates *nothing at all*, not even `revalidatePath('/admin','layout')`: every prerendered marketing page carries the `blogs` tag, so a keystroke timer on `updateTag(BLOGS_TAG)` would re-render the whole public site every second or two. An explicit Save does call `revalidatePath('/admin','layout')`, the house contract, because it is a deliberate act and the list's columns should be right on the way back.
- **Status and content move through separate doors** (the tasks/payroll rule). `_actions/blogPosts.ts` holds the three that do NOT change status (create, autosave, Save); publish, schedule, unschedule, unpublish, trash, restore, purge and amend-date are each their own door. That is what keeps `published_revision_id` out of reach of a keystroke. **Every write statement lives in the guard-free `src/db/blogStatements.ts`** taking a passed-in drizzle instance (the `monitoringStatements.ts` / `taskPredicates.ts` precedent), so the check script can run the REAL SQL — a check script cannot import a `'use server'` module.
- **The transition table is `ALLOWED_TRANSITIONS` in `blogFields.ts`, and `transitionProblem` is the one door onto it.** `published -> published` is deliberately in the set and is the only self-move that is (an Update writes a new revision and moves the pointer). `restoreTarget(history)` decides where a restore from the bin lands and is decided by HISTORY, never by the caller: a formerly published post goes to `archived`, so its URL stays a 404 until it is published again. Everything the editor OFFERS is derived from `transitionProblem` through `blogEditorActions`/`blogRowActions`, never restated, so a menu can never offer a move the leaf refuses. Migration 0045's three CHECK constraints are the database half; the `published -> scheduled` refusal is **not** redundant with them (they forbid the mechanism, this forbids the move).
- **Two fingerprints, and confusing them is invisible.** `contentFingerprint` covers the article as a reader meets it and is what moves `content_modified_at` — so an SEO-only edit must NOT move it, or the site republishes a freshness signal for every post somebody tidied. `publicFingerprint` covers everything a visitor renders and is what gates the **IndexNow ping**. Both are compared for equality across a jsonb round trip, so their JSON must be key-sorted: Postgres does not promise key order back out of a jsonb column, and an unsorted `JSON.stringify` reports a change that never happened on a random subset of saves. Never ping an unchanged URL.
- **`src/lib/blogInvalidate.ts` is the ONE invalidation door, in three thin shapes over one body.** `invalidateBlog` (a post written by a SERVER ACTION), `invalidateBlogFromCron` (the same post written by a ROUTE HANDLER) and `invalidateBlogTaxonomy` (an author or a category, which every public blog surface renders through). The first two share `applyBlogInvalidation` and **differ in exactly one function**: `updateTag` for the action, `revalidateTag(tag, { expire: 0 })` for the cron. That is not cosmetic. `updateTag` THROWS outside a server action (Next's `revalidate.js`, error E872), so a cron copying an action's block would publish every due row and then throw. And `{ expire: 0 }` is **not** `'max'`: `'max'` resolves to a year-long expiry, so `areTagsExpired` stays false and only `areTagsStale` is true, which is stale-while-revalidate — the first read after the cron gets served the PRE-PUBLISH snapshot, on `/blogs` above all, which reads searchParams and renders per request. `{ expire: 0 }` is byte-for-byte what `updateTag` does. It lives in its own module rather than beside its first caller because a `'use server'` file may export only async functions.
- **Expiring `BLOGS_TAG` is mandatory on every public-facing write, not belt-and-braces.** `getPublishedPost` reaches its per-slug entry only after a snapshot membership test, so a newly published slug is invisible until the COARSE tag is invalidated — which is exactly the cron's case, since every post it publishes is one the store has never seen. `invalidateBlogCoarseFromCron` is the floor it falls back to when it published rows it can no longer describe: refresh everything, announce nothing.
- **The slug is the live URL and locks the moment a post is published** (`slugLocked` reads `published_at is not null`), because the URL identity is the WORKING row's slug. The title-to-slug auto-follow (`nextSlugFollow`/`nextSlug`) runs only while the slug is still a `draft-<hex>` placeholder and **never re-arms**. A publish additionally refuses a category with no `seo_title` + `seo_description`, since the category page the post lives on would then carry no metadata either.

**Authors** are rows (`blog_authors`, `sort_index` = the old declaration order, organization first; `knows_about` byte-identical to the old arrays because the profile page keys `SKILL_DESCRIPTIONS` by those strings). `buildAuthorSchema(author)` takes the store's `PublicAuthor`. Adding an author is an INSERT from `AuthorsDialog` on `/admin/blogs`, never a code change. **`src/lib/adminIdentity.ts` is deliberately NOT wired to `blog_authors` and must not be**: its helpers are synchronous per-render formatters for the dashboard's own avatars, and reaching for the blog store would make every admin render depend on it. A dashboard account and a blog byline are two different things, and the two rostered accounts' photo paths are inlined there on purpose.

### Media & SEO conventions

- **All images** are served through `<Img>` (`src/components/Img.tsx`), a thin `next/image` wrapper. Image slots store a `/images/...` path; **anything else resolves to `IMAGE_PLACEHOLDER` via `resolveImageSrc` (`src/utils/images.ts`)** — migrate a slot one at a time by pointing its constant at the real `/images/...` asset (public/images mirrors the route map; see `public/images/README.md`). When building OG/JSON-LD image URLs by hand, use `OG_IMAGE` / `resolveImageUrl` from `@/utils/images`, not a hand-built CDN string.
- **`<Img>` is server-only; client components use `<ImgClient>`.** `Img` auto-looks-up the blur-up placeholder from `src/lib/imageBlur.ts`, which imports the full generated base64 map and is guarded with `import 'server-only'` — a client component importing `Img` fails the build (that import used to ship the whole ~40 KB map in the shared client chunk on every route). `ImgClient` (`src/components/ImgClient.tsx`) renders identically but takes the placeholder as a `blur` prop: the server parent looks it up with `blurFor(src)` and threads it down (see Hero slides via `app/(marketing)/page.tsx`, navbar panels via `lib/navigation.ts`, services projections via `app/(marketing)/services/page.tsx`). Non-laddered marks (logos) have no blur entry — pass nothing.
- `next.config.ts` declares **no** remote image patterns — every image is a self-hosted AVIF under `public/images` — and the **runtime image optimizer is off**: `images.loader: 'custom'` (`src/lib/imageLoader.ts`) maps each requested width onto the pre-generated `-384/-640/-960/-1280` static variants (see `npm run image-variants` above), so there's no `/_next/image` transcode and no Vercel Image Optimization usage. Don't re-introduce the default optimizer, `formats`, or `unoptimized`. Because `/images/*` is served `Cache-Control: immutable`, changing an image's content requires a new filename, not an in-place overwrite.
- OG/JSON-LD images are self-hosted, so there's no on-the-fly cropping. Article JSON-LD (`articleImageSet` in `src/lib/blogJsonLd.ts`) emits a single `ImageObject` at the resolved image URL rather than the 1:1/4:3/16:9 crop set; per-page OG images default to the shared placeholder until a real asset is wired in.
- The sitemap is a **sitemap-index route handler** at `src/app/sitemap.xml/route.ts` (Rank Math style, `dynamic: 'force-static'`, `revalidate: 3600`) pointing at five child handlers in `src/app/sitemaps/{pages,blogs,authors,projects,services}.xml/route.ts`. Those route files are thin — the logic lives in `src/lib/`: `sitemap.ts` holds the XML builders (`buildUrlSet`/`buildSitemapIndex`/`xmlResponse`) and enforces a **hard rule that no URL containing `?` or `#` is ever emitted** (so `?page=`/`?category=` views stay crawlable via on-page links but never appear in XML), while `sitemap-sections.ts` is the single source of truth: a `SitemapSection[]` both the index and each child derive from. **Adding a top-level page = add it to `CORE_PAGES` in `src/lib/sitemap-sections.ts`** (not the `pages.xml` route, which now just calls `pagesSection.build()`); adding a whole new child sitemap = one entry there plus a one-line route.
- `SITE_URL` (from `@/constants`) reads `NEXT_PUBLIC_SITE_URL` and defaults to `https://www.perseustudio.com`. Use it instead of hard-coding the domain.
- `public/llms.txt` is a **hand-maintained** AI-crawler index (positioning line, five service categories + sub-services, pillar-post reading list, contact email). It doesn't regenerate from the registries — update it when services, positioning copy, or flagship blog posts change, and bump its "Last updated" date.

### Structured data conventions

**Organization identity lives once.** `src/app/(marketing)/layout.tsx` declares the full `Organization` node with `@id: ${SITE_URL}/#organization`. Per-page schema (BlogPosting, CollectionPage) references it via `PERSEUS_PUBLISHER_REF = { '@id': '${SITE_URL}/#organization' }` exported from `src/constants/index.ts`. Don't inline the publisher object again — reference by `@id`.

**Author identity consolidates by `@id`.** `buildAuthorSchema` (`src/lib/blogJsonLd.ts`) returns the org author as `PERSEUS_PUBLISHER_REF`, and individual authors as a Person node whose `@id` is `${SITE_URL}/blogs/authors/<slug>#person` — the same `@id` the author profile page's Person node declares — so crawlers merge the article byline and the profile into one entity. E-E-A-T fields (jobTitle/description/image/knowsAbout/address/worksFor) come from the author's `blog_authors` row; enrich there, not inline.

**Video schema attribution.** `<YouTube id="..." external />` opts an embed out of VideoObject emission (videos on someone else's channel). Owned embeds carry an explicit `publisher: PERSEUS_PUBLISHER_REF`.

**Image license claims — emitted over a STATIC `/images` source ONLY, and that is a correctness rule rather than a nicety.** These fields are a machine-readable claim that Perseus created the image, holds its copyright, and licenses it on the terms at `/license`. That was true by accident while every image in the corpus was hand-curated; the moment `/admin/blogs` could upload one it stopped being true, so the claim is dropped for an uploaded asset. **There are TWO emission sites in `src/lib/blogJsonLd.ts` and they emit DIFFERENT field sets — a field absent from one is not a gap to "restore" from the other.**

- `articleImageSet(imageUrl, licensed)` — the **lead** image, emitting `license` + `acquireLicensePage` **and nothing else**. Never `creator`, `copyrightHolder`, `copyrightNotice` or `creditText`: a licence pointer says where the terms are, while those four assert who owns the picture, and the hero slot carries no per-image credit to assert it from. `licensed` is the **caller's own discriminator, never a guess from the url**.
- `figureOwnership(img, year)` — behind the `figures.map(...)` block that walks the body's figure nodes, and the **only** place the full set (`creator` + `creditText` + `copyrightNotice` + `copyrightHolder` + `license` + `acquireLicensePage`) is emitted. It switches on `img.source !== 'static'`, and **`creditText` goes with the rest**: the `?? 'Perseus Creative Studio'` default that stood in for a missing credit is not applied to uploaded media, because an absent credit must render no credit rather than our name. A credit the writer typed is their own words about their own image and still travels, so an uploaded figure keeps `creditText` alone when it has one.

The `/license` page at `src/app/(marketing)/license/page.tsx` documents the terms. Both sites are pinned by `scripts/check-blogs.mts` ("The licence claim").

### Global chrome

Chrome is layered across the two layouts. `src/app/layout.tsx` (root) holds only the document shell — Inter font, `<ConsentProvider>` → `<ThemeProvider>`, `<Toaster>` — so `/admin` shares one theme/consent root without loading marketing chrome or trackers. `src/app/(marketing)/layout.tsx` renders the public chrome once: `<SmartLenis>` (Lenis smooth-scrolling, desktop-pointer-only — skipped on touch and reduced-motion; `ReactLenis` re-exported from `src/utils/lenis.ts`), `Navbar`, `Footer`, `ScrollProgress`, `SpotLightLazy`, `ConsentBanner`, and the PWA components (`OfflineBanner`, `ServiceWorkerRegister`). Page-facing SEO defaults (title/OG/robots) also live in the `(marketing)` layout — not the root — so they never leak onto `(admin)`, which sets its own `noindex`. Analytics are **consent-gated** and `(marketing)`-only: `ConsentGatedAnalytics` reads the `ConsentProvider` state (persisted to `localStorage` under `perseus.consent`) and only then loads Google Analytics + GTM and Microsoft Clarity; Vercel `Analytics` + `SpeedInsights` are always rendered. Adding analytics elsewhere will double-fire and bypass consent — extend `ConsentGatedAnalytics`, not individual pages.

The admin rail has its own source of truth, `src/lib/adminNav.ts`: Overview sits bare at the top (`ADMIN_NAV_TOP`), everything else lives in `ADMIN_NAV_GROUPS` — Work, Inbox, Website, Team — and `ADMIN_ROUTES` is **derived** by flattening those, so the ⌘K palette (`CommandPalette.tsx`), the route-label lookup, and the ticket "where did you see it?" areas (`src/lib/ticketFields.ts`) all follow one ordering instead of a hand-synced second array. A group header renders only when the viewer can see at least one of its items, and on the 68px collapsed rail each header cross-fades to a centred hairline (`GroupHeading` in `AdminSidebar.tsx`) — the label stays mounted at `opacity-0` so screen readers keep the section names. Note `isAdminRouteActive` is a prefix match, which is why `/admin/my-pay` is not `/admin/pay`.

**The Overview's quick-actions card reads that same map, and must keep doing so.** `/admin` is an access-gated bento of per-area modules, and the card is how a viewer reaches everything the bento shows no module for. It used to be a hand-written list of three, which is exactly how `/admin/careers` shipped with no door from the dashboard at all — it joined the Website group two days after the bento was built and nobody edited the literal, so an account holding only that grant landed on a page offering one link, "Your profile". It is now `ADMIN_ROUTES` filtered by `canSeeNavItem` minus the hrefs the modules on **that render** actually took — *rendered*, not *granted*, so someone holding `leaderboard` with an empty board is handed the link rather than nothing. `/admin` and Commitments are never links (this page; reached from Spend, as on the rail), Payroll and Bills are never covered (the Money card links to Spend, so their month screens stay listed — which is also what gives a single-money-grant holder a door), and Profile is placed last explicitly. Past five links the card goes two-up. **Don't reintroduce a literal here**: the next admin route added gets a door for free only while this stays derived.

Every admin list focuses its primary input on arrival through `src/hooks/useSearchFocus.ts` — `useSearchFocus` (focus + the `/` hotkey + Escape) for search boxes, `useFocusOnMount` for a form's first field. Three rules are load-bearing. It is **desktop-only** (`(min-width: 64rem) and (pointer: fine)`, the ⌘B gate) so a phone doesn't pop its keyboard on every navigation; the decision is snapshotted in a `useState` initializer and never revisited, because a `?client=`/`?task=` deep link flips its flag one render later and a re-fire would steal focus out of the dialog that just opened. And **Escape is mandatory, not polish**: the inbox and task table bind single-key shortcuts (`j/k/x/e/s/z`) whose guards skip anything typed inside an input, so a focused search box mutes them — Escape empties the field, Escape again blurs it. Ship any new focus target with its Escape stage and its hint-row entry, or the shortcuts the legend advertises stop working. The `/` handler's target guard must stay the superset that includes Radix's `[role="menu"]`/`[role="menuitem"]`; the short version let `/` yank focus out of an open filter dropdown.

The dashboard's **⌘K palette** (`src/components/Admin/CommandPalette.tsx`, mounted once in the protected layout) is a cross-entity search over nine entities — task, comment, client, project, inquiry, application, ticket, user, activity — plus a "Go to" list built from `ADMIN_ROUTES` and filtered by `canSeeNavItem`. The vocabulary and the `task: brand video` scope grammar live in the client-safe leaf `src/lib/adminSearch.ts`; sidebar and mobile triggers reach the palette through the `perseus:admin-search-open` window event, because they are sibling islands with no shared client parent. Two invariants: **payroll is never searchable** — its entire privacy model is the own-vs-admin projection split, and a search path would be a third projection routing around it — and the action resolves the caller's profile **before** any DB work, gating each entity on its own area (tickets additionally row-scoped to the reporter unless superadmin), with the client-supplied `scopes` able only to *narrow*, never to widen.

**Page width is a three-way choice, and picking it is a content judgement, not a default.** `src/components/Admin/AdminPage.tsx` is the one wrapper: `narrow` (forms, detail views, the payslip — line length is the constraint), `wide` (lists, dashboards, card grids — grows one step at `2xl`), and `table` (pages whose main content is a horizontally scrolling `<table>`: tasks' eleven columns, the payroll month, the report's delivered work — width there buys visible columns, so it keeps climbing to `2100px`). The single-column list surfaces (users, logs, tickets, both inboxes, projects, the payroll roster) stay `wide` **on purpose** — stretching a row drags its right-hand meta away from the content it belongs to. So does `/admin/feedback`: it has a `<table>`, but a `max-w-lg` title cell plus five numeric columns caps it around 900px, so it can never overflow and the extra width would only push the numbers away from the post. Three gotchas: classes must be literal (the Tailwind scanner can't see computed names); **every skeleton's `Shell` must pass the same token as its page**, or `loading.tsx` renders at one measure and the page snaps to another — which is also why the tasks DIGEST is `table` despite having no table, since all three `/admin/tasks` views share one `loading.tsx` and toggling List↔Digest must not reflow the page; and adding a column step to a grid only helps if the container actually got wider at that same breakpoint (`2xl:grid-cols-8` on the clients grid was reverted for exactly this — `wide` caps at 1600, so eight tiles came out narrower than the six they replaced).

Two shape rules hold across every admin overlay, both learned from surfaces that ran the full height of the viewport. **A dropdown caps at `min(22rem, <the Radix available-height var>)`, never the var alone** — the var means "as much of the viewport as there is", which is how the 85-row client list became a full-page column; the `min()` keeps the var as the outer bound so short viewports still shrink. The recipe lives once in `src/components/Admin/menu.ts`, and a popover whose first child is a search field uses `comboPanel`/`comboList` instead, so the field stays pinned while only the results scroll. **A dialog earns width by splitting, not by stretching**: `GlassDialog`'s rungs below 40rem are single-column, and the 44/48/52rem rungs are for bodies that go `md:grid-cols-2` — reaching for a wide rung without giving the body columns to fill just makes a long form wider. Its optional `header`/`footer` slots render outside the scroller so a tall form keeps its title and its Save button in view; passing neither is byte-identical to the original single-scroller shape, which is why the confirm-sized dialogs were left alone. The footer sits outside the `<form>`, so a submit button there needs `form={FORM_ID}`. Note the scroller must NOT carry `flex-1`: `flex: 1 1 0%` zeroes the basis, and Content is `max-h-full` rather than `h-full`, so there is no free space to grow back from — default shrink against `shrink-0` slots is what does the work. **And every dropdown is built on `Admin/DropdownMenu.tsx`, never on Radix's `DropdownMenu` directly**: Radix opens on `pointerdown` alone, and on a machine that swallows that event every menu is dead while every click-driven button works — the door's Trigger falls back to the `click`, open-only, so nothing changes where pointerdown works.

Each admin section carries an ⓘ **help guide**: `src/lib/adminHelp.ts` is a `server-only` registry of 20 topics that the server-rendered header passes to `src/components/Admin/HelpButton.tsx` as **one serializable topic prop** (the button uses `import type` only). Keep that shape — importing the registry from the client would ship every guide into every admin route's chunk. The guides are voiced for their audience, which is a privacy rule as much as a tone one: the `my-pay` topic is written to the member and must never say "anchor", "wire fee", "company cost", or mention admin notes, and no guide anywhere carries a money figure. **When a section's UI changes, its guide changes with it** — a stale guide is worse than none.

Beside the guides sits the **release feed**. `src/lib/releaseFields.ts` is the client-safe leaf (the version tuple, the semver comparator, the chip tones, `resolveWatermark`) and `src/lib/adminReleases.ts` the `server-only` registry, typed `Record<ReleaseVersion, Release>` on that tuple so a version and its entry cannot drift — the `AdminHelpKey` mechanism. An entry declares its audience in **`canSeeNavItem`'s own vocabulary** (`NavGate`) and is filtered by that same function, so the changelog can never disagree with the rail about who sees what, and an entry can express the gates a single area field cannot (Spend needs `areasAll`, Commitments `areasAny`, My pay `payrollSelf`). Three surfaces, one column: `user.release_seen_version` is a **watermark** riding `getAccessProfile()`'s existing PK read, so the whole feature costs **zero extra queries**. **NULL means "clean slate as of first sight"** — the adapter omits the column on insert and that omission is the correct meaning, exactly as for `timezone` and `last_seen_at` — and the protected layout MATERIALIZES it in `after()` (the presence-floor pattern), because merely resolving it on every read would mean a member who never dismisses anything never sees a release. **The watermark gates the ANNOUNCEMENT; the areas gate the CONTENT, and they are independent** — a member granted an area later is not retro-announced its history (that is the same wall of history a new account must not get, and the section's ⓘ guide is the right artifact for "I'm new here"), but the `/admin/profile` section is not watermark-filtered, so they can read all of it whenever they like. **Entries outside the viewer's areas are absent, never counted** — "3 changes you can't see" leaks activity about a surface they don't hold, the same reading that makes `requireOwnPayroll()` bounce rather than show an empty page. The history is a **section on `/admin/profile`, not a route**, and the version string renders in `AdminPage`'s footer (`print:hidden` — the payslip prints through that wrapper) from `CURRENT_VERSION` in the **leaf**, never the registry, because `AdminSkeletons.tsx` imports `AdminPage` and may carry no `server-only` module. **Reading an update marks it read** (2026-08-27): closing `ReleaseHistoryDialog` — by button, Escape, overlay, or by following an entry link — calls `markReleasesSeen()`, exactly as `ReleaseNotice.dismiss()` always did. The dialog's own `history.watermark` is deliberately NOT touched (it is fetched once per page life), so the "Unread" pills stay put while somebody is reading; `RecentReleaseRows` and `OpenReleaseHistory` clear their own server-derived state off `RELEASES_SEEN_EVENT` instead, the `AdminSidebar` mirror-during-render shape. The explicit "Mark as read" button survives because it is the way to clear the dot WITHOUT reading, and the distinction the old comments protected still holds: merely landing on /admin/profile marks nothing, so a password change cannot cost you your place. Dismissal writes through `markReleasesSeen()`, which takes **no arguments** (the `/admin/presence` rule), is monotonic, writes **no** activity row, and deliberately does **not** `revalidatePath` — it dispatches `RELEASES_SEEN_EVENT` and the sidebar clears its own dot, because rebuilding the layout for one dot is ~10 Neon round trips for a render you already have.

Two rules the guides themselves follow. **A quoted string must be byte-identical to the label on screen**, apostrophe included — the quotes are a promise the reader can go and find that exact word, so anything that is a paraphrase goes unquoted. And a guide documents what someone has to be TOLD, not everything present: a tile reading "Salary cost" over a figure documents itself, and spelling every tile out buries the controls that genuinely need explaining (`"Add N missing"` on the payroll month is the canonical example — nothing else pulls a late joiner into a started month).

The dialog body is CSS multi-column, and its group spacing is **padding, never margin**. Fragmentation truncates a margin sitting at a column break, so the container's height silently loses it whenever the tallest column is not the last group — which is how three guides ended up flush against the panel's bottom edge while the others looked fine. `GuideGroup` carries `pb-6` and the scroller is passed `pb-0`, so the 24px below the last line is the group's own and is the same in every column configuration.

`Navbar` (desktop mega-panels), `MobileMenu`, and `Footer` all read their link structure from one source of truth — `src/lib/navigation.ts` (`navItems` plus per-panel builders for the services/projects/blogs mega-panels). Edit destinations there, not in the individual chrome components, so desktop and mobile can't drift apart.

### Offline / PWA

The site is an installable PWA with real offline support, built **without** a PWA library (no `next-pwa`/`serwist`) because Next 16 builds with Turbopack, where their webpack plugins are unreliable. Pieces:

- **Service worker** — `public/sw.js`, a hand-written plain-JS file (not bundled/typed). All cache names are prefixed with a single `VERSION` constant; the `activate` handler deletes any cache not matching it, so **bumping `VERSION` is how you invalidate everything**. Strategies: precache app shell on install; navigations + RSC fetches network-first → cache → precached `/offline`; `/_next/static/*` cache-first (content-hashed = safe); self-hosted images (`/_next/image` + `/images/`) stale-while-revalidate (capped). Non-GET requests (including server-action POSTs) and analytics are never cached, and `/api/*` plus the tokenized `/share/*` report links are ignored entirely (a revoked share must not stay readable from cache). **`/admin` is never WRITTEN to a cache** — not a page, not an RSC payload — but a failed `/admin` *document navigation* is answered with the precached `/offline`, because the dashboard is installable and a standalone window has no address bar to escape a browser error page from. The private route handlers (`/admin/*/export`, `resume`, `screenshot`, `presence`, `/admin/avatars/*`) are bypassed **before** that branch: they are top-level navigations until their `Content-Disposition` lands, so without the bypass the worker would sit in the path of the private streams. **Don't hand-verify any of this** — `node scripts/check-service-worker.mjs` loads the real `sw.js` in a fake worker scope and records every cache write; every one of these rules fails silently in a browser.
- **Registration** — `src/components/Pwa/ServiceWorkerRegister.tsx` registers the SW **browser-only and production-only** (disabled in `npm run dev` so it doesn't cache HMR assets). Don't expect offline behavior in dev — verify with `npm run build && npm run start`. Mounted in **both** the `(marketing)` and `(admin)` group layouts (never the root, so `/share/*` still registers nothing): `/admin` needs one because Chrome wants a worker before it offers to install the dashboard app. That is a registration change only — what `/admin` may cache is decided in the fetch handler, and the answer is still nothing. The `(admin)` layout imports it by **direct path**, not the barrel: that tree is deliberately barrel-free.
- **Two manifests, because the dashboard is its own installable app.** `src/app/manifest.json` (Next metadata-file convention, served at `/manifest.json`, `<link rel="manifest">` auto-injected) is the marketing app — `id`/`start_url` `/`. `public/dashboard.webmanifest` is the team's — `id`/`start_url` `/admin`, `scope: "/admin"`, ink icons — linked **only** from the `(admin)` layout via `metadata.manifest`, which overrides the root file convention (`mergeStaticMetadata` applies a manifest file only for the segment that owns it, and runs after the segment's own keys merge). **The split is decided at install time, not at runtime**: a browser installs whichever manifest the page you are standing on links, so a member installing from `/admin/login` gets an app that launches into `/admin` and a visitor installing from the public site gets the unchanged one that launches into `/`. Nothing on the marketing side references `/admin`; the offer lives only in `InstallDashboardCard` on `/admin/login` and `/admin/profile`. There is deliberately **no cookie and no launch-router** — the session cookie is `httpOnly`, so a client-side branch was never possible, and a server-side one would have meant a new long-lived device cookie plus a dynamic route on the statically prerendered home page. Three traps, all load-bearing: the dashboard manifest must live at the **root** (the manifest link is fetched without credentials in production, so a `/admin/*` URL is bounced by `src/proxy.ts` and the install fails); `scope` is `"/admin"` with **no trailing slash** (`"/admin/"` would put `start_url` out of scope); and declaring `metadata.icons` in the `(admin)` layout **overrides** the file-convention icons rather than adding to them, so `src/app/icon0.svg` has to be re-declared there by hand or admin tabs silently fall back to `favicon.ico`. Anything linking to `/` from inside `/admin` ejects a member out of the installed app, which is why the rail logos point at `/admin` and the deliberate out-links carry `target="_blank"`. `viewport.themeColor` is a light/dark pair in the `(admin)` layout (a partial `viewport` export is safe — Next overwrites only the keys a child declares, so the root's `viewportFit: 'cover'` survives, and `AdminBottomBar` depends on it). `appleWebApp` lives in `layout.tsx`'s `metadata` and is the **single** source of `<meta name="apple-mobile-web-app-title">` — a hand-written duplicate in `<head>` was emitted first and silently beat the admin override on WebKit; don't re-add one.
- **Web Push** — notifications for the installed dashboard, on every platform the studio uses. `src/lib/push.ts` is the ONE door (the only importer of `web-push`) and the only place that decides what a delivery failure means; `src/lib/pushFields.ts` is its client-safe leaf. **`sendToUser` has no `title` or `body` parameter** — it takes a `PushNotice` discriminated union and `renderNotice` is the only thing that turns one into words, so "no free text on a lock screen" is a TYPE error rather than a rule to remember, the same mechanism that makes `ActivityValue` scalars-only. **Never call `webpush.setVapidDetails()`**: it writes to a module singleton and Fluid Compute reuses instances across concurrent requests — pass `vapidDetails` per call, the `mail.ts` rule. `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` live in **Production only** (a Preview deploy has `NODE_ENV === 'production'`, so it WOULD register a worker and could write a real row), and the public key reaches the browser as a **server-derived prop**, never `NEXT_PUBLIC_*` — inlining freezes it at build time so a rotation would serve the stale key until a redeploy. Rotation is destructive: every existing subscription then returns 403, which is *not* a dead-subscription signal, so rotating must be paired with emptying the table. **Platform rules that are not optional**: `applicationServerKey` must be a `Uint8Array` (Safari and Firefox reject the string form Chrome accepts); permission must come from a user gesture and Firefox 72+ enforces it, which is why the registration is resolved in the effect rather than after the tap; a push event must ALWAYS display exactly one notification or Chrome shows its own banner and eventually revokes the permission; and **iOS/iPadOS delivers only inside a Home-Screen-installed app** (16.4+, and the manifest must not be the default `display: browser`) — in a Safari tab `window.Notification` is undefined, so unguarded access throws. The subscription table is `UNIQUE(endpoint)` and `ON DELETE CASCADE`; both are privacy controls, not hygiene — see the block comment in `schema.ts`. `pushsubscriptionchange` is deliberately unhandled (Safari never fires it, and elsewhere the 24-hour session cookie has usually expired by the time it does), so `NotificationsCard` reconciles on every visit instead — **unconditionally**, because deleting and re-adding the iOS Home Screen icon mints a new endpoint while the old row is still on file. **Two surfaces switch it on and they share ONE implementation**: `src/hooks/usePushSubscription.ts` is the door, consumed by `NotificationsCard` (`/admin/profile`) and by `NotificationsPrompt`, the post-login modal that offers it in one tap — a second copy of the four platform rules above would drift, and every one of them fails silently in a browser. Only the CARD reconciles (`reconcile: true`): both are mounted on `/admin/profile`, and two reconcilers would mean two writes and two refreshes for one device — which is also why the prompt renders nothing on that route. **The prompt opens ONLY on `off`**, because every other state is a dead end and a modal you cannot act on is worse than none (`denied` — the browser will not prompt again; `needs-install` — an iPhone still in a Safari tab; `unsupported` — which includes `npm run dev`, where VAPID is Production-only). It snoozes 30 days on dismissal under a **per-user** localStorage key (`PasskeyPrompt`'s lesson: a shared key let one admin's dismissal suppress it for the next admin on that browser), and stands aside for a day when a `notice` release is queued for the same login, so two modals never stack.
- **Every member-facing email has a push twin, and they go out through one door.** `src/lib/notify.ts` (`notifyMember` for one person, `notifyGroup` for a recipient list) is the only place a member is told anything: it sends both channels from a SINGLE recipient list, so a person cannot end up on the email and off the push. **The two deliberately say different things, and that is a privacy control**: the email carries the detail (task titles, client names, the month, what someone wrote) because an inbox needs an unlocked device and an authenticated account, while the push carries **counts and fixed sentences only** because it renders on a lock screen. That is enforced by the type — `notifyMember` takes a `PushNotice`, and no parameter anywhere accepts a notification title or body. Wired today: the `weekly-digest`, `due-reminders` and `payroll-nudge` crons (`recurring-tasks` sends no email, so it has no twin), task assignment, a filed ticket, a triaged ticket, a sent payroll line, a flagged payment, and a contact-form arrival (which pushes to whoever holds the matching inbox AREA, since the email goes to a role address rather than a person). **The sign-in alert is the one deliberate PUSH-ONLY notice** — `session.create.after` in `auth.ts` sends `{ kind: 'signin' }` through `sendToUser`, not `notifyMember`, because a "was that you?" email on every sign-in would be daily noise that trains people to filter the alert away; the rule this file states is that every EMAIL has a push twin, not that every push has an email. It fires only on the paths in `SIGN_IN_PATHS`, an ALLOWLIST, because `session.create` also fires for `/change-password` (which mints a replacement session, `update-user.mjs:170-176`) and a false alarm on that notice is worse than no notice. It carries no device, city or IP on purpose: those are the very things a sign-in alert elsewhere names, and every one is free text or personal data on a lock screen a stranger may be holding — the detail lives on `/admin/logs`, behind the session. **A notification's recipients are derived from the GRANT that opens the page it links to, never from a hardcoded list** — and both halves of that sentence were learned the hard way. The contact form used to email three literal addresses while pushing to the live `inquiries`/`applications` holders: one member held the area and got a notification about leads they never received an email for, and an offboarded person's address would have kept receiving every application with the résumé attached, invisibly. The rule also runs the other way: `listOpenDueByAssignee` and the assignment ping now skip anyone without the `tasks` grant, and `ticketTriageRecipients` needs role **AND** the `tickets` area, because a notice pointing at a page `requireArea` would bounce them from is a dead end whichever channel carries it. When an area list can be empty, fall back to a shared address for the EMAIL only (`INBOX_FALLBACK`) — losing a lead is worse than a stale recipient, and there is no account to push to anyway. **The password-reset email is the one deliberate exception and must stay email-only** — a reset is requested by whoever typed the address, who is not necessarily the person holding the phone, so a notification would confirm to a bystander that the address has an account here. **The app-icon badge counts in the SERVICE WORKER and is cleared by the PAGE.** The Badging API is write-only (there is no `getAppBadge`), so the running total lives in **IndexedDB, never Cache Storage** — parking it in a Response would break the invariant that nothing on the push path touches a cache, which `check-service-worker.mjs` asserts by recording every `cache.open` and `cache.put`. It means "notifications since you last opened the dashboard", so only the page can count it down (`AppBadge.tsx`, on mount and on every return to visible); the worker only counts up, after `showNotification`, so a badge failure can never cost the notification Chrome requires. **Where it actually draws, verified against MDN/BCD, caniuse, WebKit and Chrome docs rather than assumed**: a NUMBER on iOS/iPadOS 16.4+ (Home-Screen install only, and only once notification permission is granted — WebKit exposes badging to workers precisely so a push handler can set it), on macOS/Windows Chrome and Edge 81+ (installed) — but **from Chrome 152 (stable 2026-08-25) macOS gates the badge behind NOTIFICATION permission**, matching WebKit: without it `setAppBadge` silently does nothing, so the badge stops being independent evidence that a push arrived. That independence is what made "badge moves, nothing appears" a usable diagnostic on 151 and earlier, and it is gone; 152 also attributes a PWA's notifications to the app shim's own name and icon rather than to "Google Chrome", which is why an installed dashboard finally gets its own row in System Settings, and on macOS Safari 17+ via Add to Dock. **NOT AT ALL on Android** — Chrome, Samsung Internet and Firefox all lack the API, and the launcher draws its own DOT from the notification tray instead, whose lifetime follows the notification rather than our counter. Not in Firefox desktop, which cannot install a PWA at all. And on **Chrome for Linux the call resolves but nothing is drawn**, a silent no-op feature detection cannot catch. Installation is required everywhere; a plain tab has no icon to badge. So the count is a best-effort enhancement, never a channel — the notification itself is the delivery, and every call is wrapped because a missing badge must never surface as an error. **A LAPSED session does NOT suppress a push, and must not**: a subscription is a capability granted to a BROWSER, not a session, there is nothing signed in at 3am, and a reminder is most useful when the dashboard is closed — tie push to a live session and every cron reminder is suppressed, which is the whole feature. Nothing leaks, because the payload is counts; and the deep link finishes the job — `src/proxy.ts` bounces the sessionless navigation to `/admin/login?next=<the notification's own path>`, so signing in lands them exactly where it pointed. **An EXPLICIT sign-out is the opposite case and DOES silence the device** (2026-08-27): `releaseThisDevicePush()` in `src/hooks/usePushSubscription.ts` drops this browser's subscription, and both sign-out doors — `AdminSidebar` and the ⌘K palette — must call it **before** `authClient.signOut()`, because `unsubscribeDevice` is a server action behind `getAccessProfile()` and is refused once the session is gone. The distinction is the point: "my cookie lapsed overnight" is not a decision about the device, "I pressed Sign out" is — and signing out otherwise removed the only surface that can turn notifications off, since `NotificationsCard` lives behind the session, so a handed-on or borrowed phone kept buzzing with no way to stop it. The other thing that silences a device is the account being deleted, via the table's cascade.
- **Offline write outbox** — the contact form is the only client mutation. When offline (or a send drops mid-request), `src/components/Contact/ContactHub.tsx` queues the payload — including a **byte snapshot** of the resume, never the live `File`, whose on-disk backing can move before the flush — via `src/lib/contactOutbox.ts` on top of the zero-dependency wrapper `src/lib/offlineDb.ts`. `OfflineBanner` flushes the queue on the `online` event and on mount, replaying each record through the `submitContact` server action (at-least-once; deleted after confirmed send, or dropped if the action deterministically rejects it so one bad record can't poison the queue). `contactOutbox.ts` rides the shared chunk via OfflineBanner — it must never import zod/`contactSchema.ts`, and it dynamic-imports the action. See `OFFLINE.md` for the full strategy table and test checklist.

### Component organization

`src/components/index.ts` is the **barrel export** every page imports from. New shared components should be added there. Domain-specific subfolders mirror routes (`Home/`, `About/`, `Blogs/`, `Services/`, `Projects/`, `Contact/`, `Mdx/`, `Admin/` for the dashboard — its glass tokens live in `Admin/Glass.tsx` and its dropdown/popover panel recipe in `Admin/menu.ts` (one door: five bars had private copies and they drifted; `Admin/tasks/menu.ts` re-exports it and keeps only the in-cell editor grammar), and its dropdown PRIMITIVE in `Admin/DropdownMenu.tsx` — the one importer of Radix's `DropdownMenu`, enforced by ESLint, whose Trigger also opens on `click` when `pointerdown` never arrived (`Admin/menuTrigger.ts` is the pure leaf; see Commands) — plus `Pwa/` for the service-worker / offline UI). `Admin/blogs/` carries the posts list, the editor and its two dialogs, with the ProseMirror surface isolated under `Admin/blogs/editor/`: `BodyEditorLazy.tsx` is a `dynamic()` boundary around it precisely because that chunk is ~522 KB, which is also why the word counter states the STORED count rather than calling `wordCount` in the browser (a second boundary would emit a second ProseMirror chunk beside it). **It is `ssr: false`, the one deliberate exception to the keep-SSR rule below**: a contenteditable has nothing to prerender and the server HTML would only mismatch whatever ProseMirror builds in the browser. `ssr: false` is illegal inside a Server Component, which is why the `Lazy` wrapper exists at all. The shadcn-style primitives live under `src/components/ui/` (configured in `components.json`, style `new-york`, alias `@/components/ui`, `@/lib/utils`).

**The barrel is for pages/layouts only — components must import each other by direct path** (`@/components/Button`, `./BlogCard`, …), never from `@/components`, `./`, or `..` resolving to the barrel. A component importing the barrel creates a components↔index cycle that defeats Turbopack's export-level tree-shaking: every client component that touched the barrel used to drag the re-exported *server* components — and through them the entire `services.ts`/`blogs.ts` registries — into one shared client chunk loaded by all 86 routes (~110 KB gzip of dead JS per page before the 2026-07 de-barreling). Same discipline for data: client components take slim server-derived props (see `blogFeed.ts`, `lib/navItems.ts` vs `lib/navigation.ts`, and the Services overview projections in `app/(marketing)/services/page.tsx`) instead of importing the content registries; verify with `rg -l "We align on goals" .next/static/chunks/` after a build — it must come back empty.

**Chunking reality (2026-07 audit):** Turbopack merges every *eagerly referenced* client module into one shared chunk group — all routes list the same script set, so anything a client component imports eagerly is paid by every page. Two consequences: (1) content data must never be a client value import — `faqItems` lives in `src/constants/faq.ts` (FAQ page passes it to `<FaqList items={…}>`), the Partners marquee logos come from Postgres via `getPartnerLogos` (`src/lib/projectsStore.ts`) and reach `<Partners>` as slim server-derived props, the home hero gallery in `src/constants/homeGallery.ts` (home page passes slides to `<Hero gallery={…}>`), and the about timeline entries flow through `<Timeline entries={…}>` — keep new content data in leaf modules (or server-side DB reads) imported only by server components. (2) Heavy page-specific client components are code-split with `next/dynamic` **keeping SSR** (cobe globes in `HomeWelcome`/`ServicesHero`, embla primitives in `ServicesAds`, the apple-cards carousel in `ServicesList`, the contact form in `ContactHubLazy` — zod lives only in that async chunk) — the async chunk loads only where the component renders; don't convert these back to static imports. three.js (`shader4/5` behind `ThemedShader`) already follows this pattern.

### Styling

Tailwind CSS 4 with `@tailwindcss/postcss`, `@tailwindcss/typography`, and `tw-animate-css`. Global tokens and CSS variables are in `src/app/globals.css`. Conditional class merging uses `clsx` + `tailwind-merge` (re-exported as `cn` from `src/lib/utils.ts`).

**Pointer cursors are a base-layer rule, not a per-component class.** Tailwind v4's preflight dropped v3's `button, [role="button"] { cursor: pointer }`, so every hand-rolled `<button>` silently reverted to an arrow — only the shared `Button` primitives carried the class. `globals.css`'s `@layer base` block restores it as `button:not(:disabled), [role='button']:not(:disabled)`. Don't add `cursor-pointer` to individual buttons; do keep using explicit `cursor-not-allowed` / `cursor-text` / `cursor-grab` / `cursor-default` where the pointer is wrong, because the utilities layer is ordered after `base` and still wins.

**Fields never render under 16px on a touch screen, and that is one global rule, not a per-field class.** iPhone Safari zooms the page onto any focused `input`/`textarea`/`select` whose font-size is under 16px and stays zoomed after the blur. `ui/input.tsx` is `text-base md:text-sm` for that reason (why `/admin/login` never zoomed), but the inline search boxes, the `glassField` call sites, the date inputs and the native selects were `text-sm` at every width — so `globals.css` carries an **unlayered** `@media (pointer: coarse) { input, textarea, select { font-size: 1rem } }` beside the autofill rule (unlayered because `text-sm` is a utility and `@layer base` loses to it; `pointer: coarse` rather than a width query because an iPhone in landscape is wider than `md`). A new field needs no size trick; a field that must render ABOVE 16px has to opt out of that rule rather than be shrunk by it. `maximumScale: 1` on the viewport is not the alternative — Android Chrome honours it and loses pinch-zoom, and accessibility audits flag it.

## Conventions to respect

- **Server-first.** Only mark a component `'use client'` when it needs state, effects, or browser APIs. The blog index page passes server-read `searchParams` down to `<BlogPost>` as `initialCategory`/`initialPage` specifically to avoid a `useSearchParams()` CSR bailout so crawlers see article links in initial HTML — don't refactor that into pure client state.
- **Blog routing is URL state, not routes.** Do not propose `/blogs/category/<slug>` pages; keep `/blogs?category=<slug>`.
- **Main content before sidebar in DOM.** On `app/(marketing)/blogs/[blog]/page.tsx`, the main content `<div>` is placed BEFORE the desktop sidebar `<aside>` in source order. CSS grid `col-start-1` / `col-start-2` puts the sidebar visually on the right. This DOM order is intentional — putting the sidebar first caused a heading-order violation (H1 → H3 from SidebarCta) that AI-search audits flag on every post.
- **No `#posts` fragment in pagination hrefs.** Blog pagination uses `<Link scroll={false} href={...}>` and a `useEffect` watching `initialPage` to scroll `#posts` into view. Crawlers like Semrush flag the fragment-bearing URL as canonicalised against the fragment-free canonical — keep the fragment behavior client-side only.
- **Parameterised views navigate via `NavButton`, never `<a href>`.** Facet-filtered project views (`?service=` / `?industry=` / `?location=`) and contact prefills (`?tab=careers&role=`) canonicalise to their bare path and must not enter the crawl graph: emitted as links they audit as hundreds of thin single-link/deep pages, and robots-blocking them instead makes Semrush count each one as "blocked from AI search" (AI Search Health 95→85 — both tried, 2026-08-03). `src/components/NavButton.tsx` (`router.push` + hover/focus prefetch, honors `preventDefault` like `<Link>`) is the pattern — the URL still updates and deep links stay shareable. Deliberate exceptions that stay real anchors: `?page=N` pagination and `/blogs?category=` (indexable by design, self-canonical). Keep `src/app/robots.txt` allow-all except `/admin` + `/api/` — crawl-surface control lives at the link layer, not in robots.
- **Admin copy carries no em dashes.** Members read this dashboard daily and the em dash is the most recognisable LLM-writing tell; it made the studio's own tool feel machine-written, so 720 of them were swept out of member-visible copy on 2026-08-29. New copy under `src/app/(admin)/**`, `src/components/Admin/**`, `adminHelp.ts`, `adminReleases.ts` and the member emails/push uses a full stop, a comma plus a connective, or a colon. **Never a spaced hyphen " - " and never an en dash as a substitute** — both read the same way. Match the phrasing a sibling already uses rather than inventing one (`'Delete failed. Try again.'`, `'That category is archived, so pick another.'`, `'<fact>. Archive it instead.'`, `Label: value. Change` for aria-labels), because the same sentence appearing two ways across the dashboard is worse than either. **Four classes keep their dash and are not oversights:** comments and JSDoc (invisible to members, and the comments here are load-bearing documentation); the lone `'—'` empty-value glyph in a tile or table cell (`cadOrDash`, `?? '—'`) — a spreadsheet convention, not prose; regex literals, where it is load-bearing (`MESSAGE_KEY_RE` and `LOG_MESSAGE_RE` in `monitoringFields.ts` permit `—` but not `:`, so a colon silently collapses a message key to `'unknown'`); and developer-only diagnostics passed to `log()` / `logError()` / `reportError()` or thrown as an `Error` no member sees. **Public marketing copy has its own rule, below** — it used to be exempt and no longer is.
- **Public marketing copy carries no em dashes either, and the fix goes deeper than punctuation.** The public site read as machine-written for the same reason the dashboard did, but the dash was a symptom rather than the disease: `src/constants/services.ts` did not hold 481 em dashes so much as one sentence formula — `list → em dash → appositive payoff` — repeated 481 times, and swapping each dash for a comma would have left 481 identically-shaped sentences reading worse than before. New and edited copy under `src/app/(marketing)/**`, `src/constants/**`, the marketing dirs of `src/components/**`, the blog bodies written in `/admin/blogs` and the `careerFields.ts` composers follows four rules. **Voice is confident and specific**: lead with the checkable fact rather than the adjective, name the deliverable, stack or city instead of an abstraction, vary sentence length so no two consecutive sentences share a shape, and cut any sentence whose only content is reassurance. **Replace a dash by its class, never by rule** — an appositive payoff becomes two sentences or a colon; a parenthetical pair becomes commas or parentheses (`faq.ts` is the case where the prose is already good and only the punctuation moves); an emphatic pivot ("it’s not just X, it’s Y") is deleted along with the sentence around it; a one-word answer (`'Yes — we plan for it on the day.'`) takes a full stop. Never a spaced hyphen and never an en dash as a substitute. **The banned vocabulary is** `ensure`/`ensures`/`ensuring`, `seamless`, `leverage`, `unlock`, `elevate` (literal elevation is fine), `meticulous`, `robust`, `holistic`, `comprehensive`, `unparalleled`, `empower`, `synergy`, `streamline`, `vibrant`, `navigate the`, metaphorical `landscape`, and `at the end of the day`, together with four structural tells: stacked tricolons of ABSTRACT nouns (a concrete deliverable list is a spec and stays), scare-quoting coined terms, formulaic `## Why …` section openers, and decorative mid-sentence bolding in body copy. **Facts are frozen** — never invent a capability, client, statistic or credential, never add a price (the /contact/careers pay ranges are the deliberate BC Pay Transparency exception), keep every deliverable list item, and keep the target keyword phrases intact in titles, H1s, meta descriptions and opening paragraphs, rewriting only the connective tissue around them. **Three couplings make a copy edit here a code edit**: the `careerFields.ts` composers are pinned by `scripts/check-careers.mts` (one assertion pins a dash, so both move together); `faq.ts`'s `HIRING_FAQ_QUESTION`/`REMOTE_FAQ_QUESTION` are matched by EXACT string to swap the live careers answers in, so rewording a question there silently serves a stale answer; and `services/page.tsx`, `about/page.tsx` and `contact/page.tsx` each restate their meta description verbatim inside their own JSON-LD block. A body heading additionally slugifies into a TOC anchor and a `HowTo` step id, so renaming one changes a URL fragment. **Two classes keep the dash**: comments and JSDoc, and the en dashes, which are semantically correct ranges and compound modifiers (`Mon–Fri 8–6 PST`, `$30–45 / hour`, `Transport Canada–licensed`). Nothing enforces any of this — ESLint and `next build` are both copy-blind, and no `check-*.mts` script imports the marketing constants.
- **A member-visible admin change carries a release entry.** If a member could notice the difference — a new control, a moved control, a changed default, a habit that no longer works, a fix they had learned to work around — it gets an entry in `src/lib/adminReleases.ts` **in the same commit as the change**, and that section's ⓘ guide is updated with it (the stale-guide rule). Versions are **CalVer, `YYYY.M.N`** — year, month, and the Nth release of that month, so N resets on the 1st and the number can never run away to `1.200.0`. Batch a push into one release; a notable fix alone still gets its own number. **No leading zeros** (`2026.8.1`, never `2026.08.1`): the watermark is compared as numbers but stored as a string, so two spellings would be two watermarks. There is no MAJOR/MINOR/PATCH here on purpose — that is a compatibility promise to somebody choosing whether to upgrade, and this dashboard has no such reader; the New/Improved/Fixed chip already carries the kind of each change, finer than one number over a whole release could. `announce: 'notice'` interrupts everyone holding the area with a one-time dialog and is for a change someone has to be TOLD about; `'quiet'` is the default and leaves only the dot on the sidebar's identity block. Internal refactors, copy nobody was reading, and anything invisible to a member carry **no** entry — a changelog that lists everything is one nobody reads, and the studio ships ~10 commits a day. Entries are **append-only**: never edit, reorder or delete a shipped release, because everyone whose watermark has passed it will never see the correction — ship the correction as its own later release instead. **Renumbering the scheme is the one exception and it costs a data migration** (`drizzle/0037`): a stored watermark from the old numbering sorts below every new version, so without moving the watermarks with the numbers every member is handed the whole back catalogue as unread. The version in the page footer is `RELEASE_VERSIONS[0]`; there is no second place to bump.
- **Content changes carry a freshness ritual.** A blog edit sets `content_modified_at` (the editor stamps it); a services copy edit bumps that record's `seo.lastUpdated` (drives sitemap `<lastmod>`, the visible "Updated" line, and WebPage `dateModified`). After the change deploys, ping IndexNow for the affected URLs (`npm run indexnow` — see Commands). Careers edits made in /admin ping themselves. Date bumps and pings only ever accompany real content changes — never bump a date or ping an unchanged URL.
- **Two clocks, one door.** `src/lib/calendar.ts` is the only module that may name a timezone or turn an instant into a calendar day. Everything a signed-in person reads — task-date defaults, the Today/Tomorrow chips, overdue tints, the digest's day headings, report and leaderboard month windows, every timestamp on every screen — resolves in **their own** zone via `viewerZone()` (`src/lib/adminAccess.ts`), stored on `user.timezone`. That column is **derived, never chosen** — `TimezoneSync` writes whatever the browser reports on the next /admin render after it changes, and `/admin/profile` shows it read-only. There is deliberately **no manual override, and don't add one**: `resolvedOptions().timeZone` is the OPERATING SYSTEM's zone (not the network's — a VPN doesn't move it), so it already follows a real relocation on its own, and a pinnable setting could only make dates wrong (pin, move, and every date is silently a day off with nothing on screen to explain it). A zone this runtime's ICU can't resolve is logged as `timezone.rejected` — with no override, that log line is the only way a stuck zone becomes diagnosable. Only the surfaces with **no viewer to follow** take a fixed zone: the public `/share/reports/[token]` page (stamped with the minting admin's zone on the share row, so the client sees exactly what was sent), the weekly-digest and recurring-tasks crons (`STUDIO_TZ` — a daily template must fire once per studio day, not once per member), the estimate-stats window, and the marketing site's Vancouver office clock (`StudioStatus`, `Stats`, `FooterClient`, `MobileMenu` — a real fact about a real office). **A formatter with no `timeZone` option is a bug, not a viewer-local default** — an unpinned `Intl.DateTimeFormat` resolves to the RUNTIME's zone, which is UTC on Vercel; use `zonedFormat(tz, …)`, or pin `'UTC'` when the input is a calendar KEY rather than an instant (`YYYY-MM-DD` has no instant behind it — that is why `Admin/tasks/format.ts` is UTC on purpose). Accepted consequence of viewer-relative month windows: a task completed Aug 31 at 20:00 Vancouver time is Sep 1 in Tehran, so it counts toward August for a Vancouver reader and September for a Tehran one. That was a deliberate call (most of the work is done in Tehran, so the report agreeing with whoever did it is the truer reading) and it is pinned in `scripts/check-calendar.mts`.
- **Don't run git commands.** The maintainer handles all git operations; suggest commit messages instead of executing them.
- UI/redesign work: avoid generic agency/SaaS aesthetics (glass tiles, grayscale hover, soft drop-shadows) — distinctive design is the bar.
