# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start Next.js dev server with TurboPack on http://localhost:3000
- `npm run build` — production build. **Requires a reachable `DATABASE_URL`** (in `.env.local` locally; the Neon integration provides it on Vercel): prerendered pages read the portfolio through `src/lib/projectsStore.ts` at build time — the Navbar/Footer project panel alone puts every route on that path.
- `npm run start` — serve the production build
- `npm run lint` — runs the ESLint CLI directly (`eslint .`) against `eslint-config-next`'s **native flat configs** (`core-web-vitals` + `typescript`) in `eslint.config.mjs`. `next lint` was removed in Next 16, so don't reintroduce it.
- `npm run optimize-images` — `node scripts/optimize-images.mjs`, shrinks any over-budget asset in `public/images` in place (quality-safe; wrapped by the `/optimize-images` skill). `scripts/` also holds one-off image tooling not wired to npm: `migrate-images-to-avif.mjs` (ImageKit → self-hosted AVIF, with `--max-dim` downscale), `reduce-images.mjs`, and `generate-dotted-map.mjs` (world-map dot data).
- `npm run image-variants` — `node scripts/generate-image-variants.mjs`: pre-generates the responsive `-384/-640/-960/-1280` rungs next to every laddered image in `public/images` **and** regenerates the blur-up LQIP map `src/lib/imageBlur.generated.json`. Idempotent (skips up-to-date variants; `--force` rebuilds, `--dry-run` previews, optional subfolder arg). **Run it whenever images are added and commit the generated files with them.** The rung ladder + "what gets variants" rule live in `src/lib/imageVariants.ts` and are mirrored by the script and `deviceSizes` in `next.config.ts` — keep all three in sync.
- `npm run indexnow` — `node scripts/indexnow-submit.mjs`: pings IndexNow (Bing → Copilot/ChatGPT-search grounding) with changed URLs. **Run it after any content change deploys** — `npm run indexnow -- /blogs/<slug>` for a post, `npm run indexnow -- --sitemap services` after services-copy changes (`--dry-run` previews). Saman forgets this, so Claude should run it proactively (or remind explicitly) whenever a content change ships. Project edits in /admin ping automatically (`src/lib/indexnow.ts`, `after()` in `_actions/projects.ts`), and so do careers edits — `_actions/careers.ts` pings `/contact/careers` only when a non-draft listing's public fingerprint changed, and `/frequently-asked-questions` too when the open set changed (a draft edit, a reorder, or an icon swap pings nothing). **Client edits do NOT** — `_actions/clients.ts` only invalidates caches (its `after()` calls are blob cleanup, not pings), so when a client rename changes visible copy on `/`, `/about`, or project cards, ping those URLs manually. A logo swap or marquee reorder changes pixels rather than indexable text and is deliberately left unpinged. **Never ping unchanged URLs** — false freshness is a Bing spam signal, which is why this is a manual command and must never become a deploy hook. The key file `public/<32-hex>.txt` is public by protocol and must stay byte-identical with `INDEXNOW_KEY` in `src/lib/indexnow.ts`.
- `npm run psi` — `node --dns-result-order=ipv4first --env-file=.env.local scripts/psi.mjs` (`.env.local` supplies `PSI_API_KEY`; **keep `--dns-result-order=ipv4first`** — without it the googleapis call stalls on IPv6 from some networks, which is the "PSI is flaky" symptom): PageSpeed Insights v5 against the **live production site** — Lighthouse category scores, lab metrics (FCP/SI/LCP/TBT/CLS), and CrUX p75 field data, mobile + desktop in one run. Defaults to the homepage; `npm run psi -- /about /services` tests other paths, `--strategy mobile|desktop` narrows. Local changes don't move these numbers until deployed.
- `npm run db:generate` / `npm run db:migrate` — drizzle-kit against the Neon Postgres database (schema `src/db/schema.ts`, config `drizzle.config.ts`, migrations committed under `drizzle/`). Workflow for any schema change: edit schema → `db:generate` → `db:migrate` → commit `drizzle/` with the change. **Never use `drizzle-kit push`** — the schema will keep evolving (/admin, blogs) and needs migration history. `drizzle.config.ts` loads `.env.local` via dotenv (drizzle-kit doesn't read Next env files); `DATABASE_URL` comes from the Neon integration on Vercel.
- `npm run db:studio` — opens **Drizzle Studio** (`drizzle-kit studio`), a local read/write GUI over the Neon Postgres tables, at `local.drizzle.studio`. This is the way to browse/inspect the database in development (there is no in-app database viewer — a custom `/admin/database` route was removed in favor of this). Needs `DATABASE_URL` in `.env.local`.
- `npm run db:seed` / `npm run db:seed-clients` / `npm run db:seed-bios` / `npm run db:seed-careers` / `npm run db:seed-task-tags` — one-off idempotent seeders (run with `--env-file=.env.local`): team admin accounts (there is no public sign-up — this is how logins get created; prints each new account's temp password once), the ~84 logo-wall clients with their marquee membership/order, researched client bios (internal reference copy; never overwrites non-empty bios), and the careers catalogue — the 7 categories + 18 openings that lived in the retired `src/constants/careers.ts`, plus a backfill of `contact_submissions.role_title` for applications that predate the column. The careers seed matches by slug, skips any opening that already exists (/admin owns the row after the first run), and never deletes. `db:seed-task-tags` follows the same contract for the ~32 task tags and their category scopes — the vocabulary derived from what the studio's own task TITLES already encoded ("TH", "Reels", "VT"/"HZ", "(Eslahie)", "keyword research"). Its companion `node --env-file=.env.local --import tsx scripts/backfill-task-tags.mts` reads those titles and applies the matching tags — **dry-run by default**, `--apply` to write, idempotent through the `(task_id, tag_id)` primary key, and it only ever ADDS.
- `node --import tsx scripts/check-payroll.mts` / `node --env-file=.env.local --import tsx scripts/verify-payroll-db.mts` — the payroll self-checks (not wired to npm, like the other one-off `scripts/` tooling). The first pins the money math, form validation, and status matrix against the two **real Donya invoices** (DCINV234292 / DCINV234648) plus Mahdi NP's prorated first month; the second round-trips those same figures through Neon to prove `bigint({ mode: 'number' })` and `sum(...)::bigint` don't come back as strings or drift. The DB one is safe to re-run — it prefixes everything `ZZ-VERIFY-` and sweeps up in a `finally`, and its fixtures are dated **2999** rather than the real invoice months, because `payroll_runs.month` is globally unique and the tag lives only in `note` (seeding a run at a month payroll actually uses collides with the real row and kills the script before a single assertion runs). **Run both after touching `src/lib/payrollAmounts.ts`, `payrollStatus.ts`, `payrollSchema.ts`, or the payroll tables** — a silent arithmetic regression here is both invisible and expensive.
- `node --env-file=.env.local --import tsx scripts/check-activity-log.mts` — the activity-log self-check (same one-off `scripts/` shape as the payroll pair). Pins the **redaction denylist** (every secret and payroll figure refused, every ordinary field kept, `\bauth\b` not swallowing `author`), the `scrub`/`diff` helpers, and the DB layer: enum refusal, `ON DELETE SET NULL`, jsonb round-tripping as an object, and the `count(*) over ()` window pagination. Safe to re-run — every row it writes carries entity `ZZ-CHECK` and is swept in a `finally`. **Run it after touching `src/lib/activityFields.ts` or the `activity_log` table** — a loosened denylist is silent and unrecoverable, because once a salary is written into an audit row it is in every backup.
- `node --import tsx scripts/check-task-filters.mts` / `node --env-file=.env.local --import tsx scripts/check-task-filters.mts --db` — the task-filter self-check (one script, two rigor levels — the payroll pair's shape collapsed into one file). Without `--db` it is pure and env-free: it pins the URL contract (`parseTaskListParams` ↔ `taskListQs` round-trips, legacy `?due=`/`?month=` aliases, the phantom-date rejection) and the date-facet window resolver across all five fields × every preset in **both Vancouver and Tehran**, including the regression that motivated it: bare `drange=today` must window `COALESCE(due_date, start_date)`, because quick-add's default task shape is start-only and a due-only "Today" hid it. With `--db` it also seeds `ZZ-CHECK`-prefixed fixtures into Neon (swept in a `finally`, every assertion query scoped by `q=ZZ-CHECK`), runs the **real** `tasksWhere` (importable from the guard-free `src/db/taskPredicates.ts` — the reason that module exists) for every view × filter × zone combination, and compares row sets against an independent oracle. It also pins the **search reach** — `q` spans title, notes, `assignee_name`, the client's name (plus the `'Perseus'` literal the Client column shows for a null client), the category's name and any tag's name, so those cases scope by fixture **id** rather than by `q=ZZ-CHECK` (they search by something other than the title on purpose). It also pins the **tag facet**: the `?tag=` slug list sorted/deduped/capped (the sort is load-bearing — `task_views` compares canonical query strings by equality), the exclusive `tag=none` untagged sentinel, `tagmode=all` dropped when it would mean nothing, and, under `--db`, that `all` returns a strictly narrower set than `any` against seeded links. **Run it after touching `src/lib/taskFilters.ts`, `src/db/taskPredicates.ts`, or the task list/count queries** — a filter that silently returns the wrong rows looks exactly like an empty day.
- `node --import tsx scripts/check-task-tags.mts` — the task-tag scope self-check (no DB, no env). `task_tag_categories` encodes "offered everywhere" as an EMPTY scope, which means the schema can say *everywhere* but not *nowhere* — so this pins the two refusals `planCategoryTagOffers` (a pure leaf in `taskTagFields.ts`, the `taskPredicates.ts` precedent) exists to make: a global tag can't be ticked into a single category (it would be demoted, and no category added later would pick it up), and a tag can't be dropped from its LAST category (its scope would empty and it would reappear under every category instead of none). It also pins `tagInScope` / `splitTagsForCategory` — the same rule read from the picker's end — including the untouched-archived and "Other" cases. **Run it after touching `planCategoryTagOffers` or `setCategoryTagOffers`** — neither misfire throws, neither shows in a filter test, and both surface only as "why is Reels suddenly offered under SEO?".
- `node --import tsx scripts/check-calendar.mts` — the calendar self-check (same one-off `scripts/` shape as the payroll and activity-log ones; needs no DB and no env). Pins the **two-clocks contract** in `src/lib/calendar.ts`: the original bug (22:15Z on Aug 19 is Aug 20 in Tehran and Aug 19 in Vancouver), day-start round trips across both DST transitions, that Vancouver still observes DST and **Tehran does not** (so a tzdata change reinstating Iranian DST is caught here rather than by dates quietly moving), the accepted end-of-month edge, and that `resolveZone` never throws on junk. **Run it after touching `src/lib/calendar.ts`** — a regression there is silent: dates keep rendering, they are just the wrong day.
- `node --import tsx scripts/check-session-policy.mts` — the session-policy self-check (no DB, no env). Pins the three numbers in `src/lib/sessionPolicy.ts` as literals (24h idle, 5-minute refresh, 30-day ceiling), the `clampSessionExpiry` ceiling math at its boundaries, and `safeAdminReturnPath` — the open-redirect guard behind the login page's `?next=` — against protocol-relative, backslash, control-character, fragment, and login-loop inputs. **Run it after touching `src/lib/sessionPolicy.ts` or the `session` block / session hooks in `src/lib/auth.ts`** — a "harmless" edit to a number changes how long a stolen cookie works, and a loosened guard is an open redirect, and neither fails anything else.
- `node --import tsx scripts/check-careers.mts` — the careers self-check (no DB, no env). Pins the copy composers in `src/lib/careerFields.ts` (the hero paragraph, the ≤160-character meta description with its "and N more" fold, both FAQ answers, for 0/1/4/8 open roles), `formatPay`, `roleLabel`'s fallback order, the public fingerprint that gates IndexNow pings, and the policy refinements in `src/lib/careersSchema.ts` — above all that a listing cannot be `open` without a pay range and a posted date. **Run it after touching `careerFields.ts` or `careersSchema.ts`** — a composer that silently drops a role name rewrites the page's meta description and FAQ for every visitor, and a loosened refinement is a BC Pay Transparency Act miss that nothing else catches.

There is no test runner configured in this repo. **`next build` runs only TypeScript, not ESLint** — lint and type-check are two separate gates: `npm run lint` for ESLint, `npm run build` for types. There is no standalone `tsc` script.

ESLint notes: `public/**` is globally ignored (static assets + the hand-written `sw.js`, which uses service-worker globals). `eslint-plugin-react-hooks` v6 (bundled with Next 16) adds React-Compiler-readiness rules; the ones that flag working, intentional patterns in the existing motion/3D code — `set-state-in-effect`, `purity`, `static-components`, `immutability` — are deliberately set to `warn` in `eslint.config.mjs`. Don't "fix" those warnings by refactoring working code, and keep the classic `rules-of-hooks`/`exhaustive-deps` at error level.

## Architecture

Next.js 16 / React 19 site using the **App Router** with TypeScript (Turbopack is the default bundler for both `dev` and `build`), split into two route groups: **`(marketing)`** — the public site — and **`(admin)`** — the team dashboard. Route groups don't affect URLs, but file paths carry the group segment. All routes are server components by default; interactive pieces opt in with `'use client'`. Services/blog content is code-defined — `src/constants/*` and `src/content/blogs/**/*.mdx`, **no CMS** — while the portfolio (case studies + clients) lives in Neon Postgres, managed from `/admin` (see "Services & projects content model").

Mutations are server actions only. The public site has two: the `submitContact` server action (`src/app/(marketing)/contact/actions.ts`) validates with Zod (`src/lib/contactSchema.ts`), writes to **Neon Postgres via Drizzle** (`src/db/schema.ts` + `src/db/index.ts`, `server-only`-guarded), uploads career-application resumes to **Vercel Blob**, and emails notifications via **Resend**; and the blog's "was this article helpful?" vote (`src/app/(marketing)/blogs/[blog]/actions.ts`) upserts into `article_feedback` (tallies at `/admin/feedback`). The `(admin)` dashboard — Better Auth email+password + passkeys, public sign-up disabled, optimistic session-cookie gate in `src/proxy.ts` with real DB-validated sessions in `(protected)/layout.tsx` — manages the team's task board, per-client monthly reports, the leaderboard, tickets, the contact/careers inboxes, portfolio projects/clients, payroll, users & per-area access, the activity log, and feedback tallies through server actions under `(protected)/_actions/`; private files (résumés, avatars, ticket screenshots) stream through authenticated route handlers. All email goes through `src/lib/mail.ts` (`sendMail` + the `NOTIFY_FROM`/`AUTH_EMAIL_FROM` constants — the one Resend door; plain-text only, no template layer). `/api` routes: the Better Auth handler at `/api/auth/[...all]`, plus **four** `CRON_SECRET`-gated cron endpoints (`weekly-digest`, `recurring-tasks`, `due-reminders`, `payroll-nudge`) invoked by the `crons` in `vercel.json`, the repo's only Vercel config file (exact schedules in the Route map below — they are staggered on purpose, not all at one hour). Server secrets (`DATABASE_URL`, `RESEND_API_KEY`, `BLOB_READ_WRITE_TOKEN`, `PUBLIC_BLOB_READ_WRITE_TOKEN`, `BETTER_AUTH_SECRET`, `GOOGLE_PLACES_API_KEY`, `CRON_SECRET`) are never `NEXT_PUBLIC_*`.

### Contact form (unified project + careers)

`/contact` renders `ContactHub` (tabs: "Inquiries" / "Join the team") behind the SSR-kept `dynamic()` wrapper `ContactHubLazy` — ContactHub is the only client importer of zod, so that weight stays in the contact async chunk. The server page derives slim props: `serviceGroups` (29-service picker projection from `CATEGORIES`) and `roles` (the `open` listings from `getOpenRoles()` in `src/lib/careersStore.ts` + `GENERAL_APPLICATION` from `src/lib/careerFields.ts`), plus `initialTab`/`initialRole` from `await searchParams` (`?tab=careers&role=<slug>` deep links pushed by the careers page's Apply cards — crawl-silent `NavButton`s, not `<a>`s; see "Conventions to respect" — this makes `/contact` request-time rendered, same trade as `/blogs`). Idempotency: the client generates one `client_id` per fill session (invalidated on any edit, so an *edited* resubmission is a new submission while an unchanged retry dedups); `contact_submissions.client_id` is unique and the insert is `onConflictDoNothing`, so outbox replays/retries can't double-write or double-email. Roles: `submitContact` resolves the slug through `getRoleTitleMap()` (every listing, any status, + General application) and stamps the title onto `contact_submissions.role_title` — a snapshot, because listings get deleted from /admin/careers and an application must outlive the posting it answered. An unknown slug is **stored raw, never rejected** (the same degrade policy as services and referral sources): a validation rejection makes the offline outbox permanently drop the queued record, so a role delisted between queue time and flush time would silently lose a candidate. Spam: honeypot (`pcs_extra` — the name/label deliberately avoid browser-autofill vocabulary like "organization", which would get autofilled for real visitors) + minimum-fill-time; flagged submissions are **stored with `status: 'spam'`** (no email) rather than dropped, so false positives are recoverable. Resume uploads: PDF ≤4MB (Vercel's hard body cap is 4.5MB — `experimental.serverActions.bodySizeLimit` in `next.config.ts`), magic-byte sniffed on both client and server, stored **private** in Blob (`resume_path` column); the notification email carries the PDF as an attachment, and /admin will stream it later via `get(pathname, { access: 'private' })`. There is no code-level rate limit — if abuse appears, add a Vercel WAF rate-limit rule on POSTs to `/contact` (zero code) before reaching for a Redis-backed limiter.

### Path aliases

`@/*` resolves to `src/*` (see `tsconfig.json`). Always import via `@/...`. Shared components live in `src/components`, surfaced to pages through the `src/components/index.ts` barrel — see "Component organization" for the barrel rules.

### Route map

Public routes live under `src/app/(marketing)/`, the dashboard under `src/app/(admin)/`; `src/proxy.ts` (Next 16's successor to `middleware.ts`) bounces sessionless `/admin` requests to `/admin/login` (cookie check only — the real authorization boundary is the protected layout):

- `/` — `app/(marketing)/page.tsx`
- `/about`, `/contact`, `/contact/careers`, `/frequently-asked-questions`, `/privacy-policy`, `/terms-of-service`, `/license`
- `/services` (hub) → `/services/[category]` → `/services/[category]/[service]` — category landing + service-detail pages, **statically generated**: the `[category]` route's `generateStaticParams()` enumerates `Object.keys(CATEGORIES)` and the `[service]` route's enumerates `allServiceDetailParams()`, both from `src/constants/services.ts`; unknown slugs `notFound()`. (`/services/websites` is now `category=websites` through the dynamic route — there is no static websites page or `Websites/` component dir anymore.)
- `/projects` (hub) → `/projects/[category]` → `/projects/[category]/[project]` — per-category case-study index enumerated from `Object.keys(PROJECT_CATEGORIES)` (`src/constants/projects.ts`). **Unlike `/blogs`, these are real routes**, but in-category filtering (`?service=` / `?industry=` / `?location=`) and pagination (`?page=N`) are URL state canonicalised back to the unsuffixed `/projects/<category>` — and every filtered-view href is emitted as a crawl-silent `NavButton`, never an `<a>`; only pagination stays a real anchor (see "Conventions to respect"). Note: despite `generateStaticParams()`, the category pages render **at request time** — both the page and `generateMetadata` read `searchParams` for the `?page=N` suffixed titles, which opts the route out of static prerendering. This is a deliberate trade (same as `/blogs`): paginated views keep unique metadata for duplicate-meta audits. The `[project]` detail pages are DB-driven (`getProjectDetail` / `listProjectDetailParams` in `src/lib/projectsStore.ts`); only case studies flagged `hasDetail` get deep links.
- `/blogs` — listing page; **URL state, not category landing pages.** Filters use `?category=<slug>` and `?page=N` on the same route. Each filter combination gets unique `<title>` and `<meta description>` via `CATEGORY_META` + pagination suffix in `generateMetadata` (so duplicate-meta audits stay clean). (On-page blog search was removed; a sitewide navbar search is planned separately.)
- `/blogs/[blog]` — post detail, statically generated via `generateStaticParams()` reading `blogPosts`
- `/blogs/authors`, `/blogs/authors/[author]`
- `/offline` — service-worker navigation fallback (see Offline / PWA below); `noindex`, excluded from the sitemap.
- `/admin` — the protected dashboard (`noindex`, excluded from the sitemap): inquiries & applications inboxes (status triage, CSV exports, private résumé streaming), tickets (with screenshot streaming), projects & clients portfolio management, users & per-area access, feedback tallies, payroll, the activity log, and profile (avatars stream via `/admin/avatars/[userId]`). Only `/admin/login` and `/admin/reset-password` are reachable without a session. **Roles are three tiers** — `owner` (Saman, exactly one, every area implicitly) > `superadmin` (role privileges — /admin/users, ticket triage — plus **stored** area grants; the owner edits those grants and can also reset a superadmin's password or delete the account) > `member` (stored grants only); role changes are SQL/migration-only (migration 0024 seeded them) and the owner row refuses reset/delete from everyone, so a total lockout is structurally impossible. Every admin surface is its own grantable area (`src/lib/adminAreas.ts`); `payroll` and `logs` are `SENSITIVE_AREAS` — their chips render for anyone on /admin/users but only the owner may flip them (server-enforced delta check in `_actions/users.ts`), and `DEFAULT_AREAS` is an explicit curated list (excludes `reports`, `payroll`, `logs`) so a new area can never silently pre-tick.
- `/admin/careers` — the job openings behind `/contact/careers`, `requireArea('careers')` (Website group, beside Projects/Clients). **One page, dialog editors** — the `/admin/clients` model: a roster grouped by category with status chips and a quick status menu per row, `OpeningDialog` for create/edit/delete, `CategoriesDialog` for the headings; `?role=<id>` opens that listing's dialog. No badge on the rail ("N open roles" is a readout, not a queue). Full rules under "Services, projects & careers content model".
- `/admin/tasks` — the team's work log, `requireArea('tasks')`. **One URL, two views**: the board, and `?view=digest` for a read-only last-7-days roll-up — the page component is a thin shell that branches on the param (the `/admin/inquiries` model), so don't split it into a second route. `/admin/tasks/export` streams CSV. Full rules under "Tasks" below.
- `/admin/leaderboard` — the team's monthly standing, `requireArea('leaderboard')`. Its own grant, **split from `tasks`** so the work log and the scoreboard can be handed out separately (both are in `DEFAULT_AREAS`, so new accounts get the pair). `?month=YYYY-MM` and `?range=month|d30|all`.
- `/admin/reports` (client roster + studio strip + 12-month trend) · `/admin/reports/internal` (the null-client Perseus month) · `/admin/reports/[slug]` · `/admin/reports/[slug]/print` (A4 sheet) · `/admin/reports/[slug]/export` (CSV) — all `requireArea('reports')`, an area deliberately **not** in `DEFAULT_AREAS` because it is the client-facing numbers. `internal` is a static segment on purpose: Next's route precedence shadows `[slug]`, so no client can ever claim the URL (client creation also reserves the slug). Full rules under "Reports & leaderboard" below.
- `/admin/tickets` (+ `/new`, `/[id]`, `/[id]/screenshot`) — internal issues the team files against itself. Holding the `tickets` area lets you file and read **your own**; **triage is `requireSuperadmin()`** and is the only door that changes status. Full rules under "Tickets" below.
- `/admin/presence` — a POST-only heartbeat route handler (no body, no user id: it can only stamp the caller's own `user.last_seen_at`, migration 0025). **A route handler and not a server action on purpose** — an action returns an RSC payload, so a 90-second heartbeat would re-render the whole dashboard on a timer. Read only on `/admin/users` ("Online" / "Last seen …"); the constants and the `presenceFrom()` formatter live in the pure leaf `src/lib/presence.ts`, and `getAccessProfile()` already carries `lastSeenAt`, so the write throttle costs no extra query.
- `/admin/avatars/[userId]` — authenticated avatar streaming out of the private Blob store. `user.image` is user-writable through Better Auth, so `src/lib/avatarPaths.ts` is a **security predicate**, not a formatting helper: only pathnames matching its allowlisted shape are ever fetched.
- `/admin/logs` — the site-wide audit trail, `requireArea('logs')` (a sensitive, owner-granted area — safe to widen beyond superadmins because `activity_log` is payload-free by construction). The timeline itself is server-rendered and day-grouped; the filter bar is the one client island, on the `InboxFilterBar` recipe (debounced search, chips that apply on pick). It shipped as a zero-JS GET `<form>` with a submit button and members read that as broken — every other bar in the dashboard applies on change. See "Logging & activity" below.
- `/admin/payroll` (month screen) · `/admin/payroll/members` (roster) · `/admin/payroll/[memberId]` · `/admin/payroll/export` (CSV, `private, no-store`) — all `requirePayrollAdmin()`. `/admin/my-pay` — the member's own history, `requireOwnPayroll()`. `/admin/payroll/payslip/[memberId]/[month]` — shared, `requirePayrollAccess()`. See "Payroll" below.
- `/share/reports/[token]` — the tokenized public read-only client-month report (`report_shares` table, minted/revoked from `/admin/reports/[slug]`). Outside both route groups (document shell only), `force-dynamic` so revocation bites immediately, `noindex` via its own metadata (the root layout sets no robots default), bypassed by `public/sw.js`, never in the sitemap; `robots.txt` deliberately untouched (a crawler must be able to fetch the page to see the noindex).
- `/api/auth/[...all]` — the Better Auth handler. Plus **four** cron endpoints (Bearer `CRON_SECRET` → 401, `force-dynamic`, schedules in `vercel.json`), each of which also writes a `logSystemActivity` row with `area: 'cron'` — a cron leaves no other trace, so an activity row per run is what makes the **absence** of a run visible on `/admin/logs`: **`/api/cron/recurring-tasks`** (`0 14 * * *`) mints today's tasks from active templates — deliberately an hour **ahead** of due-reminders so anything minted today is already in that email, and it also carries the 365-day activity-log retention sweep, which must run *before* the "nothing due" early return or the "Kept for 365 days" claim on `/admin/logs` becomes false; **`/api/cron/weekly-digest`** (`0 15 * * 1`) the Monday digest over the previous Mon–Sun **studio** week — the exact week, not a rolling 7 days (see "Two clocks, one door"); **`/api/cron/due-reminders`** (`0 15 * * *`) one email per member with overdue or due-today work, bucketed in **each member's own** timezone; **`/api/cron/payroll-nudge`** (`0 16 * * *`) the daily chase for payments nobody has confirmed receiving (once per payment, guarded by `payroll_payments.nudged_at`). All send through `src/lib/mail.ts`.
- Permanent redirects (in `next.config.ts`): `/visual-production → /projects`, `/authors → /blogs/authors`, `/sitemap` & `/sitemaps → /sitemap.xml`, plus legacy URLs remapped onto the current route shape — old flat service paths (`/web-development`, `/services/google-ads`, `/services/social-media-management`) now resolve to `/services/<category>/<service>`, several retired blog slugs redirect to their replacements, and renamed blog-category filter values (`?category=videography-and-photography` → `production`, `website` → `websites`) are query-matched redirects on `/blogs`.
- Response headers (also `next.config.ts` `headers()`): a baseline security set on every route — `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `X-Frame-Options: SAMEORIGIN`, `Permissions-Policy`, HSTS without `preload` — deliberately **no CSP yet** (a real one needs a nonce strategy for GTM/GA/Clarity + the inline JSON-LD blocks; tracked as a follow-up). Plus `X-Robots-Tag: noindex` on `/_next/static/:path*` (so `?dpl=`-suffixed deploy asset URLs can't be indexed as pages), `text/xsl` MIME for `public/sitemap.xsl` (the human-readable sitemap stylesheet) and `Cache-Control: immutable` for `/images/*`.

### Services, projects & careers content model

Services are **code-defined content** (not MDX); projects split between code-defined category chrome and **database-backed case studies**; careers (the job openings on `/contact/careers`) are **fully database-backed**. Services and projects share the same five category slugs: `production`, `websites`, `digital-marketing`, `social`, `branding`.

- **Services** — `src/constants/services.ts` is the single (very large) source of truth. `CATEGORIES` holds the five category-landing records; the per-category service-detail records live in `PRODUCTION_SERVICES` / `WEBSITE_SERVICES` / `MARKETING_SERVICES` (the `digital-marketing` category) / `SOCIAL_SERVICES` / `BRANDING_SERVICES`. `getServiceDetail(category, service)` resolves a detail page; `allServiceDetailParams()` feeds the `[service]` route's `generateStaticParams()`. Every record carries its own `seo` block (`title`/`description`/`canonicalPath`) consumed by `generateMetadata`. Section media comes from a registry at `src/components/Services/visuals/` via `getServiceVisual(category, slug)` → `ServiceVisualCard` (bespoke code/SVG art — distinct from the photographic category cover slots).
- **Projects** — split across two sources. `src/constants/projects.ts` is **chrome only**: `PROJECT_CATEGORIES` holds each category's hero/comingSoon/proof/FAQ/CTA/SEO copy, and its key order is the site-wide category ORDER. The case-study cards, clients, and detail media live in Postgres (`clients` / `projects` / `project_media`, managed via /admin) and are read through the cached accessors in `src/lib/projectsStore.ts` (`getCategoryProjects`, `getServiceProjects`, `getLatestAcrossCategories`, `getSummariesByCategory`, `getCategoryTallies`, `getProjectSummary`, …) — all `async`, `unstable_cache`-wrapped, and tag-invalidated (`updateTag` in the /admin actions), so content edits go live **without a redeploy**. Don't reintroduce project card data as module-scope constants — module scope evaluates before any async read can happen.
- **Careers** — `job_categories` + `job_openings` in Postgres (migration 0026), managed from `/admin/careers` (the `careers` area, in `DEFAULT_AREAS`), read through `src/lib/careersStore.ts` (`getCareersSnapshot`, `getOpenRoles`, `getRoleTitleMap`, `allListedRemote`, `latestCareersDate` — `unstable_cache` under `CAREERS_TAG`, `updateTag` in `_actions/careers.ts`). Three states: `open` (the "Available" card, a contact-form option, a JobPosting node), `filled` (kept on the page as "Position filled" — listings are never hidden when a seat closes), `draft` (admin-only). Delete is a hard delete; applications keep the `role_title` snapshot. **Two slugs are immutable after creation** — a listing's (it is the `?role=` deep-link payload and the value stored on applications) and a category's (the filter value) — the actions refuse a change rather than silently keeping the old one. **An `open` listing must carry a pay range and a posted date**, enforced by `careersSchema.ts` on both doors (the dialog and the roster's quick flip): BC's Pay Transparency Act requires expected pay on any publicly advertised posting a BC resident could fill, and Google's JobPosting requires `datePosted`; `validThrough` past its day drops the JSON-LD node (a stale-open posting is a policy violation) while the card stays. Advertised pay is a **public display range in whole CAD dollars** (`integer pay_min/pay_max`), not ledger money — `careerFields.formatPay` is its one formatter and it never touches `payrollAmounts.ts`. **The open roles are spelled into prose in exactly one place**: the composers in `src/lib/careerFields.ts` (`composeHiringIntro` → the hero paragraph, `composeHiringMeta` → the ≤160-character meta/OG description, `composeHiringFaq` / `composeRemoteFaq` → the two FAQ answers) — never hand-write a sentence that names or counts the open roles, it will be stale by the next hire. Categories carry an icon key from the fixed `JOB_CATEGORY_ICON_KEYS` vocabulary (`src/lib/jobCategoryIcons.ts` maps it to a lucide glyph); an unknown key renders the briefcase.

### Payroll

Monthly team pay, and the most privacy-sensitive surface in the app. Three compensation shapes coexist and **none is special-cased**: a payment stores an *anchor* currency+amount (what the agreement fixes) and a *paid* currency+amount (what landed), so everything collapses to `paid = anchor × rate` with `rate = 1` when they match — CAD-anchored paid in toman, toman-anchored paid in toman, and CAD paid in CAD are one row shape.

- **Money is integer minor units, never `numeric`/float** (the `estimatedMinutes` rule). CAD is `integer` cents; toman (`IRT`, the unit every invoice uses — rial appears nowhere) is `bigint({ mode: 'number' })`, because a member-year of toman overflows `int4` and `mode: 'bigint'` isn't JSON-serializable into an RSC prop. The rate is `bigint` `rate_micro` = toman-per-CAD × 1e6. **`src/lib/payrollAmounts.ts` is the single conversion door** — nothing else parses, formats, converts, prorates, or computes growth.
- **The rate belongs to a payment, not a month.** The exchange quotes each wire separately (June 2026 spanned 123,300.00–123,376.06 toman/CAD across four lines), so `payroll_runs.rate_micro` is the month's canonical figure — it pre-fills lines and drives the trend — and `payroll_payments.rate_micro` overrides it per wire. Two rounding granularities, both measured off the invoices: delivery rounds to 5,000 toman, proration to 10,000.
- **Computed amounts are suggestions.** `anchor × rate` pre-fills the cell; the admin overrides it to match the invoice exactly. The system records what happened, it doesn't dictate it.
- **The wire fee is company cost, outside anybody's salary** — never in a salary calculation, never shown to a member. The Donya invoice PDF is deliberately **never stored**: one page lists everyone's pay, so it can have no member-facing surface. Only its reference number is kept.
- **Standing salary is effective-dated** (`payroll_terms`, no `effective_to` — the next row supersedes, so gaps and overlaps are impossible). A month resolves to the newest term effective on or before its **last** day, then prorates by join/end dates: that is the only reading that reproduces Mahdi NP's July (35,000,000 × 13/31 → 14,680,000).
- **Status and amounts move through separate doors** (the tasks convention). No edit action accepts a status; no status action accepts an amount. Every transition is re-checked server-side by `checkTransition()` in `src/lib/payrollStatus.ts`, whatever the UI offered.
- **Two audiences, two projections — the split IS the privacy mechanism.** `src/db/payrollQueries.ts` exposes `admin*` (every column, every member) and `own*` (one member, scoped by a session-derived id matched in SQL, projected so `cost_cad_cents`, `fee_cad_cents`, `wire_ref`, `admin_note`, and member `notes` are never selected). A column that was never selected can't leak through a spread or an RSC payload. **Never widen an `own*` projection to reuse it for an admin screen, and never reach for an `admin*` query on a member path** — that includes the member row and the term history, not just payments: `ownGetMember` / `ownListTerms` exist so the admin's private notes about a person and the name of whoever set their salary are never *fetched* onto their own page, rather than merely left unread at the render site. Members also never see a `draft` line, and a toman-anchored member is never shown the rate (it played no part in their figure and would hand them the company's cost basis).
- **Access is three named gates** in `src/lib/adminAccess.ts`: `requirePayrollAdmin()` (the owner-granted `'payroll'` sensitive area — the named gate paid off: moving off "every superadmin" was one edit, not a sweep), `requireOwnPayroll()`, and `requirePayrollAccess(memberId)` for the shared payslip. The payroll-admin rule itself lives once, in `isPayrollAdmin(profile)` — `requirePayrollAccess` serves both audiences so it must *ask* rather than enforce, and re-deriving the answer inline there would quietly survive any future change to who counts as a payroll admin.
- **A line can't be sent until its cost is knowable.** `costInCadCents` returns null without a rate and every write path coerces that to `0` — so "cost unknown" would land in the one summable column as "cost nothing". `sendPayrollRun` therefore refuses any draft that still needs a rate, and a line needs one unless it is CAD-anchored *and* CAD-paid: the rate states the delivered amount when the currencies differ, and the company's CAD cost whenever the anchor isn't already CAD. A toman-anchored member (IRT→IRT) trips only the second half — miss it and `cost_cad_cents` freezes at 0 forever, since `repriceDrafts` only touches drafts. `getAccessProfile()` resolves `payrollMemberId`/`payrollSelf` via a `leftJoin` on its existing PK read (free on neon-http) — so **migration 0020 must be applied before this code deploys**, or every admin render breaks. Payroll is a grantable but **sensitive** area (`SENSITIVE_AREAS` in `src/lib/adminAreas.ts`): only the owner can flip its chip, it is never in the explicit `DEFAULT_AREAS`, and it contributes **no sidebar badge** (the layout computes tallies for everyone and masks after, which for payroll would mean counting other people's rows on a member's render).
- Whether a member sees their own pay is `payroll_members.self_view_enabled`, toggled from the roster — that's the switch to reach for, not an area grant. A member record's `user_id` is nullable + `ON DELETE SET NULL` with a `display_name` snapshot (the `tasks.assigneeId` precedent): pay history has to outlive an offboarded account.
- Emails (send notice, flag alert, nudge) carry **no figures**, by design. Audit rows go to `payroll_events` behind `after()`, like `logTaskEvents`.
- **`/admin/my-pay` is written for the member, not for payroll.** It is `wide` like every other dashboard route: hero (amount + status + confirm/flag) beside a 12-month column chart, three tiles (year, all time, salary now), then the growth split beside the salary step chart, the year-filtered month list, and *last* the working behind the figure. The mechanics are demoted, never removed — the standing ruling is that a member sees their whole own line, so the rate and the agreed figure stay on the page, just below the money. Labels are deliberately plain ("your agreed salary", "rate used this month"); "anchor" never appears on a member surface. Each month row links to that month's payslip, which re-derives the audience from the session, so the member id in the URL grants nothing.
- **The charts are hand-rolled and stay that way.** `PayrollCharts.tsx` (`PayColumns`, `SalarySteps`) are server components whose readouts are CSS `group-hover`, so they add nothing to the client bundle; `payrollData.ts` feeds them pre-formatted strings plus 0–100 percentages. There is no chart library in this repo and **none is wanted** — see the note atop `PayrollSections.tsx`. Column heights and the dashed average share one positioning context so they cannot drift off a common axis, and the salary step dots are positioned HTML over the SVG because `preserveAspectRatio="none"` would stretch `<circle>`s into ellipses. `/admin/payroll/[memberId]` renders the same two charts from the same builders, so an admin and a member discuss one picture. The printed payslip keeps `PayrollSections.tsx` — nothing in `PayrollCharts.tsx` is print-safe.

### Tasks

The team's shared work log — it replaced the Telegram daily-digest thread — and the source every report and the leaderboard reads from. Built across migrations 0010–0019 (`tasks`, `task_categories`, `task_events`, `task_templates`, `task_views`, plus `clients.retainer_minutes`).

- **One URL, two views.** `/admin/tasks` is the board; `?view=digest` is a read-only last-7-days roll-up. The page component is a thin shell that branches on the param (the `/admin/inquiries` model) — don't promote the digest to its own route.
- **Tags are an optional second label, scoped per category** (migration 0027: `task_tags` + `task_tag_categories` + `task_tag_links`). They replaced a dimension the studio had been writing into task TITLES ("… TH", "… Reels", "Vela 21st Street Vt", "Belcanto OP 1 (Eslahie)"). Five rules hold it together. **A tag belongs to one of three fixed groups** — `format` (the shape of the output) / `content` (what the thing is) / `workflow` (the state of the work) — and that enum drives BOTH the picker's sections and the chip colour, so there is no per-tag colour picker and the board can't drift into confetti; the tones deliberately avoid `rose` (overdue) and `amber` (due today / over estimate). **Scope gates the picker, never the stored value**: `taskTagCategories` says which categories OFFER a tag (zero rows = global, which is how the workflow tags reach everywhere), but `setTaskTags` accepts an out-of-scope tag rather than rejecting it — a task's category can change after tagging, and enforcement would silently drop a member's labels; out-of-scope tags surface in the picker's trailing "Other" section. **Slugs are immutable and archive is the retirement path**, exactly as for categories: filter URLs and saved views carry the slug, `deleteTaskTag` refuses with a count while any task carries it, and the `restrict` FK on `task_tag_links.tag_id` is the race backstop. **Tags move through their own door** — `setTaskTags` / `setTasksTagsBulk` (add/remove, NEVER replace: one "set tags" across a mixed selection would wipe what each row already carried), plus optional `tagIds` on create/update; `patchTask` and `bulkPatchTasks` are structurally unable to touch them, the same rule status follows. Vocabulary CRUD and assignment are both `requireArea('tasks')` — the people doing the tagging are the ones who know what label is missing, and the vocabulary is guarded by its domain rules (delete refuses with a count, archive is the retirement path, slugs are immutable) rather than by a role. **The manage dialog is CATEGORY-first**: a category is a pane, its tags are a checklist, and the pane saves ONCE through `setCategoryTagOffers` — which writes a delta over one `category_id` and therefore must never reach for `writeTagScope` (that replaces a whole tag's scope and would wipe every other category's rows). Two toggles are refused there and on the server, both because empty scope means *everywhere* so "offered nowhere" is inexpressible: a global tag can't be ticked into one category, and a tag can't be dropped from its LAST category. The tag-major list survives as the "All tags" pane, where rename/regroup/archive/delete belong. **Reads never N+1**: `tagsForTasks` in `taskQueries.ts` fetches a whole page's tags in ONE query and `withTags` folds them in JS. The filter facet is `?tag=a,b` (+ `?tagmode=all`, + the exclusive `tag=none` untagged sentinel) and rides **EXISTS subqueries, never a join**, so `count(*) over ()` and the join-free tab-badge COUNT keep working.
- **Tags are internal, and that is structural rather than a convention.** `TaskListRow` carries no tags; `TaskListRowWithTags` does, and `listClientMonthTasks` — the reader behind the client month report, its print sheet and the `/share` link — returns the base type, so tags *cannot* reach a client surface. Likewise `TagMixStrip` (the "What shipped" readout on the digest and `/admin/reports/internal`) takes no `tone` prop, so like `InternalKpiPanel` it has no print variant to render into. The `tags` CSV column lives in `tasksColumns` only, never `SHARED_COLUMNS`, which the report export also consumes. Whether a client-facing deliverable mix is wanted is its own decision, deferred on purpose (2026-08-24) — it needs its own copy pass, and workflow tags like "Revision" would have to be excluded.
- **Every duration in the database is an integer number of minutes, and `src/lib/taskFields.ts` is the only module that may do the x60 math.** `parseHoursToMinutes` / `formatMinutes` / `composeMinutes` / `splitMinutes` live there and the rule extends to CSV exports. Display is always `2h 50m`, never `2.83 h`; the CSVs additionally carry decimal-hours columns so spreadsheets can sum them. `WORKDAY_MINUTES = 480` — a month's delivery divided by 24 would quietly understate itself on a client-facing PDF.
- **Status and edits move through separate doors** (the same rule payroll cites). `setTaskStatus` is the one status door and `setTasksStatusBulk` the one bulk status door; `patchTask` and `bulkPatchTasks` are **structurally unable** to touch `status`/`completedAt` because their schemas have no such keys. Keep it that way — it is what stops the `completedAt` contract being bypassed from an inline cell edit.
- **The `completedAt` contract is a reporting contract.** Moving to `done` *always freshly stamps* `completedAt`, so re-completing a reopened task migrates it into the new month; **there is no month lock in v1 and that was a deliberate call, not an oversight.** Leaving `done` nulls `completedAt` but keeps `actualMinutes` — inert (reports only read `status='done'`) and the best prefill for the next completion. `needs_approval` means the work is finished and awaiting client sign-off: `actualMinutes` is confirmed but `completedAt` is still null, so **a task enters a report only once it is marked done.** Hours on completion coalesce `provided ?? actual ?? estimate`. `setTasksStatusBulk` adds `status <> target` to its WHERE so a mixed-selection "mark done" can never restamp an already-done task into a new month.
- **Recurrence is idempotent through the database, never through a read-then-write check** (neon-http has no transactions). `recurring-tasks` mints one task per active template whose schedule lands on today's `STUDIO_TZ` date, keyed `(template_id, template_run_key)` under a partial unique index with `onConflictDoNothing`. That index's `where: isNotNull(tasks.templateId)` predicate is **mandatory and must stay byte-identical to the index** — without it Postgres raises 42P10 and the whole mint throws instead of skipping the duplicate. A monthly template's `repeat_day` is capped **1–28** so no month silently skips February.
- **Whole-team visibility is the design.** Anyone holding the `tasks` grant may edit any task; there are no ownership checks and `taskQueries.ts` never scopes by viewer — this is a trusted seven-person studio. The single exception is comment deletion (own comments only, unless superadmin), and that check **rides the WHERE clause** rather than a read-then-check, so it can't race.
- **Category vocabulary is archived, never deleted**, and **slugs are immutable after creation** — filter URLs and report history carry them. `deleteTaskCategory` refuses while any task *or* template still references it (it counts both and says which); the `restrict` FK is the race backstop.
- **No cache tags.** Tasks have no public reader, so mutations only call `invalidateTasks()` (`revalidatePath('/admin', 'layout')`). The one exception is `quickCreateClient`, which also fires `updateTag(CLIENTS_TAG)` because it writes a `clients` row. The fresh tree rides back on the action's own POST response, so **a client success path must never follow up with `router.refresh()`** — that is roughly ten extra Neon round trips for a render you already have.
- **Deletion policy assumes people leave.** Every FK-to-user is `SET NULL` beside a NOT NULL name snapshot (`assignee_name`, `created_by_name`, `actor_name`, `task_title`) so offboarding an account never breaks last month's report; `tasks.client_id` is `restrict` (billable history must be untangled on purpose); and `task_events.task_id` is **`SET NULL`, not cascade** — a hard delete is the one irreversible act here, so its history has to outlive it, which is why `kind='deleted'` rows are born orphaned.
- `src/lib/taskFilters.ts` is a zero-dependency URL contract: canonical param order, defaults dropped from the URL, and one date facet (`dfield` over date/due/start/completed/created x `drange` presets or a literal `YYYY-MM`) driving menu, trigger label, and window resolver from a single predicate. `group` is a display preference, never a filter, and survives "Clear filters". This module never picks a timezone of its own.
- **The date facet's working-tab default is the composite `date` field — `COALESCE(due_date, start_date)` — not `due`.** Quick-add's default task shape is start-only (start=today, no due), so a due-only default made the board's most common task invisible to every date preset: "Today" hid a task whose Dates column visibly read today (the 2026-08-21 fix). The composite is **point semantics, not range-overlap** (an ongoing "Aug 10 →" task does not appear under "Today" — Saman rejected the flood), and **Overdue stays strictly due-based everywhere** (a start-only task is ongoing, never overdue; the preset is refused on the Start field, where it would have meant "started before today"). The chip prefixes any non-default field ("Start · Today") so it never hides which column it windows. `tasksWhere` lives in the guard-free `src/db/taskPredicates.ts` (schema.ts precedent, never client-imported) precisely so `scripts/check-task-filters.mts --db` can prove the real WHERE against seeded fixtures.
- **Search reaches every field the row DISPLAYS, and every off-table source rides an EXISTS.** `q` spans title, notes, `assignee_name` (the on-table snapshot — free), the client's name, the category's name and any tag's name, plus the `'Perseus'` literal the Client column renders for a null client (there is no row to match it against, so the label is a literal in the predicate). The three joined sources are **correlated EXISTS subqueries, never joins** — the tag facet's reason exactly: `countTasksByStatus` selects from `tasks` alone and `listTasks` rides `count(*) over ()`, so a join would multiply rows and break both. Deliberately excluded: `created_by_name` and `deliverable_url` — a URL hit is invisible in the list and reads as a false positive. Because `tasksWhere` is the one door, the CSV export and the tab badges inherit the same reach for free.
- Server-formatted strings are the only date values that reach the client — `toRowData` stamps `dueState` server-side so the board never does date math in the browser.
- Migrations 0018 and 0019 are an added-then-dropped `tasks.status_changed_at`. **The column is gone**; the time-in-status badge it fed was removed. Don't reintroduce either.

### Reports & leaderboard

Per-client monthly reporting (`/admin/reports`, `requireArea('reports')`) plus the studio's own standing (`/admin/leaderboard`). Both read the task log through one definition of delivered work: **`status='done'` with `completedAt` inside the reader's month window, valued at `actualMinutes ?? estimatedMinutes`.** The dashboard, the print sheet, the share link, the digest and both crons all use it.

- **The client-facing / internal split is structural, not a convention to remember.** `InternalKpiPanel` and `ReportReadiness` take **no `tone` prop**, so having no print variant they *cannot* render onto the print page or the share link. Keep it that way rather than adding a `tone` and a condition. Likewise the vs-last-month deltas (`tiles.tasksDelta` / `hoursDelta`) are dashboard-only, while `hoursWorkdays`, `turnaroundLabel` and the highlights note do travel — they interpret, they don't compare. `MemberBars` gets `showShare` on the dashboard and the internal page but **not** on print or share: a per-member percentage split is a staffing detail the client didn't ask for. The report CSV omits `notes` because it travels with the PDF; the internal task CSV keeps them.
- `buildClientMonthReport` and friends (`src/components/Admin/reports/reportData.ts`) are shared **verbatim** between dashboard and print, so the PDF shows the exact strings the dashboard showed. Turnaround is a **median, not a mean**. `foldReadiness` deliberately does *not* check for missing hours — a check that can never fire is worse than no check, because its silence reads as a pass.
- **A share token is the whole credential** (`randomBytes(24)`, base64url). It is therefore **never logged** — `mintReportShare` writes an `activity_log` row carrying only `{ month, clientId }` — and `listActiveSharesForMonth` **deliberately does not select the token**, because the roster only needs "have I sent this yet?" and a live URL beside 88 client names is shoulder-surfing bait. Malformed, unknown and revoked tokens all 404 **identically**, so tokens can't be probed apart. The page is `force-dynamic` so revocation bites on the next request, sets its own `noindex` (**required** — the root layout declares no robots default), and is bypassed entirely by `public/sw.js`; `robots.txt` stays untouched on purpose, since a crawler has to be able to fetch the page to see the noindex.
- **The share page recomputes live; it is not a snapshot** — consistent with there being no month lock. Its one frozen value is the timezone: `report_shares.timezone` stamps the minting admin's zone so the client reads the same numbers the sender saw (a null, from pre-column links, falls back to `STUDIO_TZ`).
- **`/admin/reports/internal` is a static segment on purpose.** Next's route precedence shadows `[slug]`, so no client can claim the URL, and client creation additionally reserves the slug.
- **Export params are strict by house rule: an absent filter silently defaults like the list page, a present-but-malformed one is a 400** — a typo must never quietly widen a file someone will believe. An unknown client or category slug returns a header-only CSV, because absent data isn't an error. Both exports set `Cache-Control: private, no-store` and write their activity row **only on success** (logging first left permanent "Exported…" entries for files that never existed). **Export links are plain `<a>`, never `next/link`** — prefetch would fire the export.
- Print is two renderings of one component: theme-aware on screen, literal neutrals under `print:`, with `PRINT_SHEET_CSS` (`src/lib/printSheet.ts`) pinning the ground. See "Print surfaces" — `bg-white`/`text-black` are flip tokens and will betray you here.
- **The leaderboard ranks on task count alone.** Hours and on-time rate ride along as context and are **not blended into a score**, so there is no formula for anyone to distrust; hours only break an exact tie. Member identity is `assigneeId ?? name:<assigneeName>`, shared with MemberBars, the digest and both crons. Ranges are `month` (default), `d30` and `all` — rolling ranges exist because a board one month into tracking is nearly empty.
- **Champions, past champions and Most Improved are structurally absent in rolling mode**, because all three compare one calendar month to another; faking them would be worse than omitting them, and the month switcher hides itself to match. Every badge carries a hint with the row's own numbers so it stays checkable, and category champions need at least 3 tasks across at least 2 members — a single-member category title reads as manufactured praise. When a row cap bites, the **oldest** bucket is dropped and `dropTruncatedMonths` refuses to publish a partial month as a real one (it would crown the wrong champion); the page says so on screen rather than silently truncating.

### Tickets

Internal issues the team files against itself, which is why they sit under "Work" in the rail rather than "Inbox" (Inbox is strictly what arrives from outside).

- **The field is `severity` (`low | medium | high`), not priority, and tickets have no comment thread.** Don't document or build either from memory.
- **`area` is plain text, not an enum** — `TICKET_AREAS` is derived at runtime from `ADMIN_ROUTES`, so adding an admin route needs no migration, and `ticketAreaLabel()` falls back to the raw slug so a retired route's old tickets still render. `ticketAreasFor(access)` narrows the picker to areas the reporter can actually reach.
- **Two roles, two doors.** Holding the `tickets` area lets you file a ticket and read **your own** (all statuses mixed, no tabs). **Superadmin is triage** — it sees everything behind open/pending/closed tabs and is the only role that can change status. A foreign id returns `notFound()` rather than a 403, so ticket ids aren't enumerable. `searchTickets` never selects `screenshotPath`, and its `reporterId` must be non-null for a non-superadmin or the ⌘K palette becomes an ILIKE oracle over everyone's reports.
- **Screenshot intake is sniffed, not trusted.** Order in `createTicket`: validate, sniff the magic bytes, gate the decoded dimensions (a 4096² ceiling against decompression bombs), `put()` to the **private** store with `addRandomSuffix`, then insert — and if the insert throws, the orphaned blob is deleted. Only then does `after()` mail the superadmins with the image attached and set `emailSent`. A failed email leaves `email_sent = false` and **never loses the ticket**. The sniffers in `src/lib/ticketFields.ts` are reused wholesale by `avatarFields.ts` and `portfolioFields.ts` — fix them there, once.
- The screenshot stream is `private, no-cache` plus a SHA-256 ETag over the stored pathname — **deliberately not `immutable`**, so every view re-authorizes, while a 304 (answered *before* the blob fetch) still skips the up-to-4MB transfer.
- The activity row for a ticket **omits `description`** on purpose: free text may carry a pasted token.

### Logging & activity

Two separate products, deliberately not one system — different durability, retention, and audience.

- **Audit trail → Postgres.** `activity_log` (migration 0021) records who did what across every /admin surface, read at **`/admin/logs`** (the `'logs'` grant — a `SENSITIVE_AREA` like payroll: owner-flipped only, never in the explicit `DEFAULT_AREAS`, and safe to grant beyond superadmins precisely because no figure or secret can reach a row). `src/lib/activityLog.ts` is the single writer: synchronous, `void`-returning, body inside `after()`, failures only log — neon-http has no transactions, so an audit write can never be tied to the mutation it describes. **Call it only in the ok-branch**, after the real write succeeded. `write()` catches `after()`'s own throw and falls back to a fire-and-forget insert, because the Better Auth hooks call this during sign-in and a failed breadcrumb must never become a failed login.
- **Redaction is enforced, not remembered.** `ActivityPayload` (in `schema.ts`) allows scalars only, so `{...row}` is a *type error* rather than a privacy incident; `REDACTED_KEY_RE` in `src/lib/activityFields.ts` (a pure leaf, so it is testable) then refuses the values at runtime. **No payroll figure ever reaches `activity_log`** — `/admin/logs` is a wider audience than `requirePayrollAdmin()`, and payroll's whole privacy design is the own-vs-admin projection split a log line would otherwise route around. Submissions are referenced by kind + short id, never an applicant's name or email. Retention is **365 days**, swept from the daily `recurring-tasks` cron.
- **`task_events` and `payroll_events` stay as they are.** They carry domain columns (`task_title`, `month`, `member_name`) that are what make their own feeds readable. Those two domains write only their **structural and destructive** acts to `activity_log` as coarse, payload-free companion rows — routine task edits would otherwise bury every other domain in the global feed.
- **Diagnostics → stdout, via `src/instrumentation.ts`.** `onRequestError` catches every server throw (`routeType: 'action' | 'route' | 'render'`), which closes a real gap: an error thrown after the RSC stream begins is logged with a **200** status, so scanning for 5xx never found it. It filters client-aborted streams (`The destination stream closed early`, next.js#96704) — otherwise the most frequent "error" the app produces. The hook is **vendor-neutral**: an error tracker is one capture call inside that one function.
- **`src/lib/log.ts` is a ~80-line zero-dependency JSON logger** — Vercel's own documented recommendation for Functions. Not pino/winston: their worker-thread transports repeatedly break Next builds (next.js#86099, unresolved for Turbopack-on-Vercel). Two rules baked in: **stateless** (Fluid Compute reuses instances across concurrent requests, so module-level state leaks between them) and **never `console.warn`** — Vercel maps it to `warning` on a streaming function but **`error`** on a non-streaming one, so alerting on level misfires both ways. Use `log()` / `logError()`; the only surviving `console.*` calls are dev-only guarded ones and the client error boundary.
- **No third-party error tracker — decided 2026-08-19, don't re-propose one.** On Turbopack the browser SDKs cannot be tree-shaken (Sentry's `bundleSizeOptimizations`/`webpack.treeshake` are webpack-only), so the floor is 50–80 KB gz — most of what the 2026-07 chunk work removed. The account is on **Vercel Pro**, so runtime logs retain 1 day, which is the backstop. If it is ever revisited, a **server-only** install measures zero client JS and changes only `src/instrumentation.ts`.
- **Also not doing:** `@vercel/otel` (conflicts with tracker-side OTel setup, and a trace of one span is a log line with more machinery), Vercel Log Drains ($0.50/GB on *uncompressed* JSON), AsyncLocalStorage correlation IDs (no public Next 16 API; threading an id through `fetch` headers busts the fetch cache — `x-vercel-id` is recorded on the audit row instead), and any diagnostics table in Neon.

### Admin sessions

**24-hour idle window, 30-day ceiling** (Saman, 2026-08-22), both in `src/lib/sessionPolicy.ts` and pinned by `scripts/check-session-policy.mts`. Better Auth's `expiresIn` is the idle window and `updateAge` (5 min, equal to the cookie cache's `maxAge` because a cache hit never reaches the DB) is how often an active session is re-stamped; the ceiling is a `databaseHooks.session.update.before` clamp in `src/lib/auth.ts` that narrows the refreshed `expiresAt` to `createdAt + 30d`, so the auth layer itself — every endpoint, not just our wrapper — refuses to slide a session past a month from sign-in.

- **"Activity" means the dashboard is visibly open, and that is structural, not a heuristic.** Only server actions and route handlers can refresh a session: Next 16 throws on `cookies().set()` outside the `'action'` phase and the `nextCookies` plugin skips refresh on RSC navigations, so a render can never re-issue the cookie. The 90-second `POST /admin/presence` heartbeat — which already pauses while the tab is hidden and fires on focus — is therefore the app's designated refresher. Work every day and you are never prompted; close the laptop for a day and the browser has dropped the cookie before you return. Don't add input-event idle tracking (rejected: a visible dashboard on an unlocked screen counts as present; the OS lock screen is the control for walking away) and don't add a per-device "keep me signed in" (nobody asked).
- **The normal expiry is the proxy bounce, not a DB rejection.** The cookie's `Max-Age` equals the idle window, so an idle session is gone from the browser before the row is checked. The row-dead-but-cookie-present path (the ceiling landing mid-session, an admin revoking it) is caught by the layout's DB read, and by the heartbeat: `PresenceHeartbeat` follows the route's redirect and sends the open tab to `/admin/login` within 90 seconds instead of letting the next click fail with a generic toast.
- **Re-sign-in lands where you were.** `src/proxy.ts` appends `?next=<path+query>` to its bounce (with Next's `_rsc` prefetch param stripped); `/admin/login` re-validates it through `safeAdminReturnPath` — the same guard, never trusted raw — and shows "Sign in to continue to Tasks." The copy never claims *why* you were signed out: the proxy cannot tell an expired session from a first visit, and a wrong claim is worse than none. The RSC-side redirects (`requireAdmin`, `getAccessProfile`) stay bare `/admin/login` on purpose — they can't see the URL without plumbing a header through the proxy, and they only fire on the rare row-dead path.
- **A lapse is not an auth event.** `session.delete.after` returns without logging when the removed row had already expired (Better Auth deletes an expired row through that same hook when its cookie is presented late), so `/admin/logs` never reads "signed out or revoked" for someone who simply went home. The daily `recurring-tasks` cron prunes the remaining dead rows **directly** (`deleteExpiredSessions`, bypassing the adapter's hooks) and reports the count as `staleLoginsSwept` — not `sessionsSwept`, because the redaction denylist refuses any key containing "session" and a count is not worth an exception.
- **The clamp hook has three rules it must keep**: act only when the patch carries `expiresAt` (the `/update-session` endpoint runs the same hook with none); **never return `false`** (that aborts the update and `getSession` then deletes the cookie and throws UNAUTHORIZED); and stay wrapped, because on the server-side `auth.api.getSession` path it runs inline and a throw there is a 500 on every admin render. `ctx.context.session` is the row being refreshed — verified against `better-auth@1.6.23` (`session.mjs:179` → `:224`) and cited in the hook's comment; re-verify on a Better Auth upgrade.
- **Unrelated but adjacent, don't confuse the two:** `freshAge` (24h from *sign-in*, untouched) gates adding a passkey and `unlinkAccount`, not removing a passkey. A member whose session is a day old cannot register a passkey until they sign in again — pre-existing, and the ceiling doesn't change it.

### Blog content pipeline

A blog post has two coupled sources of truth and **both must be updated when adding a post**:

1. **Metadata entry** in `src/constants/blogs.ts` (`blogPosts` array) — drives routing, sitemap, SEO/JSON-LD, category/author cross-references, prev/next nav. The `slug` field maps to the URL (`/blogs/<slug>`), and `category.slug` selects the MDX subfolder.
2. **MDX body** at `src/content/blogs/<category-slug>/<slug>.mdx` — loaded at build time by `loadPostMdx()` in `app/(marketing)/blogs/[blog]/page.tsx`. Missing files fall back to `post.description` silently (no error in production, console.error in dev for non-ENOENT failures).

The MDX renderer is `next-mdx-remote/rsc` with `remarkGfm`. Custom components passed to MDX: `YouTube`, `Instagram`, `HowTo`, `ProsCons`, `SmartLink` (for `a`), `Image` (for both `img` markdown syntax and explicit `<Image>` calls — switches to captioned `<figure>` mode when `caption`/`credit`/`size`/`priority` props are set; falls back to a plain `<img>` at natural aspect when no `width`/`height` is supplied, so infographics aren't cropped by a forced 16:9 container — pass explicit dimensions to use Next/Image optimization), plus `h2/h3/h4` wrappers that slugify the heading text into an `id` so the in-page TOC anchors work. `extractHeadings`/`extractFaqs`/`extractVideos`/`extractImages`/`extractHowTos`/`countWords` in `src/utils/extractHeadings.ts` parse the raw MDX string to build the desktop/mobile TOC, FAQ/VideoObject/ImageObject JSON-LD, and reading time — they regex over the markdown source (detecting both `key="value"` JSX attrs and bare boolean attrs like `<YouTube external />`), so heavy JSX in MDX may not be counted.

The "Related Articles" + "Browse other topics" sections on a post page read every other category's MDX files at build time to compute aggregate reading minutes. This I/O is paid once per deploy.

### Authors

`BLOG_AUTHORS` in `src/constants/blogs.ts` is keyed by slug. Each post sets `authorSlug` (a literal union: `'perseus-creative-studio' | 'aryan-ghasemi' | 'saman-hoseinpour' | 'arshia-farahi'`). Every consumer — blog card byline, author profile pages, JSON-LD `Person`/`Organization`, sitemap filtering — resolves through `BLOG_AUTHORS[post.authorSlug]`. Adding a new author = adding a key to `BLOG_AUTHORS` and extending the `BlogPostAuthorSlug` union.

### BlogPost fields

`BlogPost` requires `imageAlt` in addition to obvious fields. Optional fields with consumer behavior worth knowing:

- `faqs?: { question, answer }[]` — overrides MDX-extracted FAQs for FAQPage JSON-LD. MDX FAQ section still renders for human readers; JSON `faqs` only governs schema.
- `relatedPosts?: string[]` — when set, the "Related Articles" section renders these exact slugs in order via `<BlogPost forcedSlugs={...}>`. When unset, falls back to category-based picker (`forcedCategorySlug`).
- `keyTakeaways?: string[]` — renders the "Key takeaways" box at the top of the article (`KeyTakeaways`), joins into the BlogPosting `abstract`, and adds `#key-takeaways` to the speakable selectors. 3–5 answer-first bullets (≤ ~20 words), never prices.
- `externalSources?: { title, href, rel? }[]` — renders the numbered "Sources" section after the body (`SourcesList`; per-source `rel` merges into the link's rel) plus schema.org `citation` on the BlogPosting, and gets its own TOC entry (`id="sources"`).
- `entities?: { name, sameAs, primary? }[]` — emits `about` (primary) / `mentions` (rest) Thing nodes on the BlogPosting, each `@id`-anchored to its first `sameAs` URL. Every `sameAs` URL must be a verified-live Wikidata/Wikipedia/official page before it lands in the registry.
- `excerpt?: string` — type only, not currently rendered.

### Media & SEO conventions

- **All images** are served through `<Img>` (`src/components/Img.tsx`), a thin `next/image` wrapper. Image slots store a `/images/...` path; **anything else resolves to `IMAGE_PLACEHOLDER` via `resolveImageSrc` (`src/utils/images.ts`)** — migrate a slot one at a time by pointing its constant at the real `/images/...` asset (public/images mirrors the route map; see `public/images/README.md`). When building OG/JSON-LD image URLs by hand, use `OG_IMAGE` / `resolveImageUrl` from `@/utils/images`, not a hand-built CDN string.
- **`<Img>` is server-only; client components use `<ImgClient>`.** `Img` auto-looks-up the blur-up placeholder from `src/lib/imageBlur.ts`, which imports the full generated base64 map and is guarded with `import 'server-only'` — a client component importing `Img` fails the build (that import used to ship the whole ~40 KB map in the shared client chunk on every route). `ImgClient` (`src/components/ImgClient.tsx`) renders identically but takes the placeholder as a `blur` prop: the server parent looks it up with `blurFor(src)` and threads it down (see Hero slides via `app/(marketing)/page.tsx`, navbar panels via `lib/navigation.ts`, services projections via `app/(marketing)/services/page.tsx`). Non-laddered marks (logos) have no blur entry — pass nothing.
- `next.config.ts` declares **no** remote image patterns — every image is a self-hosted AVIF under `public/images` — and the **runtime image optimizer is off**: `images.loader: 'custom'` (`src/lib/imageLoader.ts`) maps each requested width onto the pre-generated `-384/-640/-960/-1280` static variants (see `npm run image-variants` above), so there's no `/_next/image` transcode and no Vercel Image Optimization usage. Don't re-introduce the default optimizer, `formats`, or `unoptimized`. Because `/images/*` is served `Cache-Control: immutable`, changing an image's content requires a new filename, not an in-place overwrite.
- OG/JSON-LD images are self-hosted, so there's no on-the-fly cropping. Article JSON-LD (`articleImageSet` in `app/(marketing)/blogs/[blog]/page.tsx`) emits a single `ImageObject` at the resolved image URL rather than the 1:1/4:3/16:9 crop set; per-page OG images default to the shared placeholder until a real asset is wired in.
- The sitemap is a **sitemap-index route handler** at `src/app/sitemap.xml/route.ts` (Rank Math style, `dynamic: 'force-static'`, `revalidate: 3600`) pointing at five child handlers in `src/app/sitemaps/{pages,blogs,authors,projects,services}.xml/route.ts`. Those route files are thin — the logic lives in `src/lib/`: `sitemap.ts` holds the XML builders (`buildUrlSet`/`buildSitemapIndex`/`xmlResponse`) and enforces a **hard rule that no URL containing `?` or `#` is ever emitted** (so `?page=`/`?category=` views stay crawlable via on-page links but never appear in XML), while `sitemap-sections.ts` is the single source of truth: a `SitemapSection[]` both the index and each child derive from. **Adding a top-level page = add it to `CORE_PAGES` in `src/lib/sitemap-sections.ts`** (not the `pages.xml` route, which now just calls `pagesSection.build()`); adding a whole new child sitemap = one entry there plus a one-line route.
- `SITE_URL` (from `@/constants`) reads `NEXT_PUBLIC_SITE_URL` and defaults to `https://www.perseustudio.com`. Use it instead of hard-coding the domain.
- `public/llms.txt` is a **hand-maintained** AI-crawler index (positioning line, five service categories + sub-services, pillar-post reading list, contact email). It doesn't regenerate from the registries — update it when services, positioning copy, or flagship blog posts change, and bump its "Last updated" date.

### Structured data conventions

**Organization identity lives once.** `src/app/(marketing)/layout.tsx` declares the full `Organization` node with `@id: ${SITE_URL}/#organization`. Per-page schema (BlogPosting, CollectionPage) references it via `PERSEUS_PUBLISHER_REF = { '@id': '${SITE_URL}/#organization' }` exported from `src/constants/blogs.ts`. Don't inline the publisher object again — reference by `@id`.

**Author identity consolidates by `@id`.** `buildAuthorSchema` (`src/constants/blogs.ts`) returns the org author as `PERSEUS_PUBLISHER_REF`, and individual authors as a Person node whose `@id` is `${SITE_URL}/blogs/authors/<slug>#person` — the same `@id` the author profile page's Person node declares — so crawlers merge the article byline and the profile into one entity. E-E-A-T fields (jobTitle/description/image/knowsAbout/address/worksFor) come from `BLOG_AUTHORS`; enrich there, not inline.

**Video schema attribution.** `<YouTube id="..." external />` opts an embed out of VideoObject emission (videos on someone else's channel). Owned embeds carry an explicit `publisher: PERSEUS_PUBLISHER_REF`.

**Image license claims.** `creator` + `copyrightHolder` + `copyrightNotice` + `license` + `acquireLicensePage` only emit on ImageObjects when every embedded image is verified Perseus-owned or appropriately licensed. The `/license` page at `src/app/(marketing)/license/page.tsx` documents the terms. Two emission sites: `articleImageSet` (hero crops) and the inline `inlineImages.map(...)` block in `app/(marketing)/blogs/[blog]/page.tsx`.

### Global chrome

Chrome is layered across the two layouts. `src/app/layout.tsx` (root) holds only the document shell — Inter font, `<ConsentProvider>` → `<ThemeProvider>`, `<Toaster>` — so `/admin` shares one theme/consent root without loading marketing chrome or trackers. `src/app/(marketing)/layout.tsx` renders the public chrome once: `<SmartLenis>` (Lenis smooth-scrolling, desktop-pointer-only — skipped on touch and reduced-motion; `ReactLenis` re-exported from `src/utils/lenis.ts`), `Navbar`, `Footer`, `ScrollProgress`, `SpotLightLazy`, `ConsentBanner`, and the PWA components (`OfflineBanner`, `ServiceWorkerRegister`). Page-facing SEO defaults (title/OG/robots) also live in the `(marketing)` layout — not the root — so they never leak onto `(admin)`, which sets its own `noindex`. Analytics are **consent-gated** and `(marketing)`-only: `ConsentGatedAnalytics` reads the `ConsentProvider` state (persisted to `localStorage` under `perseus.consent`) and only then loads Google Analytics + GTM and Microsoft Clarity; Vercel `Analytics` + `SpeedInsights` are always rendered. Adding analytics elsewhere will double-fire and bypass consent — extend `ConsentGatedAnalytics`, not individual pages.

The admin rail has its own source of truth, `src/lib/adminNav.ts`: Overview sits bare at the top (`ADMIN_NAV_TOP`), everything else lives in `ADMIN_NAV_GROUPS` — Work, Inbox, Website, Team — and `ADMIN_ROUTES` is **derived** by flattening those, so the ⌘K palette (`CommandPalette.tsx`), the route-label lookup, and the ticket "where did you see it?" areas (`src/lib/ticketFields.ts`) all follow one ordering instead of a hand-synced second array. A group header renders only when the viewer can see at least one of its items, and on the 68px collapsed rail each header cross-fades to a centred hairline (`GroupHeading` in `AdminSidebar.tsx`) — the label stays mounted at `opacity-0` so screen readers keep the section names. Note `isAdminRouteActive` is a prefix match, which is why `/admin/my-pay` is not `/admin/pay`.

Every admin list focuses its primary input on arrival through `src/hooks/useSearchFocus.ts` — `useSearchFocus` (focus + the `/` hotkey + Escape) for search boxes, `useFocusOnMount` for a form's first field. Three rules are load-bearing. It is **desktop-only** (`(min-width: 64rem) and (pointer: fine)`, the ⌘B gate) so a phone doesn't pop its keyboard on every navigation; the decision is snapshotted in a `useState` initializer and never revisited, because a `?client=`/`?task=` deep link flips its flag one render later and a re-fire would steal focus out of the dialog that just opened. And **Escape is mandatory, not polish**: the inbox and task table bind single-key shortcuts (`j/k/x/e/s/z`) whose guards skip anything typed inside an input, so a focused search box mutes them — Escape empties the field, Escape again blurs it. Ship any new focus target with its Escape stage and its hint-row entry, or the shortcuts the legend advertises stop working. The `/` handler's target guard must stay the superset that includes Radix's `[role="menu"]`/`[role="menuitem"]`; the short version let `/` yank focus out of an open filter dropdown.

The dashboard's **⌘K palette** (`src/components/Admin/CommandPalette.tsx`, mounted once in the protected layout) is a cross-entity search over nine entities — task, comment, client, project, inquiry, application, ticket, user, activity — plus a "Go to" list built from `ADMIN_ROUTES` and filtered by `canSeeNavItem`. The vocabulary and the `task: brand video` scope grammar live in the client-safe leaf `src/lib/adminSearch.ts`; sidebar and mobile triggers reach the palette through the `perseus:admin-search-open` window event, because they are sibling islands with no shared client parent. Two invariants: **payroll is never searchable** — its entire privacy model is the own-vs-admin projection split, and a search path would be a third projection routing around it — and the action resolves the caller's profile **before** any DB work, gating each entity on its own area (tickets additionally row-scoped to the reporter unless superadmin), with the client-supplied `scopes` able only to *narrow*, never to widen.

**Page width is a three-way choice, and picking it is a content judgement, not a default.** `src/components/Admin/AdminPage.tsx` is the one wrapper: `narrow` (forms, detail views, the payslip — line length is the constraint), `wide` (lists, dashboards, card grids — grows one step at `2xl`), and `table` (pages whose main content is a horizontally scrolling `<table>`: tasks' eleven columns, the payroll month, the report's delivered work — width there buys visible columns, so it keeps climbing to `2100px`). The single-column list surfaces (users, logs, tickets, both inboxes, projects, the payroll roster) stay `wide` **on purpose** — stretching a row drags its right-hand meta away from the content it belongs to. So does `/admin/feedback`: it has a `<table>`, but a `max-w-lg` title cell plus five numeric columns caps it around 900px, so it can never overflow and the extra width would only push the numbers away from the post. Three gotchas: classes must be literal (the Tailwind scanner can't see computed names); **every skeleton's `Shell` must pass the same token as its page**, or `loading.tsx` renders at one measure and the page snaps to another — which is also why the tasks DIGEST is `table` despite having no table, since it shares `/admin/tasks`' one `loading.tsx` and toggling List↔Digest must not reflow the page; and adding a column step to a grid only helps if the container actually got wider at that same breakpoint (`2xl:grid-cols-8` on the clients grid was reverted for exactly this — `wide` caps at 1600, so eight tiles came out narrower than the six they replaced).

Two shape rules hold across every admin overlay, both learned from surfaces that ran the full height of the viewport. **A dropdown caps at `min(22rem, <the Radix available-height var>)`, never the var alone** — the var means "as much of the viewport as there is", which is how the 85-row client list became a full-page column; the `min()` keeps the var as the outer bound so short viewports still shrink. The recipe lives once in `src/components/Admin/menu.ts`, and a popover whose first child is a search field uses `comboPanel`/`comboList` instead, so the field stays pinned while only the results scroll. **A dialog earns width by splitting, not by stretching**: `GlassDialog`'s rungs below 40rem are single-column, and the 44/48/52rem rungs are for bodies that go `md:grid-cols-2` — reaching for a wide rung without giving the body columns to fill just makes a long form wider. Its optional `header`/`footer` slots render outside the scroller so a tall form keeps its title and its Save button in view; passing neither is byte-identical to the original single-scroller shape, which is why the confirm-sized dialogs were left alone. The footer sits outside the `<form>`, so a submit button there needs `form={FORM_ID}`. Note the scroller must NOT carry `flex-1`: `flex: 1 1 0%` zeroes the basis, and Content is `max-h-full` rather than `h-full`, so there is no free space to grow back from — default shrink against `shrink-0` slots is what does the work.

Each admin section carries an ⓘ **help guide**: `src/lib/adminHelp.ts` is a `server-only` registry of 16 topics that the server-rendered header passes to `src/components/Admin/HelpButton.tsx` as **one serializable topic prop** (the button uses `import type` only). Keep that shape — importing the registry from the client would ship every guide into every admin route's chunk. The guides are voiced for their audience, which is a privacy rule as much as a tone one: the `my-pay` topic is written to the member and must never say "anchor", "wire fee", "company cost", or mention admin notes, and no guide anywhere carries a money figure. **When a section's UI changes, its guide changes with it** — a stale guide is worse than none.

`Navbar` (desktop mega-panels), `MobileMenu`, and `Footer` all read their link structure from one source of truth — `src/lib/navigation.ts` (`navItems` plus per-panel builders for the services/projects/blogs mega-panels). Edit destinations there, not in the individual chrome components, so desktop and mobile can't drift apart.

### Offline / PWA

The site is an installable PWA with real offline support, built **without** a PWA library (no `next-pwa`/`serwist`) because Next 16 builds with Turbopack, where their webpack plugins are unreliable. Pieces:

- **Service worker** — `public/sw.js`, a hand-written plain-JS file (not bundled/typed). All cache names are prefixed with a single `VERSION` constant; the `activate` handler deletes any cache not matching it, so **bumping `VERSION` is how you invalidate everything**. Strategies: precache app shell on install; navigations + RSC fetches network-first → cache → precached `/offline`; `/_next/static/*` cache-first (content-hashed = safe); self-hosted images (`/_next/image` + `/images/`) stale-while-revalidate (capped). Non-GET requests (including server-action POSTs) and analytics are never cached, and the authenticated `/admin` + `/api/*` paths plus the tokenized `/share/*` report links are ignored entirely — never cached, no offline fallback (privacy; a revoked share must not stay readable from cache).
- **Registration** — `src/components/Pwa/ServiceWorkerRegister.tsx` registers the SW **browser-only and production-only** (disabled in `npm run dev` so it doesn't cache HMR assets). Don't expect offline behavior in dev — verify with `npm run build && npm run start`.
- **Manifest** — `src/app/manifest.json` (Next metadata-file convention, served at `/manifest.json`, `<link rel="manifest">` auto-injected). `themeColor`/`appleWebApp` live in `layout.tsx`'s `viewport`/`metadata`.
- **Offline write outbox** — the contact form is the only client mutation. When offline (or a send drops mid-request), `src/components/Contact/ContactHub.tsx` queues the payload — including a **byte snapshot** of the resume, never the live `File`, whose on-disk backing can move before the flush — via `src/lib/contactOutbox.ts` on top of the zero-dependency wrapper `src/lib/offlineDb.ts`. `OfflineBanner` flushes the queue on the `online` event and on mount, replaying each record through the `submitContact` server action (at-least-once; deleted after confirmed send, or dropped if the action deterministically rejects it so one bad record can't poison the queue). `contactOutbox.ts` rides the shared chunk via OfflineBanner — it must never import zod/`contactSchema.ts`, and it dynamic-imports the action. See `OFFLINE.md` for the full strategy table and test checklist.

### Component organization

`src/components/index.ts` is the **barrel export** every page imports from. New shared components should be added there. Domain-specific subfolders mirror routes (`Home/`, `About/`, `Blogs/`, `Services/`, `Projects/`, `Contact/`, `Mdx/`, `Admin/` for the dashboard — its glass tokens live in `Admin/Glass.tsx` and its dropdown/popover panel recipe in `Admin/menu.ts` (one door: five bars had private copies and they drifted; `Admin/tasks/menu.ts` re-exports it and keeps only the in-cell editor grammar) — plus `Pwa/` for the service-worker / offline UI). The shadcn-style primitives live under `src/components/ui/` (configured in `components.json`, style `new-york`, alias `@/components/ui`, `@/lib/utils`).

**The barrel is for pages/layouts only — components must import each other by direct path** (`@/components/Button`, `./BlogCard`, …), never from `@/components`, `./`, or `..` resolving to the barrel. A component importing the barrel creates a components↔index cycle that defeats Turbopack's export-level tree-shaking: every client component that touched the barrel used to drag the re-exported *server* components — and through them the entire `services.ts`/`blogs.ts` registries — into one shared client chunk loaded by all 86 routes (~110 KB gzip of dead JS per page before the 2026-07 de-barreling). Same discipline for data: client components take slim server-derived props (see `blogFeed.ts`, `lib/navItems.ts` vs `lib/navigation.ts`, and the Services overview projections in `app/(marketing)/services/page.tsx`) instead of importing the content registries; verify with `rg -l "We align on goals" .next/static/chunks/` after a build — it must come back empty.

**Chunking reality (2026-07 audit):** Turbopack merges every *eagerly referenced* client module into one shared chunk group — all routes list the same script set, so anything a client component imports eagerly is paid by every page. Two consequences: (1) content data must never be a client value import — `faqItems` lives in `src/constants/faq.ts` (FAQ page passes it to `<FaqList items={…}>`), the Partners marquee logos come from Postgres via `getPartnerLogos` (`src/lib/projectsStore.ts`) and reach `<Partners>` as slim server-derived props, the home hero gallery in `src/constants/homeGallery.ts` (home page passes slides to `<Hero gallery={…}>`), and the about timeline entries flow through `<Timeline entries={…}>` — keep new content data in leaf modules (or server-side DB reads) imported only by server components. (2) Heavy page-specific client components are code-split with `next/dynamic` **keeping SSR** (cobe globes in `HomeWelcome`/`ServicesHero`, embla primitives in `ServicesAds`, the apple-cards carousel in `ServicesList`, the contact form in `ContactHubLazy` — zod lives only in that async chunk) — the async chunk loads only where the component renders; don't convert these back to static imports. three.js (`shader4/5` behind `ThemedShader`) already follows this pattern.

### The `src/lib/` map

Sixty-odd modules, most of them deliberately small. The organising idea is **one door per concern**: where a rule could be re-implemented inconsistently, exactly one module owns it and everything else calls that. Reach for the existing door before adding a helper.

- **Single doors (never re-derive these elsewhere).** `calendar.ts` — the only module that may name a timezone or turn an instant into a calendar day. `payrollAmounts.ts` — the only place payroll money is parsed, formatted, converted or prorated (advertised job pay is display copy, formatted by `careerFields.formatPay`, and is not its concern). `taskFields.ts` — the only place minutes become hours. `mail.ts` — the one Resend door. `activityLog.ts` — the one audit writer. `publicBlob.ts` — the one door to the **public** Blob store (the store's access mode is fixed at creation, which is why there are two stores and no fallback between them). `printSheet.ts` — the one print stylesheet, shared by the report sheet, the share page and the payslip.
- **Authorization.** `adminAccess.ts` is the seam: `getAccessProfile`, `requireArea`, `requireSuperadmin`, `requirePayrollAdmin`/`requireOwnPayroll`/`requirePayrollAccess`, `visibleKinds`, `viewerZone` — all reading the user row **fresh on every request**, never from the session cookie's cached copy, deduped per request with React `cache()`. `adminAreas.ts` is its client-safe vocabulary, `adminNav.ts` the one map of the route tree, `adminSession.ts` the single `getSession` call site. `sessionPolicy.ts` is the pure leaf that fixes the sign-in lifetime (see "Admin sessions" below).
- **Security predicates that look like formatters — treat them as controls.** `avatarPaths.ts` (`user.image` is user-writable through Better Auth, so only allowlisted pathname shapes may be streamed), `activityFields.ts` (the redaction denylist), `logFields.ts` (`describeError`/`scrubContext` — Drizzle leaks bound params into `error.message`), `usersSchema.ts` (the server parse **is** the password control, because Better Auth's internal adapter bypasses `minPasswordLength`), and `csv.ts` (RFC 4180 plus a formula-injection guard, with `+1 604…` phone numbers exempted).
- **URL-state contracts**, one per list surface, all zero-dependency so they stay client-safe: `taskFilters.ts`, `inboxFilters.ts`, `activityFilters.ts`. Each fixes a canonical param order and drops defaults from the URL.
- **Zod schemas**, deliberately separate from the field vocabularies so the client can import the constants without importing zod: `contactSchema` (must stay a leaf — never import the services registry), `taskSchema`, `ticketSchema` (`server-only`), `portfolioSchema`, `careersSchema` (carries the open-requires-pay rule), `payrollSchema`, `usersSchema`, `authSchema` (UX only, **not** a security control).
- **Client-safe field vocabularies + upload pre-checks:** `taskTagFields.ts` (the tag groups, chip tones, limits and the `tagInScope`/`splitTagsForCategory` scope predicate — a zero-dependency leaf so the board, quick-add, the dialog and the filter bar all share it without dragging zod into a client chunk), `ticketFields.ts` (whose magic-byte sniffers and dimension gate are reused wholesale by `avatarFields.ts` and `portfolioFields.ts`), plus `reduceScreenshot.ts` (client-only canvas downscale — no sharp, no new dependency).
- **Export builders:** `adminExport.ts`, `taskExport.ts`, `payrollExport.ts`.
- **Content, media and SEO:** `projectsStore.ts` (the cached, tag-invalidated portfolio read layer), `careersStore.ts` (the same for job openings — the careers page, the contact form's roles, the FAQ's hiring answers and the pages sitemap all read it), `careerFields.ts` (the client-safe careers vocabulary + the copy composers) with `jobCategoryIcons.ts` (its icon map), `navigation.ts` (server-only in practice — it derives the mega-panels from the full registries at module scope) vs `navItems.ts` (the client-safe half), `imageLoader.ts` / `imageVariants.ts` / `imageBlur.ts` + the generated `imageBlur.generated.json`, `sitemap.ts` / `sitemap-sections.ts`, `indexnow.ts`, `googleReviews.ts`.
- **Offline:** `offlineDb.ts` (the IndexedDB wrapper) and `contactOutbox.ts` (the queue) — neither may import zod.
- **Small leaves with no dependencies**, kept separate so heavy data stays out of shared chunks: `passwordStrength.ts` (its `COMMON_PASSWORDS` set must not reach the login chunk), `phoneCountries.ts`, `referralOptions.ts`, `emailSuggest.ts`, `formatBytes.ts`, `greeting.ts`, `presence.ts`, `payrollStatus.ts`, `authAudit.ts`, `adminSearch.ts`, `utils.ts` (`cn`).

### Styling

Tailwind CSS 4 with `@tailwindcss/postcss`, `@tailwindcss/typography`, and `tw-animate-css`. Global tokens and CSS variables are in `src/app/globals.css`. Conditional class merging uses `clsx` + `tailwind-merge` (re-exported as `cn` from `src/lib/utils.ts`).

**Pointer cursors are a base-layer rule, not a per-component class.** Tailwind v4's preflight dropped v3's `button, [role="button"] { cursor: pointer }`, so every hand-rolled `<button>` silently reverted to an arrow — only the shared `Button` primitives carried the class. `globals.css`'s `@layer base` block restores it as `button:not(:disabled), [role='button']:not(:disabled)`. Don't add `cursor-pointer` to individual buttons; do keep using explicit `cursor-not-allowed` / `cursor-text` / `cursor-grab` / `cursor-default` where the pointer is wrong, because the utilities layer is ordered after `base` and still wins.

## Conventions to respect

- **Server-first.** Only mark a component `'use client'` when it needs state, effects, or browser APIs. The blog index page passes server-read `searchParams` down to `<BlogPost>` as `initialCategory`/`initialPage` specifically to avoid a `useSearchParams()` CSR bailout so crawlers see article links in initial HTML — don't refactor that into pure client state.
- **Blog routing is URL state, not routes.** Do not propose `/blogs/category/<slug>` pages; keep `/blogs?category=<slug>`.
- **Main content before sidebar in DOM.** On `app/(marketing)/blogs/[blog]/page.tsx`, the main content `<div>` is placed BEFORE the desktop sidebar `<aside>` in source order. CSS grid `col-start-1` / `col-start-2` puts the sidebar visually on the right. This DOM order is intentional — putting the sidebar first caused a heading-order violation (H1 → H3 from SidebarCta) that AI-search audits flag on every post.
- **No `#posts` fragment in pagination hrefs.** Blog pagination uses `<Link scroll={false} href={...}>` and a `useEffect` watching `initialPage` to scroll `#posts` into view. Crawlers like Semrush flag the fragment-bearing URL as canonicalised against the fragment-free canonical — keep the fragment behavior client-side only.
- **Parameterised views navigate via `NavButton`, never `<a href>`.** Facet-filtered project views (`?service=` / `?industry=` / `?location=`) and contact prefills (`?tab=careers&role=`) canonicalise to their bare path and must not enter the crawl graph: emitted as links they audit as hundreds of thin single-link/deep pages, and robots-blocking them instead makes Semrush count each one as "blocked from AI search" (AI Search Health 95→85 — both tried, 2026-08-03). `src/components/NavButton.tsx` (`router.push` + hover/focus prefetch, honors `preventDefault` like `<Link>`) is the pattern — the URL still updates and deep links stay shareable. Deliberate exceptions that stay real anchors: `?page=N` pagination and `/blogs?category=` (indexable by design, self-canonical). Keep `src/app/robots.txt` allow-all except `/admin` + `/api/` — crawl-surface control lives at the link layer, not in robots.
- **Content changes carry a freshness ritual.** A blog edit sets the post's `updatedAt`; a services copy edit bumps that record's `seo.lastUpdated` (drives sitemap `<lastmod>`, the visible "Updated" line, and WebPage `dateModified`). After the change deploys, ping IndexNow for the affected URLs (`npm run indexnow` — see Commands). Careers edits made in /admin ping themselves. Date bumps and pings only ever accompany real content changes — never bump a date or ping an unchanged URL.
- **Two clocks, one door.** `src/lib/calendar.ts` is the only module that may name a timezone or turn an instant into a calendar day. Everything a signed-in person reads — task-date defaults, the Today/Tomorrow chips, overdue tints, the digest's day headings, report and leaderboard month windows, every timestamp on every screen — resolves in **their own** zone via `viewerZone()` (`src/lib/adminAccess.ts`), stored on `user.timezone`. That column is **derived, never chosen** — `TimezoneSync` writes whatever the browser reports on the next /admin render after it changes, and `/admin/profile` shows it read-only. There is deliberately **no manual override, and don't add one**: `resolvedOptions().timeZone` is the OPERATING SYSTEM's zone (not the network's — a VPN doesn't move it), so it already follows a real relocation on its own, and a pinnable setting could only make dates wrong (pin, move, and every date is silently a day off with nothing on screen to explain it). A zone this runtime's ICU can't resolve is logged as `timezone.rejected` — with no override, that log line is the only way a stuck zone becomes diagnosable. Only the surfaces with **no viewer to follow** take a fixed zone: the public `/share/reports/[token]` page (stamped with the minting admin's zone on the share row, so the client sees exactly what was sent), the weekly-digest and recurring-tasks crons (`STUDIO_TZ` — a daily template must fire once per studio day, not once per member), the estimate-stats window, and the marketing site's Vancouver office clock (`StudioStatus`, `Stats`, `FooterClient`, `MobileMenu` — a real fact about a real office). **A formatter with no `timeZone` option is a bug, not a viewer-local default** — an unpinned `Intl.DateTimeFormat` resolves to the RUNTIME's zone, which is UTC on Vercel; use `zonedFormat(tz, …)`, or pin `'UTC'` when the input is a calendar KEY rather than an instant (`YYYY-MM-DD` has no instant behind it — that is why `Admin/tasks/format.ts` is UTC on purpose). Accepted consequence of viewer-relative month windows: a task completed Aug 31 at 20:00 Vancouver time is Sep 1 in Tehran, so it counts toward August for a Vancouver reader and September for a Tehran one. That was a deliberate call (most of the work is done in Tehran, so the report agreeing with whoever did it is the truer reading) and it is pinned in `scripts/check-calendar.mts`.
- **Don't run git commands.** The maintainer handles all git operations; suggest commit messages instead of executing them.
- UI/redesign work: avoid generic agency/SaaS aesthetics (glass tiles, grayscale hover, soft drop-shadows) — distinctive design is the bar.
